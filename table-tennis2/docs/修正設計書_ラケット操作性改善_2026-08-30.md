## 1. 目的・背景

### 1.1 目的

1. ボールへ位置を合わせるpassive trackingでは、ラケット面をニュートラル姿勢へ安定させる。
2. touchはrelease後350ms、mouse / penは220msまで、最後の位置で実衝突を受けられるようにする。
3. active strikeの鮮度は160msのまま維持し、拡大したcontact猶予へ古い技判定を持ち込まない。
4. 可視補助輪郭へball外周が届いた接触は、少なくとも通常のpassive PUSHを成立させ得る品質へ揃える。
5. 568×320を含む対応viewportで、通常のAI返球軌道が縦方向のclampだけを理由に到達不能にならないようにする。
6. 自動吸着を追加せず、実軌道から求めた迎球位置を弱いガイドとして表示する。

### 1.2 安定性優先順位

本修正では次の順で判断する。

1. 描画と衝突の同一pose、depth gate、1 flight 1 contactを壊さない。
2. passive操作とactive strikeを時間・姿勢の両方で分離する。
3. 補助輪郭の見た目と返球可能性を一致させる。
4. 既存物理・AI・サーブ・保存・PWAを変更しない。
5. 操作感の最終判定は自動試験で代替せず、iPhone Safari実機で確認する。

## 3. 現状コードと原因

### 3.1 処理経路

```text
PointerEvent
  -> src/input.ts InputController.ingest()/onPointerUp()
  -> src/control/stroke.ts deriveStrikeMetrics()
  -> src/control/paddle.ts PaddleController
  -> src/control/contact.ts sweptPaddleContact()
  -> src/control/shot-intent.ts buildShotIntent()
  -> src/physics.ts solveDirectPlayerShot()
  -> src/game.ts Game.directPlayerContact()
  -> src/render.ts Renderer
```

描画中心と衝突中心は `PaddlePose.screenX/screenY` を共有している。この所有権は変更しない。

### 3.2 原因A：passive移動が姿勢へ流入する

`PaddleController.applyInput()` はtracking速度 `0.15` 以上で `targetAngle` / `targetTilt` を更新する。一方、active strikeは `speed >= 1.10`、`displacement >= 0.04`、`verticality >= 0.55` のAND条件である。このため、技にならない位置合わせでもラケット面だけが回転する。

さらに現在の角度補間は `target - current` の単純差であり、`+π/-π` 境界を跨ぐtarget変更で遠回りする余地がある。

### 3.3 原因B：1つのrelease期限が3責務を持つ

`RELEASE_GRACE_SEC = 0.16` は次の用途で共有される。

- release後の `follow` phaseとcontact eligibility。
- release時に固定した `releaseStrike` snapshotの有効期間。
- `beginContact()` 後の `followUntil` 再設定。

単に値を350msへ伸ばすと、release時に `active: true` だった固定snapshotも再評価されず350ms残る。また `beginContact()` が期限を延長すると、接触後の新しいflightまで無入力でcontact eligibleになる危険がある。

### 3.4 原因C：可視輪郭端の品質が0まで下がる

`sweptPaddleContact()` はassist楕円とball半径で接触を成立させるが、品質はball半径を含まないassist楕円に対して計算する。

```text
screenQuality = clamp(1 - sqrt(qAssist), 0, 1)
timingQuality = clamp(1 - depthDistance / tolerance, 0, 1)
rawQuality = 0.70 * screenQuality + 0.30 * timingQuality
```

輪郭端では `screenQuality = 0` になり得る。`solveDirectPlayerShot()` は `qualityLoss^2 * 0.16` を誤差へ加えるため、見える輪郭へ触れたのにネット・アウトになる割合が高い。また現在は `contactQuality > 0.3` のときだけ `ensureNetClear()` を通るため、極端な低品質はこの保護も受けない。

### 3.5 原因D：568×320でY上限側に届かない軌道がある

現在の `PADDLE_SCREEN_Y_MIN = 0.45` は、568×320で中心を144pxより上へ置けない。2026-08-30の設計調査では、現行の `OpponentAi.decideShot()` → `solveShot()` → `solveContactPlane()` → `predictAt()` → `projectWorldPoint()` を通す固定母集団30,362件について、Yだけが原因の到達不能がfine 6件、touch 3件あった。

同じ母集団で `PADDLE_SCREEN_Y_MIN = 0.35`、fine assist `1.20`、touch assist `1.40`、最大tilt時の縦squash `0.85` を適用すると、5 viewportすべてで到達不能は0件、最小余裕は568×320 fineの1.304pxだった。この結果から0.33への追加拡大は不要と判断し、変更量の小さい0.35を採用する。

### 3.6 原因E：迎球位置を示す状態がない

`Game` はAI打球時に `player.z = solveContactPlane(...)` を設定し、`predictAt()` と共有投影も利用できる。しかし現在の `RenderScene` は着地点 `mark` とsmash可否だけを持ち、player側bounce後の迎球位置を保持しない。

## 5. 詳細仕様

### 5.1 passive / active姿勢

`PaddleController` は各input/frameで `deriveStrikeMetrics()` を一度だけ評価し、その結果をphaseと姿勢targetの両方へ使う。

| strike | phase | target angle | target tilt |
|---|---|---:|---:|
| `active = false` | `tracking` | `π / 2` | `0` |
| `active = true` | `armed` | `atan2(vy, vx) + π / 2` | `clamp(directionY + curvature * 0.4, -1, 1)` |

- tracking速度 `0.15` による姿勢更新は削除する。
- pointerが動き続けていてもactive条件を満たさなければ、targetは毎回ニュートラルへ戻す。
- pointer入力が止まり80ms窓からactive sampleが外れた場合も、次frameでニュートラルtargetへ戻す。
- 位置、予測、速度、contact判定は従来どおりで、姿勢だけをstrike由来に限定する。

角度補間は次の最短差を使う。

```text
delta = atan2(sin(target - current), cos(target - current))
angle = current + delta * alpha
```

`shortestAngleDelta(current, target)` は `src/control/paddle.ts` のexportされた純粋関数とし、`tests/paddle-pose.test.ts` から直接境界検査する。補間tauとspeed ratioは現行値を維持する。

### 5.2 strike鮮度とcontact猶予の分離

#### pointer down中

- `deriveStrikeMetrics()` は既存80ms窓とactive 3条件を維持する。
- activeのage条件だけ `STRIKE_ACTIVE_MAX_AGE_SEC` を参照する。
- `tracking` / `armed` はcontact eligibleである。

#### release時

`PaddleController.release(time)` は次を順に行う。

1. 現在historyから `releaseStrike` を1回計算する。
2. `releaseStrikeCapturedAt = time` を保存する。
3. `pointerDown = false`、phaseを `follow` にする。
4. 保持済みpointerTypeがtouchなら `contactFollowUntil = time + 0.35`、mouse / penなら `time + 0.22` とする。
5. pointerTypeがnullなら `contactFollowUntil = time` とし、接触可能状態を新規に作らない。

#### release後のstrike再評価

`getStrikeMetrics(time)` は固定snapshotの数値をそのまま延命しない。

```text
releasedAge = releaseStrike.age + max(0, time - releaseStrikeCapturedAt)
active = releaseStrike.active && releasedAge <= 0.16
```

- contact grace内でも161ms以後は `active = false` とし、同じsnapshotの速度・方向はdebug用に保持してよいが、`buildShotIntent()` はpassive PUSHとして扱う。
- 160msちょうどはactive可、160msを超えた最初の時刻でfalseとする。
- contact grace期限後はzero metricsを返す。

#### contact時

`beginContact(time)` は `phase = "contact"` と `contactFlash = 1` だけを行い、`contactFollowUntil` を延長しない。次frameで `contact -> follow` へ移るが、元のrelease期限を超えていれば即 `recover` へ進む。pointer down中なら同frameのstrike評価により `tracking` / `armed` へ戻る。

#### reset / cancel / suspension

`reset()` はsnapshot、captured time、contact期限、pointerType、debug値を全て破棄する。既存 `InputController.onPointerCancel()`、pause、portrait、too-small、pagehideからのreset経路を維持し、graceを再生成しない。

### 5.3 contact assistとquality floor

楕円の中心、角度、tilt squash、ball半径、relative sweep、depth toleranceは変更しない。

```text
assistVisualRx = visualRx * pointerAssistScale
assistVisualRy = visualRy * pointerAssistScale
collisionRx = assistVisualRx + ballRadius
collisionRy = assistVisualRy + ballRadius
```

接触が成立した後だけ品質下限を適用する。

```text
screenQuality = clamp(1 - sqrt(qAssist), 0, 1)
timingQuality = clamp(1 - depthDistance / tolerance, 0, 1)
rawContactQuality = clamp(0.70 * screenQuality + 0.30 * timingQuality, 0, 1)
contactQuality = max(0.40, rawContactQuality)
```

- assist外、depth外、pointerType未確定は従来どおり `null` であり、floorでhitboxを広げない。
- `screenQuality` と `timingQuality` はfloor前のraw値を `ContactEvent` へ残す。
- `contactOffsetX/Y` は従来どおりassist楕円基準であり、aimを変更しない。
- raw品質が0.40以上の中央・通常接触は値を変更しない。
- `solveDirectPlayerShot()` は変更しない。結果としてすべての有効接触が既存 `contactQuality > 0.3` 条件を満たすため、非arc shotは `ensureNetClear()` の対象になる。この分布変更を固定seed校正で検査する。

### 5.4 Y可動域

`PaddleController.baseCenter()` のclamp順序を維持し、上側比率だけ0.35へ変更する。

```text
rawY = stageY * height - pointerOffset * height
ratioClampedY = clamp(rawY, 0.35 * height, 0.90 * height)
screenY = clampPaddleScreenY(ratioClampedY, height, radius)
```

- `clampPaddleScreenY()` によるblade・handle下端保護を維持する。
- 画面上端0まで広げない。
- HUD、Canvas寸法、pointer offset、X clamp、`PADDLE_LIMIT` は変更しない。
- Y到達試験では、Xが `PADDLE_LIMIT` 内の有効返球だけを母集団とし、X到達性の再設計と混ぜない。

### 5.5 迎球位置ガイド

#### 状態所有権

`src/types.ts` に次の読み取り用状態を追加する。

```text
PlayerContactGuide {
  x: world X
  y: world Y
  z: player contact plane
  plannedAt: simulation time
  etaSec: bounce時点からcontact planeまでの予測秒
}
```

`Game` が `playerContactGuide: PlayerContactGuide | null` を所有する。Rendererは再計算せず描画だけを行う。

#### 計算タイミング

- AI起点のballがplayer側tableへ実際にbounceし、`judgeBounce()` が `bounces = 1` を確定した直後に一度だけ計算する。
- `predictAt(this.ball, this.player.z, -1, FLOOR)` を使い、成功時にworld座標と `etaSec` を保存する。
- per-frameで `predictAt()` を呼ばない。軌道シミュレーションはincoming flightにつき1回とする。
- net、table外、予測失敗ではガイドを作らない。

#### 破棄タイミング

- playerのscreen contactが成立した時点。solverが非有限で返球できない場合も再接触させない現行flight lockに合わせて破棄する。
- point、new game、serve開始、player起点の新flight。
- `ball.hitter !== "A"` またはphaseがrally以外へ変わった場合は描画しない。状態が残っていても表示条件でfail closedにする。
- pointer cancel / pause / pagehideではball flightとsimulationが維持されるためguide stateを破棄しない。入力期限だけをresetし、復帰後は同じworld予測を現在cameraで再投影する。

#### 表示条件

次をすべて満たす場合だけ表示する。

```text
controlModel === "direct-paddle-v1"
state.phase === "rally"
ball.live === true
ball.hitter === "A"
ball.bounces >= 1
ball.vz < 0
playerContactGuide !== null
```

#### 描画

- `Renderer.render()` は `drawMark()` の後、`drawBall()` の前に `drawPlayerContactGuide()` を呼ぶ。
- world座標をRendererの現在cameraで毎frame投影し、viewport変更へ追従させる。
- 半径は `clamp(paddleScreenRadius(width, height, paddleDepthRatio(z)) * 0.55, 7, 12)` px。
- stroke色は `rgba(126, 224, 168, alpha)`、塗りなし、line widthは `max(1.5, radius * 0.16)` px。
- 残り時間 `remaining = etaSec - (simulationTime - plannedAt)` によりalphaを決める。

| remaining | alpha |
|---|---:|
| `> 0.35s` | `0.25` |
| `0.10s < remaining <= 0.35s` | `0.40` |
| `0s < remaining <= 0.10s` | `0.40 * remaining / 0.10` |
| `<= 0s` | 非表示 |

ガイドは「現在軌道から求めた迎球目安」であり、ラケット・ball・衝突状態へ副作用を持たない。

`?debugInput=1` のときだけ、既存datasetに次を追加・同期する。

|---|---|---|
| `data-paddle-angle` | 現在angle、rad、3桁 | poseなしで削除 |
| `data-paddle-tilt` | 現在tilt、3桁 | poseなしで削除 |

## 6. 状態遷移

```text
idle
  -> pointerdown -> tracking
tracking
  -> active strike -> armed
armed
  -> active失効 -> tracking
tracking / armed
  -> pointerup -> follow (pointer別contact期限、release snapshot保存)
tracking / armed / follow
  -> screen+depth contact -> contact (flash、期限は延長しない)
contact
  -> next frame -> tracking / armed (pointer down中)
  -> next frame -> follow / recover (pointer up後)
follow
  -> contact期限超過 -> recover (snapshot破棄、pointerTypeはrecover完了まで保持)
recover
  -> 待機位置到達 -> idle (pointerTypeをnull化)
any
  -> cancel / suspension / point reset -> recoverまたはidle、全期限破棄
```

時間比較は既存wall clock `performance.now()/1000` domainを使い、`simulationTime` はガイドの残り表示だけに使う。contact eligibilityへsimulation clockを混ぜない。

## 7. 既存機能の非破壊条件

### 7.1 direct操作

- pointer X/Y、touch 6% / mouse・pen 1% offset、16ms / 高さ5%予測を維持する。
- interaction / render / contact centerを同一値に保つ。
- relative swept ellipse、ball外周、depth gate、pointerType必須を維持する。
- `lastPlayerContactFlightId` による1 flight 1 contactを維持する。
- `aimX = clamp(-0.65 * contactOffsetX, -0.65, 0.65)` を維持する。
- passiveはPUSH、activeだけが技・power・spinを持つ。

### 7.2 物理・AI・ゲーム

- `FIXED_STEP = 1 / 240`、`MAX_SUBSTEPS`、integrate、bounce、netを変更しない。
- `solveDirectPlayerShot()` のtarget、speed model、spin carry、quality二乗誤差、乱数3回の順序を変更しない。
- AIの判断、接触面、乱数順、serve種類・長さを変更しない。
- 11点2点差、serve / rally / point、score、戦績を変更しない。

### 7.3 保存・PWA・プライバシー

- IndexedDB名 `table-tennis2`、schema、既存データを変更しない。
- 公開URL、manifest identity、root/child Service Worker分離を変更しない。
- 実装時は `package.json` / `package-lock.json` をv0.2.3へ同期し、child cacheを `table-tennis2-v0.2.3` にする。
- 新規依存、権限、network request、telemetryを追加しない。

## 10. テスト設計

### 10.1 pose / phase / time

`tests/paddle-pose.test.ts` に次を追加する。

- speed 0.80のpassive trackingはtarget angle `π/2`、tilt `0`へ収束する。
- active upward / downwardだけが姿勢targetを変える。
- current `π - ε`、target `-π + ε` と逆方向でdelta絶対値が `2ε` 以下になる。
- touchは350msちょうどまでeligible、350ms超でfalse。
- mouse / penは220msちょうどまでeligible、220ms超でfalse。
- release snapshotは160msちょうどまでactive、160ms超でpassive。同時にtouch contactは350msまでeligibleである。
- `beginContact()` 前後で元のrelease deadlineが変わらない。
- pointerType nullのreleaseは接触を作らない。
- cancel/reset/pause相当reset後は期限、snapshot、assistが残らない。

### 10.2 contact

`tests/paddle-contact.test.ts` で次を固定する。

- touch `1.40`、mouse / pen `1.20` の輪郭内、一致、ball外周一致、直後。
- assist端・timing端でも、contactが成立した場合は `contactQuality === 0.40` 以上。
- 中央のraw品質0.40超はfloorで変わらない。
- `screenQuality` / `timingQuality` はfloorされない。
- assist外、depth外、pointerType nullは `null`。
- tilt `0` / `±1`、depth ratio `0 / 0.5 / 1` で有限値を保つ。

### 10.3 物理校正

既存seed `20260805`、3打点、各400試行を維持する。`buildShotIntent()` → `solveDirectPlayerShot()` の製品intent経路でpassive PUSH、quality `0.40`を追加する。

### 10.4 Y到達固定母集団

`tests/reachable-contact.test.ts` は既存製品関数を使い、独自の簡略投影を作らない。

#### 母集団

- 乱数: `tests/direct-calibration.test.ts` と同じLCG、seed 1〜30。各候補でseedを初期化する。
- 難易度: `easy / mid / hard`。
- AI接触入力: `y = [-42, -12.001, 0, 14, 22, 24, 52, 105]`、`z = [30, 100, 178]`、`x = [-30, 0, 30]`。
- bounce: `lastBounceZ = [30, 70]`、player X `[-104, 0, 104]`。
- ball基準: `vx=0`、`vy=-100`、`vz=400`、`side=0`、`spin`は `y < 14 ? -0.5 : 0.5`。
- 経路: `OpponentAi.decideShot()` → `solveShot()` → `simLand()` → `solveContactPlane()` → `predictAt()` → `projectWorldPoint()`。
- 採用候補: player側tableへnetなしで着地し、predictionが非null、`abs(predicted.x) <= PADDLE_LIMIT`。

前提コードでは採用候補30,362件、全7 shot、全3難易度を含む。件数・種類が変わった場合はAI/物理への意図しない差分として調査する。

#### viewportと判定

```text
568x320
667x375
760x360
844x390
900x412
```

各候補・viewport・pointer種別について、最大tiltの `squash = 0.85` を使う。

```text
centerMin = 0.35 * height
centerMax = min(0.90 * height, height - paddleBottomExtent(radius))
dy = projectedYから[centerMin, centerMax]までの距離
reachableRy = visualRy * 0.85 * assistScale + ballRadius
margin = reachableRy - dy
```

- fine `1.20`、touch `1.40` の双方で到達不能0件。
- 全marginが1.0px以上。
- 568×320を最小marginケースとして含む。

### 10.5 guide unit / E2E

- player側の実bounce前は非表示、bounce確定後だけ表示する。
- `predictAt()` null、net、table外、player shot、point、resetで非表示・状態破棄。
- viewport resize後もworld座標から再投影し、予測world点は変えない。
- `remaining` の0.35 / 0.10 / 0秒境界でalphaを検査する。alpha計算は純粋helperへ分離してよい。
- `?debugInput=1` で予測X/Y/残り時間が有限、guide破棄後に属性が無い。

- touch 450ms後、fine 320ms後はreleaseだけではcontactしない。厳密な1ms境界はunitが責任を持つ。
- active upward / downward、assist外miss、depth外miss、1 flight 1 contactを回帰する。
- Desktop Chromium、Android相当Chromium、iPhone相当WebKitで実行する。
- 短時間の瞬間 `data-strike-active` は既存方針どおりunitとChromiumが担当し、WebKitは最終接触・reset結果を担当する。

## 12. エラー・中断・部分失敗

- 非有限strike / pose / guide predictionはzero metricsまたはguideなしへfail closedし、前回active・前回guideを延命しない。
- pointerType不明ではassistもrelease contactも無効にする。
- guide計算失敗はゲームを停止せず、ガイドだけ非表示にする。consoleへ座標や入力履歴を出さない。
- direct shot solverが非有限の場合は既存warnと失敗表示を維持し、自動補正・再乱数化しない。
- suspension / cancel / pagehideは全input期限を破棄して復帰時の自動contactを防ぐ。guideはball flightとともに保持し、表示条件外では描画しない。
- build/test runnerの起動失敗とtest assertion failを別に記録する。

## 13. リスクと対策

| リスク | 予防 | 検出 | 回復 |
|---|---|---|---|
| contact猶予延長で古い技が残る | snapshot ageをrelease後も加算し160msでfalse | 160/161msと200〜300ms passive E2E | strike定数とsnapshot評価だけをrevert |
| contact後に無入力で再武装する | `beginContact()` は期限を延長しない | deadline不変unit、1 flight E2E | contact phase変更だけをrevert |
| poseが角度境界で大回転する | 最短角度差 | ±π unit、G2 | neutral targetへ安全fallback |
| assistで空振りが消える | floorは成立済みcontactだけ。hitbox式は別 | assist直後・depth外miss | assist/floorを旧値へ戻す |
| quality floorでゲームが易しくなりすぎる | solver不変、q=0.40と既存high/lowを同時校正 | 固定seed統計、G2 1試合 | floorのみ0.40未満へ変更せず設計再検討 |
| Y拡大でHUDやhandleと重なる | min 0.35、bottom clamp維持、5 viewport | reach test、568×320 G2 | Y minを旧0.45へrevert |
| guideが誤軌道・stale表示になる | 実bounce後一回計算、flight lifecycleで破棄 | state unit、debug属性削除E2E | guideだけ無効化 |
| guide予測がframe負荷を増やす | per-flight一回、renderは投影だけ | call count unit、stability E2E | guideだけ無効化 |
| 自動試験を操作感合格と誤認する | G1/G2を分離 | 実装ログの未実施表示 | iPhone実機まで本番完了にしない |

## 14. 採用しない案

| 案 | 採用しない理由 |
|---|---|
| ラケットをball / guideへ自動吸着 | 手動X/Yと実衝突、明確な空振りを失う |
| `RELEASE_GRACE_SEC = 0.35` だけへ変更 | frozen active snapshotとcontact後再延長を同時に伸ばす |
| visual hold専用の同値期限を追加 | v0.2.3では表示保持とcontact保持が同じ要件で、重複状態になる |
| quality floorをsolver内で全shotへ適用 | AI、legacy、独立solver入力まで変わり、assist成立時だけという境界を失う |
| assist端だけを複雑な分岐でfloor | 初版の条件と検証軸を増やす。成立済みcontact全体へ単純適用してraw成分を保持する |
| Y minを0または0.33へ広げる | 0.35で固定母集団0 unreachable・1px余裕を満たし、追加変更の根拠がない |
| guideを毎frame再シミュレーション | 軌道はflight中に決定済みで、負荷と揺れだけを増やす |
| 難易度別assist profile | AI難易度と操作補助の再設計、UI・保存・試験軸が必要で本修正を超える |
| `direct-paddle-v2`併存 | 同じ経路を二重保守する。既存legacy queryとcode rollbackで回復可能 |

## 15. ロールアウト・ロールバック

### 15.1 ローカル実装

- Phase 10-1〜10-4を分割し、各gate成功後だけ次へ進む。
- G1後に版数・cache・README・正本・索引・実装ログを同期する。
- G2未了なら状態を明記し、本番完了としない。

### 15.2 即時回避

- `?controlModel=legacy` を非保存の緊急回避として維持する。
- guideは描画状態だけであり、問題時はguide生成・描画を無効化してdirect衝突を維持できる。

### 15.3 code rollback

重大な操作不能時はv0.2.2へ戻し、次の単位でrevertできる構成を保つ。

1. guide状態・描画・debug。
2. Y min、assist、quality floor。
3. contact grace / snapshot age。
4. passive / active姿勢。

公開rollback時もroot + child合成artifact、Actions、deployment SHA、HTTP/PWA、Chromeを再確認する。
