## 1. 目的・背景

### 1.1 目的

1. pointer event 間でも最大16msだけ入力方向を予測し、ラケット中心が指・マウスの操作開始後、次の描画frameから追従する状態を作る。
2. ラケット中心の描画位置と衝突位置を同じ `interaction pose` に統一し、「見えている位置」と「当たる位置」の中心差をなくす。
3. ボールへ合わせるための移動を、返球のコース・技・回転として誤解釈しない。
4. 568×320のタッチ環境でも、見える補助輪郭内へボールを合わせれば接触候補になる範囲を確保する。
5. 現行7技、静止ブロック、実衝突、低品質ミス、既存物理を残し、ゲームを自動返球へ戻さず操作負荷だけを下げる。

### 1.2 ユーザー判断

| 区分 | 決定 |
|---|---|
| 解決対象 | ラケット操作が煩雑でゲーム難易度を過度に上げている状態と、実操作へ追従して見えない状態を修正する |
| 文書境界 | 今回は設計書のみを作成し、コード、テスト、実装ログ、公開物を変更しない |
| 工程 | 設計レビューは実施せず、本書確定後の次工程を実装Phaseとする |
| 品質優先 | 特殊技の入力自由度より、ラケット中心の追従、通常返球の分かりやすさ、見た目と判定の一致を優先する |

### 1.3 現行コードから確認した原因

| 現状 | 根拠 | 問題 |
|---|---|---|
| `InputController.ingest()` は pointer event 発生時だけ `onInput` を呼ぶ | `src/input.ts` | event 間でlogical centerが更新されず、低頻度入力では位置が段階的に止まる |
| 先行設計は最新sampleから最大16msの外挿を要求するが、`PaddleController`は外挿していない | `src/control/paddle.ts` の `applyInput()` / `stepFixed()` | v0.2.0設計の低遅延契約が未実装 |
| centerをlogicalからrenderへ8〜20msで補間し、半径25%の差を許す | `PaddleController.updateVisual()` | 指に追従していても描画が遅れて見える。衝突はlogical、描画はrenderで中心が一致しない |
| `Game.updatePlayerInput()` が `player.tx` をrender poseから取得する | `src/game.ts` | 入力直後の互換world Xへ描画遅れが混入する |
| Pointer時刻は `PointerEvent.timeStamp`、phase期限は一部 `simulationTime` で比較する | `src/input.ts` / `src/game.ts` / `src/control/paddle.ts` | ページ表示から試合開始までの時間やpause時間により、follow・metrics失効の時間軸がずれ得る |
| 同じ150ms履歴が位置追従と `ShotIntent` の両方を決める | `src/control/stroke.ts` / `src/control/shot-intent.ts` | ボールへ合わせる上下左右移動が、DRIVE/CHOP/aim/side spinへ流入する |
| `aimX = 0.72 * directionX - 0.28 * contactOffsetX` | `src/control/shot-intent.ts` | 横へ球を追うほど返球方向も同じ側へ大きく変わる |
| touch offsetは画面高10%、接触補助は見た目の1.08倍 | `src/config.ts` / `src/control/contact.ts` | 320px高で指と中心が32pxずれ、奥行きによって表示blade半径が約16〜23pxになるため、指先より小さい対象へ合わせる操作になる |
| 既存pose/contactテストは単発座標・単発衝突・回復が中心 | `tests/paddle-pose.test.ts` / `tests/paddle-contact.test.ts` | 33msのevent間隔、描画中心差、時計領域、位置合わせとintentの分離を検出できない |

## 4. 採用アーキテクチャ

### 4.1 入力経路の分離

```text
PointerEvent / coalesced events
  -> PointerSample[]
  -> tracking metrics ───────────────┐
  -> latest sample                   │
                                     v
requestAnimationFrame clock -> PaddleController.advanceFrame()
  -> interaction pose（中心位置の唯一の正本）
  -> player.x / tx
  -> Renderer center
  -> sweptPaddleContact center

contact時
  PointerSample[]
    -> deriveStrikeMetrics(last 80ms)
    -> buildShotIntent(contact, strike metrics)
    -> solveDirectPlayerShot()（既存）
```

位置追従と打球意図は同じ `PointerSample[]` を入力にしてよいが、同じ集計結果を共有してはならない。tracking metricsは予測・角度にだけ使い、strike metricsだけがpassive/active、power、lift、技、spinを決める。

### 4.2 時間所有権

| 用途 | clock | 禁止 |
|---|---|---|
| Pointer sample、予測age、metrics age、release grace、phase期限 | `PointerEvent.timeStamp / 1000` と `requestAnimationFrame(timestamp) / 1000` のmonotonic wall clock | `Game.simulationTime`との比較 |
| ball、AI、point timer、fixed physics | `Game.simulationTime` | Pointer snapshot期限への利用 |
| UIの実時間timer | 既存 `window.setTimeout` | fixed-step時間への置換 |

`InputController.eventTime()` は次の順で時刻を正規化する。

1. `event.timeStamp / 1000` と `performance.now() / 1000` が有限か確認する。
2. event値が正で、現在値との差が5秒以内ならevent値を採用する。
3. それ以外は `performance.now() / 1000` を採用する。
4. 履歴末尾以下の時刻はmetrics履歴へ追加しないが、最新画面位置は更新する。

`Game.loop(timestamp)` はfixed stepを進める前に、同じ `timestamp / 1000` を `PaddleController.advanceFrame()`へ渡す。`stepFixed()`へwall clockを渡して期限判定させない。

`Game` はこの値を `currentInputTime` として保持し、そのframe内の `PaddleContactInput.time`、`ContactEvent.time`、`isContactEligible()`、`beginContact()` へ同じ値を渡す。これらの `time` はv0.2.1からwall clock秒を意味する。`simulationTime` はball / AI / point timerにだけ渡し、contact・phase・strikeの期限判定には渡さない。1frame内でfixed stepが複数回走っても `currentInputTime` は変えない。

### 4.3 所有状態

`PaddleController` は次をprivateで所有する。

- 最新の有効 `PointerSample`。
- 0.15秒、最大32件のsample履歴。
- tracking metrics。
- pointer種別。
- pointer down状態。
- release時に凍結したstrike snapshotと失効時刻。
- interaction pose。
- 前fixed stepのinteraction pose。
- angle / tiltの目標値。
- interaction poseに含まれる平滑化済みangle / tilt / contact flash。
- phaseとrelease grace期限。

独立したrender poseを持たない。`advanceFrame(frameTime, frameDelta, ...)` はcenterを確定した後、angle / tiltを1frameに1回だけ平滑化してinteraction poseへ格納する。既存 `getRenderPose()` を維持する場合もinteraction poseのcopyをそのまま返す。Renderer、assist outline、contact detectorはcenterだけでなく平滑化済みangle / tiltも同じinteraction poseから取得する。

## 6. ラケット追従仕様

### 6.1 sampleから基準中心への変換

```text
baseX = clamp(stageX * width, bladeRadius, width - bladeRadius)

offsetRatio = pointerType == touch ? 0.06 : 0.01
rawY = stageY * height - offsetRatio * height
baseY = clampPaddleScreenY(
  clamp(rawY, 0.45 * height, 0.90 * height),
  height,
  radius
)
```

- `stageX / stageY` はCanvas `DOMRect`から算出する。
- X/Y clampとworld X逆投影は先行設計の共有投影を維持する。
- 568×320のtouch offsetは19.2px、844×390では23.4pxになる。
- pointer種別はgesture開始時に固定し、同一pointerIdの途中で変えない。

### 6.2 最大16msの外挿

pointer down中だけ、各描画frameで次を計算する。

```text
age = max(0, frameTime - latestSample.time)
predictionTime = min(age, 0.016)

rawDx = trackingMetrics.vx * height * predictionTime
rawDy = trackingMetrics.vy * height * predictionTime
maxPrediction = 0.05 * height

rawDistance = hypot(rawDx, rawDy)
predictionScale = rawDistance > maxPrediction
  ? maxPrediction / rawDistance
  : 1
dx = rawDx * predictionScale
dy = rawDy * predictionScale

interactionX = clampPaddleX(baseX + dx)
interactionY = clampPaddleY(baseY + dy)
```

- `age > 0.016`でも16ms分を越えて進めず、次sampleまでその位置で保持する。
- 非有限metrics、履歴2件未満、pointer downでない場合は `dx = dy = 0`。
- pointerup時は最後に確定したinteraction centerを固定し、release grace中に追加移動しない。
- recoverはrelease grace失効後にだけ開始する。
- pause、hidden、viewport block、pagehide、pointercancelでは予測とgraceを即時解除する。

### 6.3 描画中心と衝突中心

- Rendererはinteraction poseの `screenX / screenY` をそのまま使う。
- contact detectorは同じframeで確定したinteraction poseを使う。
- centerの指数補間と「半径25%までの中心差」契約を廃止する。
- angle / tiltは `advanceFrame()` 内で既存の `tau = lerp(0.020, 0.008, speedRatio)` により1回だけ補間し、interaction poseへ確定する。別のrender angle / tiltを作らない。
- blade本体、通常assist outline、debug ellipse、contact detectorは同じ平滑化済みangle / tiltを使う。
- `speed < 0.15`が連続した場合、angle / tiltは0.12秒以内に待機値へ戻す。
- `Game.updatePlayerInput()` とfixed step後の `player.x / tx` はinteraction poseのworld Xを使い、render値を参照しない。

### 6.4 fixed stepとの順序

1. `Game.loop(timestamp)` がframe時刻とviewportを取得する。
2. `PaddleController.advanceFrame(frameTime, frameDelta, ...)` がcenterと平滑化済みangle / tiltを含むinteraction poseを1回確定する。
3. そのframeのfixed stepを0〜12回実行する。
4. 最初のfixed stepは「前回fixed pose → 最新interaction pose」のsegmentを使う。
5. 同一frameの2回目以降は「最新pose → 最新pose」を使う。
6. fixed stepが0回なら前回fixed poseを消費せず、次回stepで最新poseまでを1本のsegmentとして評価する。
7. Rendererは同じ最新interaction centerを描く。

Pointer callback中にballへ接触させない。contact成立は従来どおりfixed physics内だけで行う。

## 7. phase・release仕様

| 現在 | event / 条件 | 次 | center | contact |
|---|---|---|---|---|
| idle / recover | valid pointerdown | tracking | sampleへ即時移動 | 可 |
| tracking | active strike成立 | armed | 追従 | 可 |
| armed | active strike失効かつpointer down | tracking | 追従 | 可（passive） |
| tracking / armed | contact成立 | contact | contact位置 | 同flight不可 |
| contact | 次frame | follow | contact位置で固定 | 同flight不可 |
| tracking / armed | pointerup | follow | 最終位置で固定 | 0.16秒以内のみ可 |
| follow | grace失効 | recover | 待機位置へ移動 | 不可 |
| recover | 待機位置到達 | idle | 待機位置 | 不可 |
| 任意 | cancel / suspension / quit | recover | 予測なし | 不可 |

- pointer down中に入力が0.15秒止まった場合もcontactはpassive blockとして可能にする。tracking metricsとstrike metricsは0へ戻す。
- pointerup後のstrike snapshotはgraceと同時に失効する。期限後に古いフリックを打球へ使わない。
- contact済みflightはgrace中でも再contactさせない。
- recover速度は既存 `385 px/s` を維持する。

## 8. 接触補助仕様

### 8.1 pointer種別別の楕円

```text
assistScale = pointerType == touch ? 1.30 : 1.15

visualRx = radius * PADDLE_BLADE_SCALE
visualRy = visualRx * 0.94 * squash

assistVisualRx = visualRx * assistScale
assistVisualRy = visualRy * assistScale

collisionRx = assistVisualRx + projectedBallRadius
collisionRy = assistVisualRy + projectedBallRadius
```

- pointer種別が未確定のidle/recoverはcontact不可であり、scaleのfallbackを使わない。
- world Z depth gate、relative sweep、中間角度、非有限値の扱いは先行設計を維持する。
- blade本体を1.30倍へ拡大しない。補助範囲だけを輪郭表示する。

### 8.2 可視補助輪郭

- rally中、ballがplayer側へ進行し、`ball.bounces >= 1`、paddleがcontact eligibleのときだけ表示する。
- 中心、平滑化済みangle、tiltから得るsquashはblade本体・衝突楕円と同じinteraction poseの値を使う。
- 半径は `assistVisualRx / assistVisualRy` とし、ball半径は輪郭へ加えない。
- fillなし、既存debug軌跡と区別できる白系、alpha `0.22`、line width `max(1.5px, radius * 0.08)` とする。
- pointerup後はrelease grace中だけ表示し、contactまたはgrace失効で消す。
- `?debugInput=1` ではvisual blade楕円とcollision楕円を別色で追加表示してよいが、通常表示の補助輪郭と寸法を変えない。

### 8.3 接触位置と品質

最短接触点はassist楕円で正規化する。

```text
qAssist =
  (contactX / assistVisualRx)^2 +
  (contactY / assistVisualRy)^2

screenQuality = clamp(1 - sqrt(qAssist), 0, 1)
timingQuality = clamp(1 - depthDistance / depthTolerance, 0, 1)
contactQuality = clamp(0.70 * screenQuality + 0.30 * timingQuality, 0, 1)

contactOffsetX = clamp(contactX / assistVisualRx, -1, 1)
contactOffsetY = clamp(contactY / assistVisualRy, -1, 1)
```

- 補助輪郭の中心ほど高品質、輪郭端ほど低品質とする。
- collision半径はball半径を加えるため、ball外周だけが輪郭へ触れた接触は `screenQuality = 0`になり得る。
- contactQualityの下限を設けず、低品質ミスを残す。
- 接触補助拡大後は既存固定seed校正を再実行し、低品質と高品質の差を消していないことを確認する。

## 9. 打球意図の分離

### 9.1 `StrikeMetrics`

`src/types.ts` に返球専用の内部型を追加する。

```ts
interface StrikeMetrics {
  vx: number;
  vy: number;
  speed: number;
  displacement: number;
  directionX: number;
  directionY: number;
  verticality: number;
  curvature: number;
  age: number;
  active: boolean;
}
```

`ContactEvent.paddleMetrics` は `ContactEvent.strikeMetrics` へ置き換える。tracking用 `StrokeMetrics` を `buildShotIntent()` へ渡せない型契約にする。これは内部型だけの変更で、保存schemaや外部APIには影響しない。

### 9.2 strike解析窓

接触時刻を `tContact` とし、`tContact - 0.08` 以降のsampleだけを使う。

- 2sample未満はzero metrics。
- 速度・方向・変位・曲率の単位と符号は既存 `computeStrokeMetrics()` と同じ。
- pointer down中は接触時に再計算する。
- pointerup後はrelease時点で計算したsnapshotを使い、`RELEASE_GRACE_SEC`後に破棄する。
- `age`はwall clockで計算する。
- 非有限結果はmetrics全体をzeroへ戻し、前回active値を延命しない。

```text
verticality = speed > 0 ? abs(vy) / speed : 0

active =
  speed >= 1.10
  && displacement >= 0.04
  && verticality >= 0.55
  && age <= 0.16
```

horizontal-onlyの追従は速度が高くても `active = false` とする。activeではない接触はすべてpassive PUSHになる。

### 9.3 `ShotIntent` への変換

```text
passive = !strikeMetrics.active

power = passive
  ? 0.12
  : clamp((speed - 1.10) / (3.60 - 1.10), 0, 1)

lift = passive ? 0 : clamp(-directionY, -1, 1)

aimX = clamp(-0.65 * contactOffsetX, -0.65, 0.65)

topSpin = passive
  ? 0
  : clamp(lift * (0.35 + 0.65 * power), -1, 1)

sideSpin =
  passive || abs(curvature) < 0.30
    ? 0
    : clamp(curvature * (0.30 + 0.70 * power), -1, 1)
```

- `directionX` をaimへ使わない。
- contactOffsetはassist楕円基準とし、中心接触は `aimX = 0`。
- 曲線操作は残すがactive strikeのときだけ横回転へ反映する。通常返球に曲線操作を要求しない。
- depthの既存式、top/side spin clamp、incoming carryを維持する。

### 9.4 技分類

技の種類と表示名は維持し、active認定後だけ次表を評価する。

| 条件（上から評価） | `classifiedShot` |
|---|---|
| passive | `PUSH` |
| shortかつ `lift <= -0.42` | `STOP` |
| shortかつ `lift >= 0.42` | `FLICK` |
| shortのその他 | `PUSH` |
| `lift >= 0.42` かつ `ballY < LOB_MAX_Y` | `LOB` |
| `lift >= 0.42` かつ `speed >= 2.90` かつ `ballY > SMASH_MIN_Y` | `SMASH` |
| `lift >= 0.42` | `DRIVE` |
| `lift <= -0.42` | `CHOP` |
| その他 | `PUSH` |

`STRIKE_MIN_VERTICALITY = 0.55`により通常のactive入力では `abs(lift) >= 0.55` となるが、表の±0.42境界は既存分類互換と防御的入力のため維持する。

## 14. テスト設計

### 14.1 clock・prediction

`tests/paddle-pose.test.ts`を中心に次を固定する。

1. sample時刻 `t` とframe時刻 `t + 0 / 0.008 / 0.016 / 0.017 / 0.033`。
2. 16msを越えて予測距離が増えない。
3. 速度が大きくても予測距離はCanvas高5%を越えない。

5. touch offsetは高さの6%、mouse / penは1%。

| renderのtauだけ短くする | event間でlogical centerが止まる問題、clock混在、intent干渉を解消しない |
| ラケットをballへ自動吸着する | 実衝突と空振りの意味を失い、ゲームが旧auto-returnへ戻る |
| touchだけblade本体を1.30倍描画する | ラケット外観と奥行き表現を大きく変える。補助輪郭の方が判定範囲を明示できる |
| directionXを小係数でaimへ残す | 位置合わせとコース指定の干渉が係数依存で残る |
| 曲線操作を完全削除する | 既存横回転機能を不必要に失う。active-only・高いしきい値で任意操作にできる |
| 簡単／上級モードと設定保存を追加する | UI、保存schema、移行、テスト軸を増やし、今回の追従修正を複雑化する |
| `direct-paddle-v2`を追加してv1を併存する | 同じ実衝突経路の二重保守が必要になる。既存legacy queryとcode rollbackで回復可能 |
| fixed physicsを60Hzへ下げる | 衝突精度を落とし、追従遅れの原因を解消しない |

## 18. ロールアウト・ロールバック

### 18.1 ローカル実装

- Phase 8-1〜8-4では版数を上げず、負のコントロールと実装を小さく進める。
- Phase 8-5のG1成立時にpackage / lock / child cacheをv0.2.1へ同期する。
- G2の自動化不能項目は未実施と記録できるが、ユーザーが「操作が改善した」と確認するまで操作感の完全受入とはしない。
- 実装開始時だけ `docs/実装ログ.md` にPhase 8を追加する。本書作成だけではPhaseを開始しない。

### 18.2 即時回避

- URLへ `?controlModel=legacy` を付けると既存X位置指定・接触面返球を利用できる。
- queryは保存せず、通常URLへ戻せばdirectへ戻る。
- 保存データ、PWA identity、戦績は両経路で共有し、migrationを行わない。

### 18.3 code rollback

- 対象commitを `git revert`し、reset / force pushを使わない。
- package / lock / child cacheをv0.2.0へ揃える。
- root workerのchild bypass、manifest identity、IndexedDBを戻さない。
- 公開rollback時もroot+child検査、Actions、deployment SHA、HTTP/PWA、Chromeを再確認する。
