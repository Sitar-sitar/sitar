## 1. 目的・背景

### 1.1 ユーザー要望

「ゲームのシステムは既存を踏襲しつつ、グラフィック面を大幅強化したい。より遊びやすくなるよう挙動を見直し、ゲームとしての完成度も上げたい。」

### 1.2 現状の弱点（`cf89521` のコードと `design-qa/` のスクリーンショットから確定）

**グラフィック**

| ID | 現状 | 根拠 |
|---|---|---|
| G-1 | 体育館の壁・床・柵は平坦なグラデーションと直線だけで奥行き感と光の表現がない | `render.ts` `drawScene()` |
| G-2 | 卓球台は単色グラデーション。天板の反射、床への影、脚の立体感がない | `drawTable()` |
| G-3 | ネットは 24 本の縦線と半透明矩形だけ。球がネットの後ろにあっても常にネットの上に描かれる | `drawTable()` が `drawNet()` を球より先に呼ぶ |
| G-4 | 相手は頭・胴・棒状の手足の記号的な人形で、構え・体の向き・フォロースルーがない | `drawOpponent()` |
| G-5 | ボールの軌跡は 9 個の円の残像で、速度感・回転の向きを伝えない | `drawBall()` の `trail` 描画 |
| G-6 | 打球・バウンド・ネット・得点に視覚エフェクトがなく、音と振動だけに依存している | `feedback.ts` のみ |
| G-7 | 背景・台を毎フレーム全描画しており、描画コストが演出追加の余地を圧迫する | `render()` の呼び順 |
| G-8 | カメラ背後の柵 `drawFence(-560)` を毎フレーム無駄に描く | `drawScene()` 末尾 |

**遊びやすさ・完成度**

| ID | 現状 | 影響 |
|---|---|---|
| P-1 | 得点理由（`ネット` / `アウト` / `返せず` / `サーブフォルト` / `自陣に落下`）だけが中央に出て、**誰の得点か**は色（緑 / 赤）でしか分からない | 初見で失点理由を理解しにくい。色覚多様性に配慮がない |
| P-2 | 打球名 `#flash` が stage 中央 34% に 26px で出るため、飛んでいる球と重なる（`design-qa/implementation-rally-wide-844x390-v2.jpg`） | 迎球の視認を妨げる |
| P-3 | 得点が決まると球が即時に消える | 「どこに落ちたか」を確認できず、ミスの理由が体感に残らない |
| P-4 | サーブ時に選んだ長さ（短い / 中 / 長い）がどこへ落ちるかの手がかりがない | 長さ選択の意味が伝わらず、選択が形骸化する |
| P-5 | 接触品質（`contactQuality`）はデバッグ表示以外に出ない | 「なぜ返球が弱かったか」を学べない |
| P-6 | デュース・マッチポイントの表示がない | 試合の山場が伝わらない |
| P-7 | スコア変化に動きがなく、得点しても HUD が反応しない | 手応えが薄い |
| P-8 | 相手サーブ待ちの 700ms（`AI_SERVE_DELAY_MS`）に相手の構えが見えず、球が突然現れる | 相手サーブの開始を予期しにくい |
| P-9 | 入射球の回転（上回転 / 下回転）を見分ける手段がない | 押し出し・ツッツキの選択根拠を得られない |
| P-10 | `prefers-reduced-motion` を参照していない | 動きに敏感な利用者への配慮がない |

### 1.3 目的

1. 描画を「体育館の一台」から「照明の当たる試合会場」へ引き上げ、台・ネット・球・ラケット・相手の質感と立体感を大幅に高める。
2. 打球・バウンド・ネット・得点の瞬間を視覚エフェクトで返し、音・振動と合わせて手応えを作る。
3. 得点者と理由、サーブの着地帯、接触品質、回転、デュース / マッチポイントを**読める**ようにし、遊びやすさを上げる。
4. 上記をすべて view 層で実現し、物理・AI・接触判定・乱数消費・ルール・保存・PWA・HUD 寸法契約を一切変えない。
5. 静的レイヤのキャッシュで描画コストを下げ、エフェクト追加後も現行以下のフレーム時間に収める。

### 3.3 状態遷移で設計が依存してはならない点（設計レビューで確定）

| 事実 | 設計上の帰結 |
|---|---|

## 4. 全体方針

### 4.1 view 層だけを変える二層構造

1. **描画基盤層** — 静的レイヤのキャッシュ、描画モジュール分割、視覚イベントの受け口、エフェクトの純粋モデル。物理・AI からは `RenderScene` に載る**読み取り専用の値**と、Renderer 専用の drain API で受け取る**イベント列**だけを使う。
2. **表現層** — 会場・台・球・ラケット・相手の作画、エフェクト、HUD 演出、サーブ着地帯。基盤層の上で差し替え可能にする。

### 4.2 カメラは動かさない

`projectWorldPoint()` は pointer → world の逆写像（`unprojectScreenXAtZ()`）と衝突判定に共有されている。カメラ揺れ・ズーム・傾きは「見た目と当たり判定のずれ」を作る。**したがってラリー中・得点時を含め、カメラ行列はいかなる演出でも変更しない。** 迫力は球・ラケット・エフェクト・HUD 側で作る。

### 4.3 手続き描画のみで実現し、外部資産を追加しない

- 画像・フォント・音声ファイルを追加すると、`sw.js` の `APP_SHELL`、`scripts/check-dist.mjs`、合成 Pages 検査、cache 版数契約（Obsidian 注意点 18 / 22）へ同時に手を入れる必要が生じ、初回表示・オフライン・容量にも影響する。
- 会場の観客・照明・木目・網目はすべて Canvas API で手続き的に描く。乱数を使う模様は**インデックス由来の決定論的な値**（例: `Math.sin(index × 12.9898)` の小数部）で作り、乱数生成器を使わない。

### 4.4 エフェクトはイベント駆動、乱数は分離

- 打球・バウンド・ネット・サーブ・得点は `Game` が `VisualEvent` として 1 回だけ発行し、`Renderer` が次フレームで消費する。**`Feedback`（音・振動）を呼ぶ地点と 1 対 1 に対応させる**ので、演出の抜け漏れは音との照合で検出できる。
- エフェクトの乱数は `Renderer` が自前で持つ `mulberry32` を使い、`Game` の `random` には**触れない**。乱数消費回数・順序（v0.2.4 §5.4）は不変（§5.13）。

### 4.5 見た目と判定を一致させたまま「読める」情報を足す

- 補助輪郭・迎球ガイドの寸法と生成条件は変えない。
- 追加する情報（サーブ着地帯、回転の色、接触品質ラベル、得点者、状況チップ）は**既に決まっている状態の可視化**であり、判定や自動補正を伴わない。着地帯は fallback を含む製品挙動を保証しない**目安**として提示し、実際に打たれた長さは既存のサーブ名トーストで示す。

### 4.6 モーション軽減・停止中の挙動・性能予算を最初から含める

- `prefers-reduced-motion: reduce` では装飾的な動き（粒子・集中線・揺れ・パルス・待機の揺らぎ）を止め、情報的な表示（死球・着地帯・バナー・ラベル）は残す。
- 停止中（一時停止・非表示・viewport gate）は、情報表示の残り時間を保持し、装飾アニメーションを静止させる。時計は §5.1.4 の 2 系統に限定する。
- 静的レイヤ化で減った描画時間を上限として、エフェクト追加後のフレーム時間が現行を超えないことを、**同一の外部計測 harness** を v0.2.4 と v0.3.0 の両方へ適用して確認する（§5.11.2 / §9.5）。

### 4.7 採用しなかった代替案

| 代替案 | 却下理由 |
|---|---|
| WebGL / Three.js への移行 | 依存追加・バンドル増・PWA cache 契約の変更・3 環境 E2E の再構築が必要で、YAGNI に反する。Canvas 2D で目標の表現に届く |
| スプライト画像（相手・観客・台）の導入 | §4.3。資産契約と容量を動かし、解像度依存のにじみも生じる |
| 得点時のカメラ揺れ | §4.2。判定との共有投影を壊す。`point` phase 限定でも input → paddle 追従の視覚位置がずれる |
| `POINT_INTERVAL` を 1.25s → 1.6s へ延長して得点演出の時間を確保する | 既存 timing / E2E 契約と体感テンポを変える。演出は 1.25s 内に収める（§12-2 で確定） |
| 相手を実写的な人体で描く | 描画コストと作画量が過大。スタイライズした「選手」に留める |
| 照明ハローを毎フレーム脈動させる | 静的レイヤ L0 に置く照明と矛盾する。性能を優先し、照明は完全静的にする（設計レビュー P1-01） |

| 基準版 `cf89521` に計測 dataset を後付けして読む | 基準版に存在しない観測点であり実行不能（設計レビュー P0-02）。Playwright の外部 harness で両版を同じ測定器で測る |

#### 5.1.3 視覚イベント `VisualEvent`

`src/types.ts` に追加する。

```ts
export type VisualEvent =
  | { kind: "contact"; side: Side; x: number; y: number; z: number;
      shot: ShotId; passive: boolean; contactQuality: number | null; time: number }
  | { kind: "bounce"; x: number; z: number; time: number }
  | { kind: "net"; x: number; y: number; time: number }
  | { kind: "serve"; side: Side; serveType: ServeType; serveLength: ServeLength; time: number }
  | { kind: "point"; winner: Side; reason: string; scP: number; scA: number;
      ball: { x: number; y: number; z: number }; time: number };
```

- `Game` は `visualEvents: VisualEvent[]` を持ち、`pushBounded(buffer, event, VISUAL_EVENT_BUFFER)` で追加する（上限 16、超過時は最古を捨てる）。
- **`getRenderScene()` は非破壊のまま**とし、`RenderScene` にイベントを載せない。`Game.drainVisualEvents(): VisualEvent[]` を新設し、蓄積分を返して空にする。呼び出し元は `Renderer` だけ（`Renderer` のコンストラクタに `drainEvents` コールバックを渡す）。
- `time` は発行時の `simulationTime`。座標の規則：

| kind | 座標 |
|---|---|
| `contact` | **接触時点の実際の球位置** `ball.x / ball.y / ball.z`（solver へ渡す `from.y`（`SHOT_ORIGIN_Y_MIN` で下限クランプ）ではない） |
| `bounce` | バウンド判定時の `ball.x / ball.z` |
| `net` | `updatePhysics()` が既に計算している**補間済みのネット面交点** `x / y`（`ball.z = 0` へ書き換える前の値） |
| `point` | 得点判定時の `ball.x / ball.y / ball.z`（`ball.y < FLOOR` の場合もそのまま渡し、静止面の決定は Renderer が行う。§5.4.4） |

- 発行地点と consumer：

| 発行地点（`game.ts`） | kind | 併走する `Feedback` | consumer |
|---|---|---|---|
| `makeShot()`（AI と legacy プレイヤー） | `contact`（`contactQuality: null`、`passive: false`） | `hit()` | Renderer：スパーク、SMASH 集中線 |
| `directPlayerContact()` 成功時 | `contact`（`contactQuality: contact.contactQuality`、`passive: intent.passive`） | `hit()` | Renderer：同上 |
| `doServe()` 成功時 | `serve` | **`hit(0.35)`（現行どおり）** | Renderer：死球 effect と残存エフェクトの消去（新しいポイントの開始） |
| `updatePhysics()` の台上バウンド | `bounce` | `bounce()` | Renderer：バウンドリング |
| `updatePhysics()` のネット | `net` | `net()` | Renderer：ネット揺れ |
| `point()` | `point` | `win()` / `lose()` | Renderer：死球 effect の生成。DOM 側（バナー・パルス）は `Ui` が `point()` から直接受ける |

未使用のイベントはない。

#### 5.1.4 時計と停止中の契約

| 系統 | 時計 | 対象 | 停止中（一時停止・非表示・viewport gate）の挙動 |
|---|---|---|---|
| **A: シミュレーション時計** | `scene.simulationTime`（固定ステップで進む） | 粒子・リング・ネット揺れ・集中線・死球の寿命、相手の構えの戻し、**相手の待機揺らぎ、スマッシュグローの脈動**（`sin(simulationTime × …)`） | 進まない。装飾も静止する |
| **B: 情報表示の残り時間** | `Game.loop()` が渡す `frameDelta`。ただし **`isSuspended()` のときは 0 を渡す** | `#flash` トースト、`#pointBanner`。`#situation` の切替は状態依存で時計なし | 残り時間を保持する（v0.1.0 の「停止中もトーストが減衰する」挙動を置き換える） |
| 例外 | `performance.now()` | 球の回転線の回転角（現行どおり・変更しない） | 現行どおり回り続ける（`ball.live` 中しか描かれない） |

- score / rally のパルスは CSS アニメーション（420ms）で表現し、`Ui` は `pulse` クラスの付与と `setTimeout` による除去を行う。停止中は `body[data-suspended="true"] .pulse { animation-play-state: paused; }` で静止させる。`Game.setSuspensionReason()` の結果を `Ui.setSuspended(boolean)` で `body.dataset.suspended` に反映する（真のときだけ属性を置き、偽では削除）。
- `Renderer` は前フレームの `simulationTime` との差 `dt` を `stepEffects()` に渡す。`dt ≤ 0`（停止中）なら状態を進めない。`dt > EFFECT_DT_MAX_SEC (0.25)`（復帰直後）なら 0.25 に丸める。
- 1 フレームに複数の固定ステップ分のイベントが届く場合、`spawnFromEvent()` は `age = max(0, scene.simulationTime − event.time)` を初期経過時間として effect に与え、`age ≥ ttl` のイベントは生成しない。

#### 5.4.2 回転の色分け（P-9）

#### 5.4.3 軌跡

- `trail`（`TRAIL_LENGTH = 9`、物理側の push は不変）を**連続した帯**として描く。隣接 2 点を投影し、帯の幅を `radius × lerp(0.30, 1.00, progress)`、alpha を `lerp(0.05, 0.35, progress)` とする（`progress = (index+1)/length`）。
- 帯は各区間を 4 点の四角形で塗る。1 フレームあたり最大 8 区間。
- 影は現行どおり直下面に楕円。

#### 5.4.4 死球の残留（P-3。Renderer 管理の effect）

死球は `phase` / `pointTimer` に**依存しない**。`point` イベントを受けた `Renderer` が、次の `DeadBall` effect を 1 個だけ保持する（既存があれば置き換える）。

```ts
interface DeadBall { x: number; y: number; z: number; startedAt: number; }
```

- 位置：`x, z` はイベントの `ball`。`y` は**直下の面**：`onTable(x, z)` なら `0`、それ以外は `FLOOR`（イベントの `y` が `FLOOR` 未満でも `FLOOR` に置く）。ネットで止まった球は `z = 0` のまま天板上。
- 寿命：`DEAD_BALL_HOLD_SEC = 0.50` 保持 → `DEAD_BALL_FADE_SEC = 0.75` で線形に消える（合計 1.25s = `POINT_INTERVAL` と同じだが、`POINT_INTERVAL` を参照しない）。`deadBallAlpha(age) = age < 0.5 ? 1 : clamp(1 − (age − 0.5) / 0.75, 0, 1)`。`age = simulationTime − startedAt`。
- 消去：寿命到達、または `serve` イベント（次のポイント開始）、または `ball.live` が真になったとき。`phase === "over"` でも同じ寿命で表示・消滅する（`over` 中も `tick()` は走り `simulationTime` は進む。§3.3）。
- 停止中は `simulationTime` が進まないため保持される（§5.1.4 系統 A）。
- 表示：球本体を alpha 付きで描く。軌跡・回転線は描かない。影は直下面に alpha 付きで描く。描画順は `ballBehindNet(z)` に従う（§5.1.2）。
- `over` 遷移後にリザルトオーバーレイが被っても effect は寿命で必ず消え、次の `newGame()` → `startServe()` → `doServe()` の `serve` イベントでも消える。
- `?debugInput=1` のとき `body.dataset.deadBall` を `"1"`（表示中）/ `"0"` に更新する（E-V6 の観測点）。

#### 5.4.5 スマッシュ可能時の強調

`scene.smashable` が真のとき、球の周囲に `rgba(255,194,75,.35)` → 透明の放射グロー（半径 `2.2 × radius`）を描き、6Hz（**`simulationTime` 基準**、§5.1.4）で alpha を `0.25〜0.35` に脈動させる。reduced-motion では alpha 0.30 で静止。現行のラケット周りの二重輪は**線幅を 2.5 → 1.5、5 → 3 に細める**だけで残す。

| サーブ待ちの構え | `phase === "serve" && server === "A" && !ball.live` のとき、**非利き手（x − 10）**の `FLOOR+40` に球（半径 `BALL_R × 3.1 × s`、通常色）を描き、腕をそこへ向ける。球は演出であり `ball` 状態は変えない |

### 5.7 エフェクト

純粋モデルは `src/view/effects.ts`。単位は world cm、時間は秒。乱数は `random: () => number` を引数で受ける。

#### 5.7.1 接触スパーク

| 項目 | 値 |
|---|---|
| 発生 | `contact` イベント |
| 個数 | passive PUSH 6 / それ以外 10 / SMASH 16（`CONTACT_SPARK_COUNT`） |
| 初速 | `[120, 260]` cm/s（一様乱数）、方向は接触点を中心に画面平面内で一様角度、z 方向は 0 |
| 重力 | `EFFECT_GRAVITY = 600` cm/s² |
| 寿命 | `CONTACT_SPARK_TTL_SEC = 0.28` |
| 大きさ | `1.2 + random × 1.0` cm、alpha `1 → 0` 線形 |
| 色 | プレイヤー `#ffe075`、相手 `#dbe5ec`、SMASH は `#ffc24b` |
| 上限 | 全粒子 `EFFECT_MAX_PARTICLES = 48`。超過時は最古を捨てる |

#### 5.7.2 バウンドリング

`bounce` イベントで `(x, 0.5, z)` に楕円リングを 1 個生成。半径 `4 → 18` cm、alpha `0.55 → 0`、寿命 `BOUNCE_RING_TTL_SEC = 0.32`。縦横比は現行 `mark` と同じ 0.42。既存の着地予測 `mark` は変更しない（予測と実バウンドの両方が見える）。

#### 5.7.3 ネット揺れ

`net` イベントで開始。網の各縦線の x に `netWobbleOffset(t, x) = NET_WOBBLE_AMP × (1 − |x| / NET_HW) × exp(−t / NET_WOBBLE_DECAY_SEC) × sin(2π × NET_WOBBLE_HZ × t)` を加える。`NET_WOBBLE_AMP = 1.5` cm、`NET_WOBBLE_HZ = 14`、`NET_WOBBLE_DECAY_SEC = 0.12`、持続 `NET_WOBBLE_SEC = 0.36`。テープ・支柱・台上影は揺らさない。網全体に同じ位相を与え、イベントの交点 x は使わない（`x` は減衰の重みにだけ使う）。

#### 5.7.4 スマッシュ集中線

`contact` かつ `shot === "SMASH"` のとき、球の投影点から放射状に 12 本の直線を画面座標で描く。長さ `18〜40px`（インデックス由来の決定論値）、alpha `0.5 → 0`、持続 `SMASH_STREAK_SEC = 0.18`。線は球より外側 `radius × 1.6` から始め、球を隠さない。

#### 5.7.5 得点

`point` イベントの Canvas 側 consumer は死球（§5.4.4）だけである。バナーとパルスは `Ui` が担う（§5.8.2 / §5.8.4）。

```ts
// types.ts
export type MatchSituation = "deuce" | "match-point-P" | "match-point-A" | null;

// rules.ts
export function matchSituation(scP: number, scA: number): MatchSituation {
  if (isGameOver(scP, scA)) return null;
  if (scP >= 10 && scA >= 10 && scP === scA) return "deuce";
  if (isGameOver(scP + 1, scA)) return "match-point-P";
  if (isGameOver(scP, scA + 1)) return "match-point-A";
  return null;
}
```

#### 5.8.4 得点バッジのパルスとラリー節目（P-7。エッジ検出）

`tick()` はラリー中に 240Hz で `updateHud()` を呼ぶため、**すべてエッジ検出**にする（設計レビュー P1-07 / P2-06）。

- 純粋関数 `hudPulseEvents(prev, next)`（`src/view/hud-text.ts`）：

```ts
interface HudSnapshot { scP: number; scA: number; rally: number; }
type HudPulse = "score-P" | "score-A" | "rally";
export function hudPulseEvents(prev: HudSnapshot, next: HudSnapshot): HudPulse[];
```

  - `next.scP > prev.scP` → `score-P`。`next.scA > prev.scA` → `score-A`。減少・同値では出さない。
  - `next.rally !== prev.rally && next.rally > 0 && next.rally % RALLY_PULSE_EVERY === 0` → `rally`（`RALLY_PULSE_EVERY = 5`）。
- `Ui` は前回スナップショット `hudPrev` を持ち、`updateHud()` ごとに `hudPulseEvents(hudPrev, state)` を評価してから `hudPrev` を更新する。

- パルス：対象要素に `pulse` クラスを付け、`SCORE_PULSE_MS = 420` 後に外す。付与時に既に付いていれば一度外して再付与する（`requestAnimationFrame` を挟む）。CSS：`transform: scale(1 → 1.08 → 1)`、`box-shadow` に `0 0 18px rgba(255,194,75,.45)` を加えるキーフレーム。**レイアウト寸法は変えない**（transform のみ）。
- reduced-motion ではパルスを付けない。停止中は §5.1.4 のとおり静止する。

### 5.9 サーブ着地帯（P-4。目安表示）

#### 5.9.1 表示と属性

- 条件：`phase === "serve" && server === "P" && !ball.live && !paused`。
- 相手コート（`z > 0`）上に、`x ∈ [-HW, HW]`、`z ∈ SERVE_ZONE_Z[selectedServeLength]` の帯を描く。塗り `rgba(126,224,168,.10)`、縁 `rgba(126,224,168,.35)` 幅 1.5。
- 帯は**目安**である。`findServeSolution()` は解が得られない入力で aim → 0、length → `middle` へ fallback し得るため、表示した長さと実際のサーブ長が一致しないことがある。実際に打たれた長さは既存のサーブ名トースト（`〇〇サーブ（長さ）`）と `body.dataset.servedServeLength` が示す。README にも「目安」と明記する。
- `body.dataset.serveZone` は**上記の表示条件が真のときだけ** `selectedServeLength` を置き、偽のときは `delete document.body.dataset.serveZone` する（設計レビュー P1-08）。`Ui.updateHud()` と `Ui.updateServeControls()` の両方から同じ判定関数で更新する。
- 長さ切替（`selectServeLength()`）で即時に追従する。

#### 5.9.2 帯の確定（実入力 envelope で測定）

`SERVE_ZONE_Z: Record<ServeLength, readonly [number, number]>` を `config.ts` に置く。値は次の測定スクリプトの出力を転記し、単体テスト U-V8 で一致を固定する。

- スクリプト：`scripts/measure-serve-zones.mjs`（新規）。製品の `findServeSolution()` と同じ手順（`solveServe()` → aim 0 → `middle` fallback）をスクリプト内で再現し、プレイヤーサーブの**実入力 envelope** を総当たりする。

| 軸 | 値 |
|---|---|
| `player.x` | `-104 〜 104` を 8 刻み（27 点）。`ball.x = player.x × 0.5`、`from = { x: ball.x, y: SERVE_CONTACT_Y, z: PZ + 6 }` |
| `flick.vx` | `{ -7.2, -3.6, -2.4, -1.2, -0.6, 0, 0.6, 1.2, 2.4, 3.6, 7.2 }`（`MAX_GESTURE_SPEED = 3.6`。`speed` は `MAX_GESTURE_SPEED × 2 = 7.2` で飽和するため `vx` の絶対値上限も 7.2）。`aim = player.x × 0.6 + vx × 40` |
| 球種 | 9 種 |
| 長さ | 3 種（要求長さ） |
| `direction` | `+1` |
| 誤差 | 基準弾道は誤差なし。誤差適用後の着地は `elev / azim / speed` に `doServe()` と同じ式（`error = 0.014`（タップ、`vx = 0`）と `0.012`（フリック、`vx ≠ 0`））、乱数 mulberry32 seed `20260906` を**セル（player.x × vx × 球種 × 長さ）ごとに再初期化**して 1 標本 |

- 記録する量（長さごと）：母集団件数、要求長さのまま解けた件数と率、aim → 0 fallback 件数、length → `middle` fallback 件数、要求長さで解けた基準弾道の `z2` の最小・最大、誤差適用後 `z2` の帯包含率。
- 帯 = 要求長さで解けた基準弾道の `[min(z2) − SERVE_ZONE_PAD, max(z2) + SERVE_ZONE_PAD] ∩ [4, HL − 3]`、`SERVE_ZONE_PAD = 6`。
- **受入条件**（U-V8。満たさない場合の扱いも固定する）：
  1. 現実的 envelope（`|vx| ≤ 3.6`）で、要求長さのまま解ける率が各長さ **95% 以上**。未達なら帯を「目安」として表示したうえで、実装ログに率を記録し、UI 文言は変えない（fallback は製品挙動であり本書は変更しない）。
  2. 誤差適用後 `z2` の帯包含率が各長さ **95% 以上**。未達なら `SERVE_ZONE_PAD` を 6 → 10 へ 1 段だけ広げて再測定し、それでも未達なら帯を塗りなしの**境界線 2 本**へ切り替える。
  3. 帯の中央値が `short < middle < long`。`short` の上端 < `long` の下端。
  4. 帯が `[4, HL − 3]` 内。

## 11. リスクと割り切り

| リスク | 対応 |
|---|---|
| 作画刷新の過程で判定共有の式（中心・半径・角度）を誤って触る | `actors.ts` への移設は「式は移設のみ、塗りだけ変更」と明記（§5.5）。既存 `paddle-pose` / `paddle-contact` / `reachable-contact` テストが変更なしで通ることを G1 に含める |
| 演出が球の視認を妨げる | トーストは上部、バナーは 18%、集中線は球の外側から、粒子は 0.28s。ラリー中の球の経路（天板投影 26〜75%）に恒常表示を置かない |
| 最終得点で死球・バナーが見えない | 死球は `point` イベント駆動の Renderer effect で `phase` に依存しない（§5.4.4）。バナーは最終得点 0.95s でリザルトと重ならない（§5.8.2）。E-V6 で固定 |
| 静的レイヤが resize / DPR 変化で古いまま残る、または再生成が多発する | `layerKey` で再生成。U-V15 で spy による再生成回数を固定。シナリオ C で単発コストを記録 |
| `OffscreenCanvas` 非対応ブラウザ | `document.createElement("canvas")` へフォールバック。API は共通部分のみ使用 |
| エフェクトで描画時間が増え、低性能端末で 60fps を割る | 静的レイヤ化で先に予算を空け、粒子 48 / 線 12 の上限。同一 harness の前後計測を G1 に含め、超過時は上限を段階的に下げる（§5.11.2） |
| 一時停止からの復帰で溜まった `dt` によりエフェクトが飛ぶ | `dt` を 0.25s に丸める。`simulationTime` は停止中に進まないため通常は 0 |
| 停止中に DOM 演出だけが進み、Canvas と食い違う | トースト・バナーは停止中 `tickFlash(0)` で保持、パルスは `data-suspended` で静止、待機揺らぎ・脈動は `simulationTime` 基準（§5.1.4）。E-V7 で固定 |
| `#flash` の位置変更で既存 E2E が壊れる | id と API と文言を維持し、位置とスタイルだけ変える。E2E は文言のみ検査している |
| 状況チップとトーストの重なり | `body[data-situation]` でトーストを下げる CSS を用意し、null では属性を削除（§5.8.3） |
| 着地帯が実サーブ長と一致しない（fallback） | 帯は「目安」と明記し、実際の長さは既存トーストと `data-served-serve-length` が示す。envelope 全体で成功率・包含率を測定し、未達時の処置を固定（§5.9.2） |
| 240Hz の `updateHud()` でパルスが連打される | `hudPulseEvents()` のエッジ検出と `showGame()` での基準初期化（§5.8.4）。U-V14 / E-V8 |
| `getRenderScene()` を別 consumer が呼びイベントが消える | イベントは `drainVisualEvents()` 専用（N-6）。`RenderScene` に載せない |
| 相手の「構え」が判定に影響すると誤解される | 描画のみ。`OpponentAi.state` は読み取りだけで、`lean` は Renderer 内部の状態に置く |
| 色覚多様性への配慮不足 | 得点者・品質・状況は**文字**で示し、色は補助。回転色は暖色 / 寒色に加えて回転線の向きでも区別できる |
| E-V6 が長時間で CI を圧迫する | Desktop Chromium のみ、`test.setTimeout(120_000)`。安定性反復に含めるが 3 環境へは広げない |

ロールバック方針: 描画起因の重大な不具合時は v0.2.4 コミット `cf895219cd4e2bb4e0695cf34872cd99cb917ebd` へ戻す。操作系は本書で変更しないため `?controlModel=legacy` は従来どおり使える。
