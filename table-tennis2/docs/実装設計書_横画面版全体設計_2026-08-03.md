## 1. 目的・背景

現行 `table-tennis` は縦画面を含むスマートフォンとPCへ単一UIで対応している。一方、今後は横長の視野、左右の操作領域、補助パネルなど、横画面固有の機能を継続追加する予定である。

新アプリでは次を両立する。

1. 現行 v0.6.2 のゲームルール、物理、AI、操作、戦績、PWA安定性を初期基準として踏襲する。
2. 既存アプリのURL、コード、保存データ、公開を壊さない。
3. 横画面レイアウトと将来機能を、ゲーム物理へ波及させず追加できる境界を最初に用意する。
4. 動的プラグイン基盤や新しいフレームワークは導入せず、TypeScriptの明示的なモジュール登録で保守性を保つ。

## 4. 継承する仕様と非破壊条件

### 4.1 ゲーム仕様

初期版は以下を v0.6.2 と同じ意味で持つ。数値、乱数消費順、物理式を横画面化の都合で変更しない。

- 1人用、プレイヤー対AI
- 難易度 `easy` / `mid` / `hard`
- 11点先取、2点差が付くまで継続、通常2本・デュース後1本ごとのサーブ交代
- サーブ9種類: 横上左、上回転、横上右、横左、ナックル、横右、横下左、下回転、横下右
- サーブ長3種類: `short` / `middle` / `long`
- 打球7種類: `DRIVE` / `SMASH` / `PUSH` / `CHOP` / `LOB` / `STOP` / `FLICK`
- ネット、台上バウンド、サーブフォルト、自陣落下、アウト、返球失敗の判定
- STOP/FLICKの `touch` 必要速度モデル、`SHORT_BOUNCE_Z = 48`
- AIサーブ乱数順、AI短球乱数順、非対象5技の物理ベクトル
- ラケットの持ち手、打点奥行き表現、横位置を物理判定平面へ一致させる契約
- 160msのフリック有効時間
- 1/240秒固定刻み、50msフレーム差分上限、最大12 step

現行の数値正本は、基準commitの `table-tennis/src/config.ts`、`types.ts`、`rules.ts`、`physics.ts`、`ai.ts` とする。本書へ全数値を複製せず、実装開始時に同一内容をコピーし、回帰テストで差分を検出する。

### 4.2 プレイヤー・戦績仕様

- 初回起動時に `ゲスト` を作成する。
- プレイヤーの追加、選択、改名、削除を行える。
- 最後の1人は削除できない。
- プレイヤー削除時は同じプレイヤーの戦績を同一transactionで連鎖削除する。
- 決着した試合だけを記録する。
- 通算試合、勝敗、勝率、最高ラリー、難易度別、直近10試合を表示する。
- データは端末内だけに保存し、外部送信しない。
- 不正レコードは黙って補正・削除せず、値をログへ出さずに戦績機能だけを停止する。
- IndexedDB未対応、open失敗、schema不正、versionchangeでもゲーム本体は遊べる。

新規版のDBは同じversion 1・同じstore/record shapeから開始するが、DB名を `table-tennis2` として現行データから隔離する。

### 4.3 PWA・配布仕様

- バックエンド不要の静的PWAとする。
- 全アセット参照は相対URLとする。
- `dist/assets/app.js` と `dist/assets/app.css` は固定名とする。
- manifest、Service Worker、`.nojekyll`、iconsを `dist/` へ含める。
- Service Workerは現在版cache instanceだけを参照する。
- install中にアプリシェル取得が失敗した場合、不完全な新版をactivateしない。
- 制御済みページはオフライン再読み込みできる。
- CIは速度より再現性を優先し、worker 1・retry 0の反復検査をリリース前に行う。

### 5.3 拡張スロットとFeatureModule

横画面シェルは次の固定スロットを持つ。

| slot | 初期用途 | 将来用途の例 |
|---|---|---|
| `left-rail` | 試合情報・補助操作 | 戦術表示、球種履歴、練習メニュー |
| `stage` | CanvasとHUD | カメラ切替、軌道補助 |
| `right-rail` | サーブ選択・設定 | 横画面専用ショット選択、詳細操作 |
| `hud-secondary` | 補助情報 | 回転量、速度、目標表示 |
| `overlay` | タイトル、戦績、結果、案内 | チュートリアル、設定詳細 |

将来機能の最小契約は次とする。

```ts
type FeatureSlot =
  | "left-rail"
  | "right-rail"
  | "hud-secondary"
  | "overlay";

interface FeatureModule {
  readonly id: string;
  readonly slot: FeatureSlot;
  mount(host: HTMLElement, services: FeatureServices): () => void;
}

interface FeatureServices {
  getGameSnapshot(): Readonly<GameState>;
  subscribe(listener: (state: Readonly<GameState>) => void): () => void;
  readonly commands: {
    selectServe(type: ServeType): void;
    selectServeLength(length: ServeLength): void;
  };
}
```

- `FeatureServices` は読み取り専用の状態取得、限定されたcommand、UI通知だけを公開する。
- featureは `Game.state` を直接変更せず、DOMを自分の `host` 外へ追加しない。
- `mount()` は解除関数を返し、listenerやtimerを確実に破棄する。
- feature一覧は `main.ts` で静的に列挙する。実行時ダウンロード、文字列による自動探索、第三者コード実行は行わない。
- 初期版では `serve-panel` をこの契約で実装し、抽象化が実利用されることを確認する。
- feature間通信のための汎用イベントバスは作らない。必要なcommand/queryを `FeatureServices` へ小さく追加する。

### 6.2 Viewport状態

`view/layout.ts` の純粋関数はCSS pixel単位のvisual viewport `width` / `height` から、次の状態を返す。値は `visualViewport` があればその寸法、なければdocument elementのclient寸法を使う。safe areaはCSSの `env(safe-area-inset-*)` でシェル内側へ確保し、Canvasと入力はその結果の実寸を参照するため、JavaScriptで同じinsetを二重減算しない。

| 状態 | 条件 | 挙動 |
|---|---|---|
| `portrait-blocked` | `width <= height` | 回転案内を最前面表示し、入力とゲーム進行を停止 |
| `too-small` | 横向きだが利用可能領域が `568×320` 未満 | 小さすぎる旨を表示し、入力とゲーム進行を停止 |
| `compact-landscape` | 横向き、`568×320` 以上、幅760未満 | stage + right rail。left railはボタンで開くdrawer |
| `wide-landscape` | 横向き、幅760以上 | left rail + stage + right railを常時表示 |

- 判定はUser-Agentではなくviewport寸法を使う。
- `window.resize`、`visualViewport.resize`、利用可能なら `screen.orientation.change` を監視し、同一animation frame内の重複更新を1回へまとめる。
- `env(safe-area-inset-*)` をシェル、drawer、操作ボタンへ反映する。
- manifestの `orientation: "landscape"` は希望値であり、未対応ブラウザでも上記ゲートで安全に動く。
- `screen.orientation.lock("landscape")` はユーザー操作後かつAPI利用可能時だけbest-effortで試せるが、失敗をエラー扱いせず、必須経路にしない。

ブラウザ差の根拠は [MDN: Web app manifest `orientation`](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/orientation) と [MDN: `ScreenOrientation.lock()`](https://developer.mozilla.org/en-US/docs/Web/API/ScreenOrientation/lock) を参照する。manifestの向き指定と実行時lockはいずれも対応差があるため、本設計はviewport gateを唯一の必須制御とする。

### 6.3 停止理由の合成

現行の単一 `paused` だけでは、ユーザー一時停止中に回転やタブ非表示が重なった場合の再開判断が曖昧になる。新規版は次を独立保持する。

```ts
interface SuspensionState {
  userPaused: boolean;
  documentHidden: boolean;
  viewportBlocked: boolean;
}
```

`isSuspended` は3値のORで決める。

- いずれかがtrueになった時点で、ポインター状態をresetし、AIサーブtimerを取消し、固定step更新を止める。
- 回転で `viewportBlocked` がfalseへ戻っても、`userPaused` または `documentHidden` がtrueなら再開しない。
- 全理由がfalseへ戻ったときだけ、`lastFrame` とaccumulatorをresetして再開する。
- AIサーブ待ちで再開した場合は、generationを更新した新しいtimerを1本だけ登録する。
- portrait/too-small中はCanvas上のpointer eventを処理しない。
- タイトル・結果画面でも回転案内を優先表示するが、永続データやゲーム状態は変更しない。

### 6.4 横画面シェル

- `#appShell` を画面全体のgridとし、Canvasは `stage` セルの実寸を使用する。
- `compact-landscape` は `stage + right-rail` の2列、`wide-landscape` は `left-rail + stage + right-rail` の3列とする。
- scoreboardと主要HUDはstage上部へ置き、Canvasの打球領域を覆わない。
- サーブ9種類×長さ3種類はright rail内へ配置し、全ボタンの最小タップ領域を `44×44 CSS px` とする。
- タイトル画面は横2カラムとし、左にプレイヤー・戦績、右に難易度・開始・操作説明を置く。高さ不足時は各カラム内をスクロール可能にし、画面全体の意図しないスクロールは許可しない。
- プレイヤー、戦績、結果、設定は `overlay` に表示し、フォーカスをoverlay内へ移す。閉じたら起点へ戻す。
- drawer/overlayはEscapeキーでも閉じられるが、キーボードゲーム操作は本スコープ外とする。
- Canvas描画のカメラ値はstageのaspect ratioから `LayoutMetrics` が返す。coreの物理座標は変更しない。

### 6.5 入力座標

現行入力はviewportの高さでフリック速度を正規化し、ポインターXをrenderer viewportへ渡す。新規版では左右railを除いたstageを基準にする。

- `InputController` は `canvas.getBoundingClientRect()` またはrendererの `StageViewport` を取得する。
- ラケット位置と狙いは `clientX - rect.left` を `rect.width` へ正規化する。
- フリック速度は `rect.height` で正規化し、現行のしきい値と160ms契約を維持する。
- stage外で開始したgestureはゲーム入力にしない。
- gesture開始後にviewportが変わった場合はpointer captureを解除してresetする。
- 1本のprimary pointerだけを扱い、`pointercancel`、向き変更、pagehideで必ずresetする。

### 6.6 描画

- `Renderer` はCanvasのclientサイズとDPRから内部bufferを更新する。
- coarse pointerのDPR上限2、その他3という現行安定性方針を維持する。
- camera計算は `computeCamera(stageViewport)` の純粋関数へ抽出する。

- resize後の次frameでCanvasとinputが同じstage寸法を参照する。

### 6.8 PWA identityとService Worker

`manifest.webmanifest` は次を満たす。

- `id: "./"`
- `start_url: "./"`
- `scope: "./"`
- `display: "standalone"`
- `orientation: "landscape"`

- `short_name: "卓球 横"`

### 6.9 同一GitHub Pagesでの別URL共存

GitHub Pagesへの1回のdeployはサイト全体を置き換えるため、片方の `dist/` だけをdeployしない。公開時のartifactは次の合成構造とする。

```text
_site/
├── index.html                 # table-tennis/dist/index.html
├── assets/ ...               # table-tennis/dist/*
├── sw.js                     # table-tennis のroot Service Worker
├── manifest.webmanifest
├── .nojekyll
└── table-tennis2/
    ├── index.html             # table-tennis2/dist/index.html
    ├── assets/ ...
    ├── sw.js                  # table-tennis2専用scope
    ├── manifest.webmanifest
    └── icons/ ...
```

- `master` の `table-tennis/**`、`table-tennis2/**`、合成workflow変更をtriggerにする。
- deploy時は両アプリで `npm ci` と `npm run check` を行い、両方がgreenの場合だけ `_site/` を作る。
- 現行ルートのファイルはルートへ、新規版は `table-tennis2/` へコピーする。
- 同じPages環境へ複数workflowが別artifactをdeployする構成は採らない。
- PR検証はアプリ別workflowでよいが、公開workflowは両アプリを再検証する。
- 公開操作はユーザーの明示承認後だけ行う。

現行root Service Workerはscopeが `/sitar/` であり、現状のnavigation fallbackは未知のサブパスへ現行版 `index.html` を返し得る。初回公開前に、`/sitar/table-tennis2/` をroot workerの `respondWith` 対象外とする現行版側の修正が必要である。これはリリース済み `table-tennis` の変更なので、本書へ混在させず、別の修正設計書・回帰テスト・版数更新で確定する。完了するまでG2/G3へ進まない。

## 11. 代替案と不採用理由

### 11.1 現行table-tennisをそのまま横画面対応する

既存URL・UI・回帰基準へ横画面固有機能の影響が及ぶ。別アプリ・別URLというユーザー決定に反するため不採用。

### 11.2 最初から共通game-coreパッケージを作る

既存公開版のimport、workflow、releaseまで同時変更し、初期リスクが大きい。新規版が実際に分岐してから共有価値を測る方が単純なため不採用。

### 11.3 Reactやゲームエンジンへ移行する

現在のCanvas/TypeScriptで要件を満たせる。依存、bundle、移行、回帰範囲を増やすため不採用。

### 11.4 orientation lockだけで横画面を保証する

manifest orientationとScreen Orientation APIはブラウザ・表示モード差がある。未対応時に縦画面でゲームが進むため不採用。viewport gateを正本とする。

### 11.5 新規版専用workflowからtable-tennis2/distだけをPages deployする

同じPagesサイトの既存ルートを消すため不採用。単一合成artifactを使う。

### 11.6 汎用プラグインローダーを作る

個人開発の静的アプリに動的発見、権限、互換層は不要。静的なFeatureModule登録で将来拡張に必要な境界だけを持つ。
