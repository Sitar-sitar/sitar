## 1. 目的・背景

### 1.1 目的

- ラケット中心をポインターの X/Y へ低遅延で追従させ、接触前からストローク方向を見た目で理解できるようにする。
- ボールとラケットが画面上で実際に重なり、かつ奥行き条件を満たした場合だけ返球する。
- ストロークの速度、方向、曲率、接触位置、接触品質を、打球速度、着地点、縦回転、横回転、誤差へ連続的に反映する。
- 静止ラケットによる弱いブロックと、能動ストロークによるドライブ、スマッシュ、ツッツキ、ロブ、ストップ、フリックを同じ入力系で扱う。
- 現行の固定 240 Hz 物理、弾道ソルバー、9球種×3長さサーブ、AI、戦績、横画面HUD、PWAを壊さず段階導入する。

### 1.2 背景

現行 `src/input.ts` は Canvas 上のポインター X だけを `onPosition()`へ渡し、直近約 0.11 秒の X/Y サンプルから `Flick` を作る。`src/game.ts` の `playerContact()` は、ボールが `player.z` を横切ったときに world X 差と ball Y 範囲だけで返球を決める。`src/render.ts` のラケット Y と角度は、接触後に確定した `swingType` の定型アニメーションであり、入力軌跡とは一致しない。

このため現行方式には、次の構造的なずれがある。

- 指を上下へ動かしても、ラケット中心は直接上下しない。
- 画面上でボールとラケットが離れていても、world 条件だけで返球できる場合がある。
- 接触前のラケット姿勢から、ストローク方向や球種を予測できない。
- 横方向の曲線操作を `ball.side` へ反映できない。
- `solveShot()` が incoming `spin` / `side` を固定の打球値で上書きする。

## 6. 採用アーキテクチャ

### 6.1 全体経路

```text
InputController
  -> PointerSample[]
  -> computeStrokeMetrics()
  -> PaddleController.updateInput()
  -> logicalPose / renderPose / phase

Game fixed step
  -> project ball segment with shared projection
  -> sweptPaddleContact(ball segment, paddle segment, depth gate)
  -> buildShotIntent(contact, metrics, incoming ball)
  -> solveDirectPlayerShot(intent)
  -> existing BallState / AI planning / score flow

Renderer
  -> RenderScene.directPlayerPose
  -> same pose basis used by contact detector
```

### 6.2 モジュール責務

| ファイル | 責務 |
|---|---|
| `src/control/stroke.ts` | sample整列・除去、速度、方向、加速度、変位、曲率、snapshot |
| `src/control/paddle.ts` | pointerから姿勢への変換、phase、予測、描画平滑化、reset / recover |
| `src/control/contact.ts` | ball/paddle segment の純粋なスイープ楕円判定、品質算出 |
| `src/control/shot-intent.ts` | passive判定、技分類、power / aim / depth / spin intent |
| `src/view/projection.ts` | Rendererから抽出するworld→screen投影と、指定Z面のscreenX→worldX逆変換 |
| `src/physics.ts` | 既存ソルバーを維持し、player専用 `solveDirectPlayerShot()` を追加 |
| `src/input.ts` | Pointer Event、coalesced events、primary pointer、callback、serve adapter |
| `src/game.ts` | control model選択、所有権、fixed-step接触、flight lock、shot適用 |
| `src/render.ts` | direct poseによるラケット描画、接触flash、debug overlay |

`game.ts`、`input.ts`、`physics.ts`へ全ロジックを集約しない。純粋計算を上記4 control moduleへ分け、DOMを使わない単体テストを可能にする。

### 6.3 制御モデル

```ts
type ControlModel = "legacy" | "direct-paddle-v1";
```

- v0.2.0 の既定値は `direct-paddle-v1`。
- URL query `?controlModel=legacy` のときだけ legacy 経路を使う。
- `?controlModel=direct-paddle-v1` は明示比較用として受け付ける。
- 未知値、空値、複数値は既定の `direct-paddle-v1`へフォールバックする。
- query は session中の読取専用であり、URLを書き換えず、IndexedDB / localStorageへ保存しない。
- 通常UIへ切替ボタンを追加しない。

## 7. 型・状態契約

### 7.1 追加型

```ts
interface PointerSample {
  clientX: number;
  clientY: number;
  stageX: number;
  stageY: number;
  time: number;
  pointerType: "touch" | "mouse" | "pen";
}

interface StrokeMetrics {
  vx: number;
  vy: number;
  speed: number;
  acceleration: number;
  directionX: number;
  directionY: number;
  pathLength: number;
  displacement: number;
  curvature: number;
  age: number;
}

type PaddlePhase =
  | "idle"
  | "tracking"
  | "armed"
  | "contact"
  | "follow"
  | "recover";

interface PaddlePose {
  screenX: number;
  screenY: number;
  worldX: number;
  worldZ: number;
  velocityX: number;
  velocityY: number;
  angle: number;
  tilt: number;
  pointerDown: boolean;
  phase: PaddlePhase;
}

interface ContactEvent {
  screenX: number;
  screenY: number;
  contactOffsetX: number;
  contactOffsetY: number;
  screenQuality: number;
  timingQuality: number;
  contactQuality: number;
  ballHeight: number;
  ballVelocityBefore: BallVector;
  paddleMetrics: StrokeMetrics;
  time: number;
}

interface ShotIntent {
  power: number;
  aimX: number;
  depth: number;
  lift: number;
  topSpin: number;
  sideSpin: number;
  contactQuality: number;
  timingQuality: number;
  strokeCurvature: number;
  classifiedShot: ShotId;
  passive: boolean;
  isServe: false;
}
```

`PointerSample.time` は秒、X/Y速度は Canvas 高さ/秒で正規化する。`stageX` / `stageY` と `ShotIntent` の各正規化値は、特記がない限り `[0, 1]` または `[-1, 1]` へ clamp済みである。

### 7.2 既存型の扱い

- `PaddleState.x / tx / z / viewZ / swing / swingType` は legacy と AI のため削除しない。
- direct mode の姿勢は `Game` が所有し、`RenderScene.directPlayerPose: PaddlePose | null` として描画へ渡す。
- `PaddleState.x` は direct mode でも world X の互換値として更新し、AIの狙い・既存状態参照を壊さない。
- contact済み管理は `BallState`へ永続的なIDを追加せず、`Game` private の `flightId` と `lastPlayerContactFlightId` で行う。

## 8. 入力データ仕様

### 8.1 sample取得

- `pointerdown` で履歴を初期化し、最初の sample を追加する。
- `pointermove` は `event.getCoalescedEvents()` が空でなければ全件を時刻順に処理し、元 event が末尾sampleに含まれない場合だけ元 event も追加する。
- sample時刻は各 event の `timeStamp / 1000` を使う。coalesced sampleへ同一の `performance.now()` を割り当てない。
- 非有限時刻、直前以下の時刻、直前と座標・時刻が同一のsampleは解析履歴へ追加しない。最新ポインター位置自体は元 event から更新する。
- `pointerup`、`pointercancel`、pause、viewport block、pagehide、document hidden、試合終了では active pointer、sample、snapshot、phase、contact eligibility を解除する。
- `setPointerCapture()` 失敗は現行どおり致命的にしない。

### 8.2 定数

| 定数 | 値 | 用途 |
|---|---:|---|
| `STROKE_HISTORY_SEC` | `0.15` | ストローク解析窓 |
| `CONTACT_WEIGHT_SEC` | `0.10` | 接触直前へ曲率・速度の重みを置く窓 |
| `STROKE_SNAPSHOT_TTL_SEC` | `0.10` | pointerup後にfollow接触を許す期限 |
| `MAX_POINTER_SAMPLES` | `32` | 履歴上限 |
| `GESTURE_MIN_SPEED` | `0.55` | armed / 能動打球の最低速度 |
| `SMASH_GESTURE_SPEED` | `2.90` | smash分類の最低速度 |
| `MAX_GESTURE_SPEED` | `3.60` | power正規化上限 |
| `CURVE_MIN_SEGMENT` | `0.008` | Canvas高さ比。未満の区間を曲率から除外 |
| `CURVE_MIN_DISPLACEMENT` | `0.03` | Canvas高さ比。未満は曲率0 |
| `CURVE_SPIN_THRESHOLD` | `0.20` | 横回転を有意と扱う絶対曲率 |

### 8.3 速度・方向・加速度

解析窓の先頭と末尾だけで速度を決めず、接触直前100ms内の有効区間を時間重み付き平均する。

```text
segmentVx = deltaClientX / deltaTime / canvasHeight
segmentVy = deltaClientY / deltaTime / canvasHeight
vx, vy    = 有効区間の時間重み付き平均
speed     = hypot(vx, vy)
direction = speed > 0 ? (vx / speed, vy / speed) : (0, 0)
accel     = (latestSegmentSpeed - oldestSegmentSpeed) / elapsed
```

- `deltaTime <= 0` の区間は除外する。
- `canvasHeight` は sample batch 取得時の Canvas `DOMRect.height` を使い、1未満なら1とする。
- 非有限結果は0へ丸めず、そのmetrics全体を invalid として直前の有効metricsを最大1 frameだけ維持する。次frameもinvalidなら0へ戻す。

### 8.4 曲率

1. 隣接する有効区間の単位方向ベクトル間で `atan2(cross, dot)` を求める。
2. `CONTACT_WEIGHT_SEC` 内ほど大きい線形重みを掛ける。
3. 符号付き角度合計を `Math.PI` で割り、`[-1, 1]`へ clampする。
4. 総変位が `CURVE_MIN_DISPLACEMENT` 未満なら0とする。

画面座標で時計回りを正、反時計回りを負とする。符号は tests で固定し、実装途中に見た目都合で反転しない。

### 8.5 serve互換

- player serve中も同じ sample を取得するが、direct contact detectorは無効にする。
- `tryPlayerServe()`へは `StrokeMetrics` から `{ vx, vy, sp, t }` を作る legacy adapter を渡す。
- 既存の tap serve、左右フリックの aim 補正、9球種×3長さ、サーブ誤差を変更しない。
- serve成功後の履歴は通常の時間窓で失効させ、返球時へ持ち越さない。

## 9. ラケット姿勢・状態遷移

### 9.1 pointerからscreen姿勢への変換

```text
stageX = clamp((clientX - rect.left) / rect.width, 0, 1)
stageY = clamp((clientY - rect.top) / rect.height, 0, 1)

touchOffset = 0.10 * rect.height
mouseOrPenOffset = 0.01 * rect.height

screenX = clientX - rect.left
screenY = clientY - rect.top - offset
```

- `screenY` は `[0.45 * height, 0.90 * height]`へ clampした後、既存 `clampPaddleScreenY()` で持ち手を画面内へ収める。
- `screenX` は描画時のブレード外周が Canvas 内へ残るよう、現在の描画半径で clampする。
- touchは10%、mouse / penは1%の上方offsetを使う。v0.2.0では端末別設定を追加しない。

### 9.2 world X / Z

- world Z は現行 `solveContactPlane(ball, "P")` の結果を使い、ユーザー入力から変更しない。
- Renderer内の投影式を `src/view/projection.ts` の純粋関数へ抽出し、Rendererとcontact detectorで共有する。
- `worldX` は `screenX` と現在の `worldZ` を共有逆投影関数へ渡して求め、`[-PADDLE_LIMIT, PADDLE_LIMIT]`へ clampする。
- 単純な `(stageX - 0.5) * PLAYER_AIM_SPAN` は legacy modeだけに残す。direct modeでこの近似を描画位置へ使わない。
- `player.z` は判定用、`player.viewZ` は既存どおり奥行きスケール・影の平滑化用として維持する。

### 9.3 logical poseとrender pose

- logical poseは最新sampleを最大16msだけ速度外挿し、Canvas内へ clampする。
- render poseはlogical poseへ指数追従する。

```text
speedRatio = clamp(speed / MAX_GESTURE_SPEED, 0, 1)
tau        = lerp(0.020, 0.008, speedRatio)
alpha      = 1 - exp(-dt / tau)
render     = lerp(previousRender, logical, alpha)
```

- contact detectorはlogical pose、Rendererはrender poseを使う。
- 両poseの中心差は常に現在のブレード半径の25%以下へ制限する。超える場合はrender poseをlogical側へ補正する。
- この上限により、見た目では離れているのに判定だけ当たる状態を作らない。

### 9.4 phase

| 現在 | event / 条件 | 次 | contact可否 |
|---|---|---|---|
| idle | valid pointerdown | tracking | 可（静止block） |
| tracking | `speed >= 0.55` | armed | 可 |
| armed | `speed < 0.55` かつpointer down | tracking | 可 |
| tracking / armed | contact成立 | contact | 同flightは直ちに不可 |
| contact | 次のfixed step | follow | 不可 |
| tracking / armed | pointerup | follow | snapshot期限内だけ可 |
| follow | snapshot期限切れ | recover | 不可 |
| recover | 待機姿勢へ到達 | idle | 不可 |
| 任意 | cancel / suspension / quit | recover | 不可 |

- followは接触済みflightへ再接触しない。
- recoverは 0.14〜0.22秒の範囲で距離依存とし、`P_SPEED` はrecoverの上限速度として再利用してよい。
- 新しい pointerdown はrecoverを中断してtrackingへ入れる。

### 9.5 ラケット角度

- 持ち手角度は `atan2(velocityY, velocityX) + Math.PI / 2` を基準にする。
- `speed < 0.15`では、直前角度から既存待機角 `Math.PI / 2`へ緩やかに戻す。
- ブレードの縦横比は `lift` と `curvature` から最大15%だけ変化させる。
- contact時は0.08秒以内のflashだけを加え、ボールへ吸着する自動移動を行わない。
- `prefers-reduced-motion: reduce`では残像を描かず、flashは透明度変化だけにする。

## 10. プレイヤー実衝突

### 10.1 成立条件

次を全て満たすときだけcontact候補を評価する。

1. `controlModel === "direct-paddle-v1"`。
2. ゲームがsuspendされておらず、phaseがrally。
3. `ball.live === true`。
4. `ball.hitter === "A"`。
5. `ball.bounces >= 1`。
6. `ball.vz < 0`。
7. paddle phaseがtracking / armed、または未接触flightの有効follow。
8. 現在 `flightId !== lastPlayerContactFlightId`。
9. world Z depth gate内。
10. 画面座標スイープ楕円が交差する。

### 10.2 flight lock

- serve成功と `makeShot()` 成功のたびに `flightId`を1増やす。
- player contactを採用した瞬間、ballを変更する前に `lastPlayerContactFlightId = flightId` とする。
- 時間だけの `contactCooldown` を多重打球防止の主契約にしない。
- solver失敗時も同flightを再打球させない。ballはincoming状態のまま進行し、通常の失点判定へ到達させる。

### 10.3 depth gate

```text
depthTolerance = clamp(
  CONTACT_DEPTH_BASE + abs(ball.vz) * FIXED_STEP,
  CONTACT_DEPTH_BASE,
  CONTACT_DEPTH_MAX
)
```

| 定数 | 値 |
|---|---:|
| `CONTACT_DEPTH_BASE` | `14` world unit |
| `CONTACT_DEPTH_MAX` | `24` world unit |

`abs(ball.z - paddle.worldZ) <= depthTolerance` を必須とする。高速球でも1 fixed step分の移動量を加えるが、上限24を越えて奥行き判定を広げない。

### 10.4 画面座標スイープ楕円

各fixed stepで、直前・現在の ball world位置を共有投影関数でscreenへ変換し、直前・現在のlogical paddle poseと相対運動を作る。

1. paddleの中間角度で相対segmentの両端を逆回転する。
2. 描画blade半径を `visualRx`、`visualRy`、投影ball半径を `ballR` とする。
3. contact用半径は `rx = visualRx * 1.08 + ballR`、`ry = visualRy * 1.08 + ballR` とする。
4. 相対segment `d(t)` に対する `q(t) = (dx(t)/rx)^2 + (dy(t)/ry)^2` の最小点 `t` を二次式から求め、`[0, 1]`へ clampする。
5. `q(t) <= 1`なら画面交差とする。

見た目より8%大きい許容は初心者補助である。品質計算は1.08倍前のvisual半径を使うため、補助領域だけで当たった接触は品質0となる。

### 10.5 接触品質

```text
screenQuality = clamp(1 - sqrt(qVisualAtContact), 0, 1)
timingQuality = clamp(1 - abs(ball.z - paddle.worldZ) / depthTolerance, 0, 1)
contactQuality = clamp(0.70 * screenQuality + 0.30 * timingQuality, 0, 1)
```

- `contactOffsetX/Y` はvisual楕円半径で正規化した接触位置を `[-1, 1]`へ clampする。
- 品質を下限へ底上げしない。低品質接触は誤差とミスへ反映する。
- collision計算が非有限、半径0、投影不能になった場合は非接触として扱い、状態を変更しない。

## 11. ShotIntent

### 11.1 passive / active

- `metrics.speed < GESTURE_MIN_SPEED` はpassive接触とし、`classifiedShot = "PUSH"`、`power = 0.12`とする。
- それ以外はactiveとし、次式でpowerを求める。

```text
power = clamp(
  (speed - GESTURE_MIN_SPEED) /
  (MAX_GESTURE_SPEED - GESTURE_MIN_SPEED),
  0,
  1
)
```

### 11.2 連続値

```text
lift = clamp(-directionY, -1, 1)

aimX = clamp(
  0.72 * directionX - 0.28 * contactOffsetX,
  -1,
  1
)

topSpin = passive
  ? 0
  : clamp(lift * (0.35 + 0.65 * power), -1, 1)

sideSpin = passive || abs(curvature) < CURVE_SPIN_THRESHOLD
  ? 0
  : clamp(curvature * (0.30 + 0.70 * power), -1, 1)
```

depthは分類後の既存 `SHOTS[type].dep` を正規化し、powerで小さく補正する。

```text
baseDepth = clamp((SHOTS[type].dep - 24) / ((HL - 14) - 24), 0, 1)
depth = passive
  ? baseDepth
  : clamp(baseDepth + (power - 0.5) * 0.12, 0, 1)
```

### 11.3 技分類

| 条件（上から評価） | `classifiedShot` |
|---|---|
| passive | `PUSH` |
| short かつ `lift <= -0.42` | `STOP` |
| short かつ `lift >= 0.42` | `FLICK` |
| short のその他 | `PUSH` |
| `lift >= 0.42` かつ `ballY < LOB_MAX_Y` | `LOB` |
| `lift >= 0.42` かつ `speed >= 2.90` かつ `ballY > SMASH_MIN_Y` | `SMASH` |
| `lift >= 0.42` | `DRIVE` |
| `lift <= -0.42` | `CHOP` |
| その他 | `PUSH` |

- short判定は既存 `isShortBall(lastBounceZ, ballY, "P")` を使う。
- 横回転は独立連続値であり、新しい `ShotId` を追加しない。
- flash、効果音、チュートリアル用の表示名には既存 `ShotId` と `SHOTS[type].lab` を使う。

## 12. player専用打球ソルバー

### 12.1 既存経路との分離

- 既存 `solveShot()` を直接拡張してAIとplayerを同時に変更しない。
- `solveDirectPlayerShot()` を追加し、direct player contactだけから呼ぶ。
- AIとlegacy playerは従来どおり `solveShot()` を使う。
- direct solverの純粋入力には、contact前のball、`ShotIntent`、固定された乱数関数を渡す。

### 12.2 target

```text
targetX = aimX * (HW - 7)
targetZ = 24 + depth * ((HL - 14) - 24)
```

player打球なので target Z は正側とする。X/Zは最後に既存台内安全範囲へ clampする。

### 12.3 speed / elevation

| ShotId | v0.2.0 direct solver |
|---|---|
| `DRIVE` / `SMASH` / `PUSH` / `CHOP` | 既存absolute範囲を使い、`lerp(0.72 * min, max, power)`。乱数で基準speedを抽選しない |
| `LOB` | `solveSpeed()`、elevation `1.02`、必要speedへ `lerp(0.95, 1.08, power)` を乗算 |
| `STOP` | `solveSpeed()`、elevation `0.50`、必要speedへ `lerp(1.00, 1.08, power)` を乗算 |
| `FLICK` | `solveSpeed()`、elevation `0.40`、必要speedへ `lerp(1.03, 1.18, power)` を乗算 |

- absolute系は上表speedと `solveAngle()` で targetへ解く。
- LOBは既存どおり `ensureNetClear()` を通さない。
- LOB以外かつ `contactQuality > 0.30` の基準弾道だけ `ensureNetClear()` を通す。
- 誤差適用後の弾道を成功帯へ戻す後処理を行わない。低品質とミスの差を消さない。

### 12.4 縦・横回転とincoming carry-over

```text
generatedSpin = intent.topSpin * MAX_TOP_SPIN
generatedSide = intent.sideSpin * MAX_SIDE_SPIN

spinCarry = passive ? 0.55 : 0.18
sideCarry = passive ? 0.60 : 0.25

outSpin = clamp(generatedSpin + incomingSpin * spinCarry, -1.25, 1.25)
outSide = clamp(generatedSide + incomingSide * sideCarry, -1.00, 1.00)
```

| 定数 | 値 |
|---|---:|
| `MAX_TOP_SPIN` | `1.25` |
| `MAX_SIDE_SPIN` | `1.00` |
| active spin carry | `0.18` |
| active side carry | `0.25` |
| passive spin carry | `0.55` |
| passive side carry | `0.60` |

incomingはcontact前にcopyし、ballへ新値を代入した後から読まない。符号規約は現行 `BallVector.spin / side` を維持する。

### 12.5 誤差・乱数

```text
qualityLoss = 1 - contactQuality
error = SHOTS[type].err + qualityLoss^2 * 0.160
```

direct solverは1打球につき次の3回だけ乱数を消費する。

1. elevation error: `(r1 * 2 - 1) * error`
2. azimuth error: `(r2 * 2 - 1) * error * 1.5`
3. speed error: `1 + (r3 * 2 - 1) * error * 1.6`

- side、基準speed、spinに追加乱数を使わない。
- player direct経路の新規乱数列は上記で固定する。
- AI・serve・legacyの既存乱数消費回数と順序は変更しない。
- テストでは注入したrandomで消費回数と順序を検査する。

### 12.6 solver失敗

次のいずれかはsolver失敗とする。

- target、speed、elevation、azimuth、velocity、spin、sideのいずれかが非有限。
- speedが0以下。
- `solveSpeed()` / `solveAngle()` が既存の有効解条件を満たさない。

失敗時はincoming ballを変更せず、同flightの再contactを禁止したまま通常進行させる。UIには `返球できませんでした` を短時間表示し、console warningは固定reason codeだけを出す。座標、プレイヤー名、保存値、入力軌跡をログへ出さない。

## 13. 描画・フィードバック

### 13.1 player racket

- direct modeは `RenderScene.directPlayerPose` のscreen X/Yを中心として描く。
- ブレード半径は既存 `paddleScreenRadius()` と `viewZ` の奥行き比を維持する。
- 持ち手角度、楕円の回転、縦横比はcontact前から入力速度・lift・curvatureへ追従する。
- shadowは既存depth表現を維持するが、ラケット中心から不自然に離れないようscreen Xを共有する。
- `smashable` の輪は既存表示を維持し、direct contactを自動成立させる補助にはしない。

### 13.2 follow / recover

- contact後はcontact時の速度方向へ0.10〜0.16秒だけ減衰移動する。
- pointerupだけの場合もsnapshot期限内は同方向へfollowし、その後recoverする。
- follow中に画面外へ出ず、recoverは入力offsetを適用した待機位置へ戻る。
- 定型 `swingType` アニメーションはlegacyだけで使い、direct modeでは入力poseへ重ねない。

### 13.3 ball・横回転

- `ball.side` は既存物理へ渡す。
- v0.2.0で新しい3Dボールモデルは追加しない。
- debug時のみ、sideの符号と強さを短い線または色で表示してよい。通常表示の回転表現変更は必須にしない。

### 13.4 debug契約

`?debugInput=1` のときだけ、次を有効にする。

- 直近0.15秒の入力軌跡。
- logical pose / render pose / collision ellipse / depth gate状態。
- `body` の `data-control-model`、`data-last-shot`、`data-side-spin-sign`、`data-contact-quality-band`。

debug値はE2E観測用であり、通常URLでは軌跡と追加datasetを公開しない。個人情報・保存値・生座標をconsoleへ出さない。

| 右・奥 | `45` | `-45` | `52 / 74` | `0.8` |

- quality: high `0.85`、low `0.25`
- DRIVE / CHOP / PUSH / SMASHについて、各代表条件・各qualityを400試行
- 横回転は中央条件・quality `0.85`・sideSpin `-0.8 / 0.8`を各400試行

判定:

- DRIVE / CHOP / PUSH のhigh品質は台内率85%以上。
- SMASHのhigh品質は台内率70%以上。
- 各ShotIdのlow品質ミス率はhigh品質より10 percentage point以上高い。
- sideSpin正負の平均landing X差は符号どおりで、0をまたぐ。
- 同一seed・同一入力は結果と乱数消費数が再現する。

これは確率的回帰しきい値であり、全打球の成功保証や理論上限とは表現しない。母集団、除外条件、seed、製品関数経路をテスト名とコメントへ残す。

### 17.5 E2E

Playwrightは内部関数を直接呼ばず、CanvasへPointer Event列を送って製品経路を通す。観測だけ `?debugInput=1` のdatasetを使う。

- query無しでdirect、`?controlModel=legacy`でlegacyになる。
- X/Y追従とpointerType別offset。
- ballへ重ねた静止ラケットで弱いPUSH、外すと非返球。
- 上gestureでDRIVE、高球高速上gestureでSMASH。
- 短球の下gestureでSTOP、上gestureでFLICK。
- 曲線gestureの向きで `data-side-spin-sign` が反転する。
- 同flightでflash / rally incrementが1回だけ。
- pointercancel、pause、portrait、too-small、pagehide後にphaseがarmed / followで残らない。
- 9球種×3長さサーブ、AIサーブ、得点、結果、戦績、PWAを回帰する。
- desktop Chromium、Android相当Chromium、iPhone相当WebKitの3環境で行う。

### 17.6 安定性・性能

- `npm run test:e2e:stability` をworker 1、retry 0、3反復で成功させる。
- 20分相当のfixed-step合成ラリーでBall / pose / metricsにNaNが無い。
- PointerSampleは32件を越えず、pointer終了後に参照を保持し続けない。
- 568×320でdebug無効時の描画に毎frame配列確保を追加しない。
- パフォーマンス低下を疑う場合は計測を残し、物理stepを240Hzから下げて解決しない。

## 19. リリース・ロールバック

### 19.1 ローカル段階

- Phase 7-4まではquery無しの既定をlegacyに保ち、テストURLだけでdirectを有効にしてよい。
- Phase 7-5の全gateが通った変更で、query無しの既定をdirectへ切り替える。
- 途中成果物をPagesへ公開しない。

### 19.2 公開後の即時回避

- ユーザーはURLへ `?controlModel=legacy` を付けることで旧操作を利用できる。
- このqueryはデータ移行を伴わず、IndexedDBとPWA identityを共有する。
- legacy利用を自動保存しないため、通常URLへ戻せばdirectへ戻る。

### 19.3 code rollback

- 対象commitを `git revert`し、履歴を書き換えるreset / force pushを使わない。
- package / lock / child cacheをrollback先版へ一致させる。
- root workerのchild bypass、manifest identity、IndexedDBを戻さない。
- rollback公開でもroot+child検査、Actions、deployment SHA、HTTP/PWA、Chromeを再確認する。

## 20. リスクと対策

| リスク | 予防 | 検出 | 回復 |
|---|---|---|---|
| 操作が難しすぎる | 見た目+8% contact、既存target solver、passive block | Chrome空振り/命中確認、品質統計 | 本書範囲内で定数を再校正。必要ならlegacy query |
| 見た目と判定がずれる | shared projection、pose差25%上限 | logical/render/debug ellipse E2E | renderをlogical側へ補正 |
| 高速球がすり抜ける | fixed 240Hz、relative swept segment、速度依存depth | 1step横断単体 | depth上限内で基準値を同一設計へ追記して再校正 |
| sample rateで球威が変わる | event timestamp、時間窓、coalesced events | 60/120/240Hz差5% | metrics式を修正し、速度閾値だけで隠さない |
| 回転でsolverが不安定 | spin/side clamp、player専用solver | 固定母集団、NaN検査 | solver失敗を安全な非返球として処理 |
| 低品質ミスを補助が消す | 誤差後の再解決禁止 | high/lowミス率差 | post-correctionを追加せず誤差/係数を再校正 |
| AI回帰 | player専用solver、既存AI/legacy関数維持 | 既存乱数・AI・U31回帰 | direct変更だけを切り離してrevert |
| サーブ回帰 | serve adapter、既存 `doServe()` 維持 | 9×3×2×3総当たり | direct serve変更を行わずlegacy adapterへ戻す |
| PWA旧cache混在 | package/cache同期、current cache限定 | app/dist/合成Pages検査 | revert版で再deployし旧系列cacheをactivate時削除 |
| Chrome自動化が実時間操作に間に合わない | E2Eと手動項目を分離 | 未実施を明記 | ユーザー実機で操作感だけ完了確認 |

## 21. 採用しない案

| 案 | 採用しない理由 |
|---|---|
| 完全な3D剛体ラケット衝突 | Canvas 2D・スマートフォン操作に対して複雑で、既存ソルバーとテスト資産を失う |
| 初回からWebGL / Three.jsへ移行 | 操作改善と描画基盤変更を同時に行い、原因分離とrollbackを難しくする |
| 既存 `solveShot()` を直接拡張 | AI・legacy・乱数契約まで同時に変わり、回帰範囲が過大になる |
| world Zも指で操作 | 2D画面から奥行きを一意に決められず、操作学習と接触判定が不安定になる |
| `CONTROL_ASSIST = 0.65` でraw velocityとsolverをblend | ラフ案にraw 3D velocityの定義がなく、係数だけでは実装可能な契約にならない。v0.2.0は既存target solver自体を補助として使う |
| 誤差後に必ず台内へ戻す | 接触品質とミスを消し、低品質打球が実質ノーリスクになる |
| control modelをIndexedDB / localStorageへ保存 | schema・設定UI・移行を増やし、比較用fallbackの目的を越える |
| v0.2.0でAI実衝突・gesture serve・trainingも実装 | player coreの受入前に調整軸が増え、操作不具合の原因を分離できない |

## 22. 未確定・要確認事項
