## 1. 目的・背景

v0.3.0 時点の `src/view/layout.ts:evaluateViewport()` は `width <= height` を即 `portrait-blocked` とし、`src/view/orientation.ts` が「端末を横向きにしてください」のガードを全画面表示する。`manifest.webmanifest` は `orientation: "landscape"` を宣言し、`scripts/check-app.mjs:444` がそれを契約として強制している。アプリ名も「卓球 横画面」である。

つまり現状、縦持ちでは一切遊べない。片手で持ったまま遊びたい、横持ちに持ち替えるのが面倒、という利用形態を取りこぼしている。

一方で、縦画面対応は「CSS を足せば動く」類の変更ではない。本アプリの**接触判定は画面空間（投影後の px）で行われ**（`src/control/contact.ts:sweptPaddleContact()`）、ラケットの捕球半径は `Math.min(width, height) * 0.055`（`src/utils.ts:paddleScreenRadius()`）、カメラ焦点距離は `Math.max(300, Math.min(1.3 * width, 0.8 * height))`（`src/view/camera.ts:computeCamera()`）で決まる。stage のアスペクト比を変えると、**世界座標での捕球半径と左右到達距離が変わり、難易度と操作感が変わる**。

注意点27・28 の教訓（代表打点1点で校正しない／補助や速度下限を触ると低品質のミスが消える／難易度の体感指標を実測で受け入れる）を踏まえ、本設計は**物理・接触・難易度の定数を一切動かさない**ことを最優先の制約とする。

以下はコードの静的確認と数式からの計算に基づく。実機性能測定・実機操作感・公開受入は未実施である。

## 3. 全体方針

### 3.1 中心となる契約：stage を正方形に固定する

縦画面では stage（`#stage`、canvas の親）を **正方形（高さ = 幅）** とし、残りの縦方向を画面下部の操作レールに充てる。

これが成立する理由：

`computeCamera(W, H)` の焦点距離は `f = max(300, min(1.3W, 0.8H))`。stage 幅 `W ≥ 0.615 × H` の範囲では `min` が `0.8H` 側になるため、**f は stage 高さだけで決まる**。地平線 `cy = H × 0.735 − 190 × (f / 193)` も stage 高さだけで決まる。

一方 `paddleScreenRadius()` は `min(W, H) × 0.055` なので、**`W ≥ H` の範囲ではラケット半径も stage 高さだけで決まる**。

正方形（`W = H`）は、この 2 つの条件を同時に満たす上限である。したがって縦画面の正方形 stage は、**同じ高さを持つ横画面 stage と、f・cy・ラケット半径・px/cm 換算・世界座標での捕球半径がすべて一致する**。

### 3.2 数値による検証（z = −178、cameraZ = −330、`paddleDepthScale` = 1）

接触面は注意点27 のとおり実 AI 返球の 99% で最遠 clamp `z = -178` になる。この面での px/cm は `f / 152`。

| 構成 | f | px/cm | ラケット半径 | 捕球半径[cm] | 左右到達[cm] | cy | 天板奥端 y |
|---|---|---|---|---|---|---|---|
| 横 844×390（stage 625×390）**基準** | 312.0 | 2.0526 | 21.45px | **10.45** | 139.18※ | −20.50 | 106.4 |
| 横 568×320（stage 392×320） | 300.0 | 1.9737 | 18.00px | 9.12 | 87.91 | −60.14 | 61.9 |
| 横 915×412（stage 677×412） | 329.6 | 2.1684 | 22.66px | 10.45 | 143.04※ | −21.66 | 112.4 |
| 縦 S=360 | 300.0 | 1.9737 | 19.80px | 10.03 | 78.66 | −30.74 | 91.3 |
| 縦 S=375 | 300.0 | 1.9737 | 20.63px | 10.45 | 81.94 | −19.71 | 102.3 |
| 縦 S=390 | 312.0 | 2.0526 | 21.45px | **10.45** | 81.94 | **−20.50** | **106.4** |
| 縦 S=412 | 329.6 | 2.1684 | 22.66px | 10.45 | 81.94 | −21.66 | 112.4 |
| 縦 S=430 | 344.0 | 2.2632 | 23.65px | 10.45 | 81.94 | −22.60 | 117.4 |
| 縦 S=820 | 656.0 | 4.3158 | 45.10px | 10.45 | 81.94 | −43.10 | 223.8 |

※ 横画面の左右到達は画面 clamp では縛られず、世界 clamp `PADDLE_LIMIT = 104cm` が binding する。

読み取れること：

1. **S = 390 は横 844×390 と f・cy・ラケット半径・捕球半径・天板奥端 y が完全一致する。** 天板奥端 y = 106.4px は注意点30 に記録された「約 107px」と一致し、計算系の妥当性が確認できる。
2. **縦の捕球半径は S に依存せず 10.45cm（S ≥ 375）/ 10.03cm（S = 360）** で、既存横画面の範囲 9.12〜10.45cm の中に収まる。難易度・接触補助を触る必要がない。
3. **縦の左右到達は 78.66〜81.94cm** で、台の半幅 `HW = 76.25cm` を上回る。AI の狙い clamp は `±(HW − 7) = ±69.25cm` なので、バウンド後のドリフトを含めても届く。
4. S = 360 未満では画面 X clamp が `HW` を割る（S = 320 で 69.9cm）。**よって縦画面の最小 stage 辺を 360px とする。** これは X clamp やラケット定数を触らずに済ませるための判定であり、定数変更の代替である。
5. S > 836 では `PADDLE_SIZE_MAX = 46` が binding して捕球半径が縮むが、これは横画面で stage 高さが 836px を超える場合と同じ既存挙動であり、新規の劣化ではない。

### 3.3 退けた代替案

| 代替案 | 退ける理由 |
|---|---|
| stage を viewport 全面（縦長）にする | `f = 0.8H` が増える一方 `radius = 0.055W` が据え置かれ、捕球半径が 10.45 → 7〜9cm へ縮む。難易度が無断で上がる。 |
| 縦画面用に接触補助倍率を上げる | 注意点6・27・28 の罠。補助でミスを消すとラリーが終わらなくなり、自滅率の単調性も壊れる。校正のやり直し（`measure-play-balance` の再測定と閾値再確定）が必要になり、工数が 3〜4 人日増える。 |
| 画面 X clamp を縦だけ緩める | 横画面と縦画面で `baseCenter()` の分岐が増え、注意点29 の「製品経路と違う引数でテストする」事故を招きやすい。最小幅 360px の gate で済む。 |
| カメラ式に縦専用の分岐を入れる | `computeCamera()` は 3 箇所（描画・接触・ラケット world 変換）から共有されており、分岐は投影の不一致を生む。注意点30 の再発源になる。 |

### 3.4 操作レールは固定高にする

横画面ではサーブ操作パネルを `body[data-phase="serve"][data-server="P"]` のときだけ表示している。縦画面で同じ出し入れをすると、**レール高が局面ごとに変わり stage 辺長が変わる** → f・px/cm・捕球半径がラリー途中で変化し、静的レイヤ（`layerKey`）も再生成される。

したがって縦画面では**操作レールを固定高 272px とし、サーブ操作パネルは常時表示**する。プレイヤーサーブ待ち以外では `pointer-events: none` と不透明度低下で操作不能にするだけで、DOM と占有高は変えない。局面による高さ変動を作らない。

272px の根拠：ラベル 16 ＋ 球種 3 行 × 44 ＋ 行間 6 × 2 ＋ 長さ 1 行 44 ＋ 試合操作 1 行 44 ＋ 行間と上下 padding 36 = 272。44px 操作領域（注意点24）を全要素で確保する。

## 4. 詳細仕様

### 4.1 viewport 分類（`src/view/layout.ts`）

定数を追加する。既存の 3 定数は変更しない。

```
MIN_PORTRAIT_STAGE_SIDE = 360
PORTRAIT_RAIL_HEIGHT = 272
```

`ViewportState` を次へ変更する。`"portrait-blocked"` は削除し、`"portrait"` と `"portrait-too-small"` を追加する。

```
"portrait" | "portrait-too-small" | "too-small" | "compact-landscape" | "wide-landscape"
```

純粋関数 `portraitStageSide({width, height})` を追加する。戻り値は `Math.min(width, height - PORTRAIT_RAIL_HEIGHT)`。`width` / `height` が有限の正数でない場合は `0` を返す。

`evaluateViewport()` の判定順：

1. `width` / `height` のいずれかが有限の正数でない → `too-small`
2. `width <= height`（縦）
   - `portraitStageSide() >= 360` → `portrait`
   - それ以外 → `portrait-too-small`
3. `width < 568 || height < 320` → `too-small`
4. `width < 760` → `compact-landscape`、それ以外 → `wide-landscape`

`isViewportBlocked()` は `portrait-too-small` と `too-small` で `true`。`portrait` は `false`（プレイ可能）。

境界の確定値（単体テストで固定する）：

| 入力 | 期待 | 理由 |
|---|---|---|
| 390×844 | `portrait` | side = min(390, 572) = 390 |
| 390×664 | `portrait` | side = min(390, 392) = 390 |
| 390×632 | `portrait` | side = min(390, 360) = 360（境界ちょうど） |
| 390×631 | `portrait-too-small` | side = 359 |
| 360×640 | `portrait` | side = min(360, 368) = 360 |
| 360×631 | `portrait-too-small` | side = 359 |
| 359×844 | `portrait-too-small` | side = 359（幅が binding） |
| 568×568 | `portrait-too-small` | 正方形は縦扱い、side = min(568, 296) = 296 |
| 430×660 | `portrait` | side = min(430, 388) = 388（レターボックス） |
| 568×320 | `compact-landscape` | 既存不変 |
| 567×320 / 568×319 | `too-small` | 既存不変 |
| 760×320 | `wide-landscape` | 既存不変 |

### 4.2 ガード文言（`src/view/orientation.ts`）

`update()` のメッセージ分岐を 3 系統にする。`portrait` ではガードを出さない。

| 状態 | 文言 |
|---|---|
| `portrait-too-small` | `画面が小さすぎます（現在 W×H、縦画面は幅360以上・高さ幅+272以上が必要）` |
| `too-small` | `画面が小さすぎます（現在 W×H、横画面は 568×320 以上が必要）`（既存文言を横画面向けに明確化） |

`#viewportGateTitle` は現在「横画面でプレイ」の固定文字列。`portrait-too-small` / `too-small` のどちらでも「画面サイズが足りません」へ差し替える。`#viewportGate` の `↻` 装飾は横向き誘導の意味を失うので削除する。

`document.body.dataset.viewport` には新しい state 名をそのまま入れる。CSS は `body[data-viewport="portrait"]` で縦レイアウトを適用する。

### 4.3 縦画面レイアウト（`src/styles.css`）

`index.html` の DOM は変更しない。`#appShell` の子は `#leftRail` / `#stage` / `#rightRail` の順であり、CSS Grid の行配置だけで縦レイアウトを作れる。`#board` / `#situation` / `#pointBanner` / `#flash` / `#hint` は `#stage` の内側にあるため、コーナースコアと演出は stage 相対のまま自動的に追従する。

```
body[data-viewport="portrait"] .app-shell {
  grid-template-columns: minmax(0, 1fr);
  grid-template-rows: minmax(0, 1fr) 272px;
  align-items: start;
}
body[data-viewport="portrait"] .app-rail--left { display: none; }
body[data-viewport="portrait"] #stage {
  aspect-ratio: 1 / 1;
  width: auto;
  height: auto;
  max-width: 100%;
  max-height: 100%;
  margin-inline: auto;
}
body[data-viewport="portrait"] .app-rail--right {
  /* 横並び 2 ブロック: 試合操作行 → サーブ操作 */
  height: 272px;
  padding: 8px 12px;
  overflow: hidden;
}
```

- stage は残り領域の上端へ寄せる（`align-items: start`）。余った縦方向は操作レール直上の余白になり、親指の置き場になる。
- 縦画面ではサーブ操作パネルを常時表示する。`body[data-viewport="portrait"]:not([data-phase="serve"]) .serve-controls`、および `body[data-viewport="portrait"][data-phase="serve"][data-server="A"] .serve-controls` に `pointer-events: none; opacity: .45;` を当てる。`display` と占有高は変えない。
- 球種グリッドは 3 列 × 3 行、長さは 3 列 × 1 行。各ボタンは最小 44×44px。
- 試合操作（設定 / 音 / 振動）と `#playStatus` は 1 行 44px に横並びで収める。
- 568〜759px × 高さ 360px 以下の横画面圧縮規則（注意点24）は `body[data-viewport="compact-landscape"]` 相当の既存セレクタに閉じたままにし、縦画面へ適用しない。既存メディアクエリに `and (orientation: landscape)` が付いているものはそのまま機能するが、`@media (max-width: 430px)` のように orientation 非依存のブロックは縦画面にも当たるため、縦専用指定で明示的に上書きする。

### 4.4 canvas のリサイズ

`src/render.ts:resize()` は `canvas.clientWidth` / `clientHeight` を読むため、CSS の変更だけで追従する。`window.resize` / `visualViewport.resize` の購読も既存のままでよい。`layerKey`（幅×高さ@dpr）が変わったときだけ静的レイヤを再生成する既存挙動を使う。**コード変更なし。**

ただし回転時に `visualViewport` のサイズ確定が遅れる端末があるため、既存の `window.setTimeout(this.resize, 250)` を維持する（`src/render.ts:298`）。

### 4.6 入力・ラケット・接触

**変更なし。** 根拠：

- `src/control/paddle.ts:baseCenter()` は `stageX * width` と `stageY * height − offset * height` で、stage 矩形に対する正規化座標を使う。stage が正方形になっても式は同じ。
- `POINTER_OFFSET_TOUCH = 0.06` は stage 高さ比。S = 390 の縦画面では 23.4px で、横 844×390（390 × 0.06 = 23.4px）と同一。
- `STRIKE_MIN_DISPLACEMENT = 0.04` / `STRIKE_MIN_SPEED = 1.1` / `GESTURE_MIN_SPEED = 0.55` も stage 高さ比。S = 390 で横 844×390 と同一の px しきい値になる。S = 360 では 10% 小さい px しきい値（= わずかに出しやすい）になるが、これは横 568×320（高さ 320）で既に起きている既存の挙動範囲の内側である。
- `src/view/input-math.ts:normalizeStageX()` と `src/control/stroke.ts:normalizeStagePoint()` は canvas 矩形基準。変更不要。

### 4.7 停止理由

`src/view/suspension.ts` は変更しない。`viewportBlocked` は `isViewportBlocked()` の結果で駆動されるため、`portrait` では停止せず、`portrait-too-small` では従来どおり停止する。回転して縦 ↔ 横を跨いだときは、どちらもプレイ可能なら停止せずレイアウトだけ切り替わる。

ただし**回転時に stage 辺長が変わるため、ラリー中の回転は捕球半径[cm]を 9.12〜10.45cm の範囲で変化させる**。これは横画面内のリサイズでも既に起きる既存挙動であり、新しい保証は追加しない。回転直後に `input.reset()` を行う既存動作（`src/input.ts:reset()`）を維持する。

## 10. 未確定・要確認事項

### 10.1 確定済み

- **PWA 表示名（§4.5）**: 2026-11-06 のユーザー確認により、`name` / `short_name` を「卓球」へ変更すると確定。`description` も縦横両対応の文言へ変更する。`id` / `start_url` / `scope` / cache 名 / IndexedDB 名は変更しないため、既存インストールの更新経路と既存戦績には影響しない。

### 10.2 未確定

1. **縦画面の実機操作感**: §3.2 の計算では捕球半径が既存横画面の範囲内に収まるが、片手持ちで親指が届く範囲は実機でしか判断できない。G2 で不足と判断された場合の対応（stage をさらに上へ寄せる、レール高を増やす）は実測後に本書を改訂して確定する。**補助倍率・品質下限・プレイヤー誤差は実測なしで触らない。**
2. **縦画面の縦方向エフェクト余白**: 得点バナー・状況チップ・打球トーストは stage 相対の固定 px オフセット（`#matchMeta` 直下 54px / 60px）で配置されている。正方形 stage でも収まる見込みだが、重なりの最終判断は 8.3 の撮影で行う。重なる場合は縦専用のオフセットを本書へ追記する。
3. **portrait プロジェクトの環境選定**: Playwright の既存 3 環境（desktop-chromium / mobile-chromium / mobile-webkit）に対し、portrait を chromium・webkit のどちらで走らせるか（あるいは両方か）は、CI 時間の実測後に決める。初期採用は mobile-chromium 相当の 1 環境とする。
