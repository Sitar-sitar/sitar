## 1. 目的・背景

v0.3.0 時点の `src/view/layout.ts:evaluateViewport()` は `width <= height` を即 `portrait-blocked` とし、`src/view/orientation.ts` が「端末を横向きにしてください」のガードを全画面表示する。`manifest.webmanifest` は `orientation: "landscape"` を宣言し、`scripts/check-app.mjs:444` がそれを契約として強制している。アプリ名も「卓球 横画面」である。

つまり現状、縦持ちでは一切遊べない。片手で持ったまま遊びたい、横持ちに持ち替えるのが面倒、という利用形態を取りこぼしている。

一方で、縦画面対応は「CSS を足せば動く」類の変更ではない。本アプリの**接触判定は画面空間（投影後の px）で行われ**（`src/control/contact.ts:sweptPaddleContact()`）、ラケットの捕球半径は `Math.min(width, height) * 0.055`（`src/utils.ts:paddleScreenRadius()`）、カメラ焦点距離は `Math.max(300, Math.min(1.3 * width, 0.8 * height))`（`src/view/camera.ts:computeCamera()`）で決まる。stage のアスペクト比を変えると、**世界座標での捕球半径と左右到達距離が変わり、難易度と操作感が変わる**。

注意点27・28 の教訓（代表打点1点で校正しない／補助や速度下限を触ると低品質のミスが消える／難易度の体感指標を実測で受け入れる）を踏まえ、本設計は**物理・接触・難易度の定数を一切動かさない**ことを最優先の制約とする。

## 3. 全体方針

### 3.1 中心となる契約：stage を正方形に固定する

縦画面では stage（`#stage`、canvas の親）を **正方形（高さ = 幅）** とし、残りの縦方向を画面下部の操作レールに充てる。

これが成立する理由：

`computeCamera(W, H)` の焦点距離は `f = max(300, min(1.3W, 0.8H))`。stage 幅 `W ≥ 0.615 × H` の範囲では `min` が `0.8H` 側になるため、**f は stage 高さだけで決まる**。地平線 `cy = H × 0.735 − 190 × (f / 193)` も stage 高さだけで決まる。

一方 `paddleScreenRadius()` は `min(W, H) × 0.055` なので、**`W ≥ H` の範囲ではラケット半径も stage 高さだけで決まる**。

正方形（`W = H`）は、この 2 つの条件を同時に満たす上限である。したがって縦画面の正方形 stage は、**同じ高さを持つ横画面 stage と、f・cy・ラケット半径・px/cm 換算・世界座標での捕球半径がすべて一致する**。

### 3.2 数値による検証（z = −178、cameraZ = −330、`paddleDepthScale` = 1）

接触面は注意点27 のとおり実 AI 返球の 99% で最遠 clamp `z = -178` になる。この面での px/cm は `f / 152`。

読み取れること：

1. **S = 390 は横 844×390 と f・cy・ラケット半径・捕球半径・天板奥端 y が完全一致する。** 天板奥端 y = 106.4px は注意点30 に記録された「約 107px」と一致し、計算系の妥当性が確認できる。
2. **縦の捕球半径は S に依存せず 10.45cm（S ≥ 375）/ 10.03cm（S = 360）** で、既存横画面の範囲 9.12〜10.45cm の中に収まる。難易度・接触補助を触る必要がない。
3. **縦の左右到達は 78.66〜81.94cm** で、台の半幅 `HW = 76.25cm` を上回る。AI の狙い clamp は `±(HW − 7) = ±69.25cm` なので、バウンド後のドリフトを含めても届く。
4. S = 360 未満では画面 X clamp が `HW` を割る（S = 320 で 69.9cm）。**よって縦画面の最小 stage 辺を 360px とする。** これは X clamp やラケット定数を触らずに済ませるための判定であり、定数変更の代替である。
5. S > 836 では `PADDLE_SIZE_MAX = 46` が binding して捕球半径が縮むが、これは横画面で stage 高さが 836px を超える場合と同じ既存挙動であり、新規の劣化ではない。

### 3.3 退けた代替案

| 代替案 | 退ける理由 |
|---|---|
| stage を viewport 全面（縦長）にする | `f = 0.8H` が増える一方 `radius = 0.055W` が据え置かれ、捕球半径が 10.45 → 7〜9cm へ縮む。難易度が無断で上がる。 |
| 縦画面用に接触補助倍率を上げる | 注意点6・27・28 の罠。補助でミスを消すとラリーが終わらなくなり、自滅率の単調性も壊れる。校正のやり直し（`measure-play-balance` の再測定と閾値再確定）が必要になり、工数が 3〜4 人日増える。 |
| 画面 X clamp を縦だけ緩める | 横画面と縦画面で `baseCenter()` の分岐が増え、注意点29 の「製品経路と違う引数でテストする」事故を招きやすい。最小幅 360px の gate で済む。 |
| カメラ式に縦専用の分岐を入れる | `computeCamera()` は 3 箇所（描画・接触・ラケット world 変換）から共有されており、分岐は投影の不一致を生む。注意点30 の再発源になる。 |

### 3.4 操作レールは固定高にする

横画面ではサーブ操作パネルを `body[data-phase="serve"][data-server="P"]` のときだけ表示している。縦画面で同じ出し入れをすると、**レール高が局面ごとに変わり stage 辺長が変わる** → f・px/cm・捕球半径がラリー途中で変化し、静的レイヤ（`layerKey`）も再生成される。

したがって縦画面では**操作レールを固定高とし、サーブ操作パネルは常時マウント**する。プレイヤーサーブ待ち以外は既存の `button.disabled`（`src/ui.ts:427`・`:436` で既に設定済み）で操作不能にし、DOM と占有高は変えない。局面による高さ変動を作らない。

固定高は `PORTRAIT_RAIL_HEIGHT = 304px`。border-box の内訳を実 CSS から再計算した（1.2 版の 272px は算術誤りで、実際には収まらない）。

## 4. 詳細仕様

### 4.1 viewport 分類（`src/view/layout.ts`）

定数を追加する。既存の 3 定数は変更しない。

```
MIN_PORTRAIT_STAGE_SIDE = 360
PORTRAIT_RAIL_HEIGHT = 304
```

`ViewportState` を次へ変更する。`"portrait-blocked"` は削除し、`"portrait"` と `"portrait-too-small"` を追加する。

```
"portrait" | "portrait-too-small" | "too-small" | "compact-landscape" | "wide-landscape"
```

**入力を 2 系統に分ける（F-04 対応）。** gate・stage・レールが同じ content box 寸法を使うことが必須なので、縦画面の辺長だけは shell の content box から求める。

```
interface ViewportMetrics {
  readonly viewport: ViewportSize;  // visualViewport 由来。縦横判定と横画面しきい値に使う
  readonly content: ViewportSize;   // #appShell の content box。縦画面の stage 辺長に使う
}
```

`#appShell` は `padding: env(safe-area-inset-*)` を持つ（`src/styles.css:81-89`）ため、その content box はセーフエリアを除いた実利用領域と一致する。CSS Grid の行も同じ content box 上で解決されるので、JS と CSS が別式にならない。

純粋関数 `portraitStageSide(content)` を追加する。戻り値は `Math.floor(Math.min(content.width, content.height - PORTRAIT_RAIL_HEIGHT))`。`content.width` / `content.height` が有限の正数でない場合は `0` を返す。小数を切り捨てるのは、辺長をそのまま CSS の px 値として渡すため（§4.3）。

`evaluateViewport({ viewport, content })` の判定順：

1. `viewport` / `content` のいずれかが有限の正数でない → `too-small`
2. `viewport.width <= viewport.height`（縦）
   - `portraitStageSide(content) >= 360` → `portrait`
   - それ以外 → `portrait-too-small`
3. `viewport.width < 568 || viewport.height < 320` → `too-small`
4. `viewport.width < 760` → `compact-landscape`、それ以外 → `wide-landscape`

**横画面のしきい値はセーフエリアを控除しない。** 568×320 と 759/760×360 の既存契約（注意点24）は viewport 寸法で確定しており、ここで content box へ変えると既存の横画面挙動と既存 E2E が変わる。非対称は意図的であり、縦画面側だけが F-04 の対象である。

`isViewportBlocked()` は `portrait-too-small` と `too-small` で `true`。`portrait` は `false`（プレイ可能）。

境界の確定値（単体テストで固定する）。inset 列が 0 の行は `content == viewport`。

### 4.2 ガード文言と stage 辺長の受け渡し（`src/view/orientation.ts`）

`currentViewport()` を 2 系統へ拡張する。

- `viewport`: 既存どおり `visualViewport`（無ければ `documentElement.clientWidth/Height`）を丸めた値。
- `content`: `#appShell` の `clientWidth` / `clientHeight` から `getComputedStyle()` の `padding-*` を引いた content box。`#appShell` が取れない場合は `viewport` をそのまま使う。

`update()` のメッセージ分岐を 3 系統にする。`portrait` ではガードを出さない。

| 状態 | 文言 |
|---|---|
| `portrait-too-small` | `画面が小さすぎます（現在 W×H、縦画面は安全領域を除いて 360×664 以上が必要）`（W×H は `content` の値） |
| `too-small` | `画面が小さすぎます（現在 W×H、横画面は 568×320 以上が必要）`（W×H は `viewport` の値。既存文言を横画面向けに明確化） |

1.2 版の「高さ幅+272以上」という文言は §4.1 のレターボックス許容と一致していなかったため、必要サイズ（360×664）を直接書く形へ改める。

`#viewportGateTitle` は現在「横画面でプレイ」の固定文字列。`portrait-too-small` / `too-small` のどちらでも「画面サイズが足りません」へ差し替える。`#viewportGate` の `↻` 装飾は横向き誘導の意味を失うので削除する。

**stage 辺長の受け渡し（F-03 対応）。** `update()` は `document.body.dataset.viewport` を書くのと同じ箇所で、gate に使ったのと同一の値を CSS へ渡す。

- `portrait` のとき: `document.body.style.setProperty("--portrait-stage-side", `${portraitStageSide(content)}px`)`
- それ以外のとき: `document.body.style.removeProperty("--portrait-stage-side")`

gate 判定と CSS の実寸が同じ 1 つの戻り値から出るため、「判定は通ったが stage が 360px 未満」という状態を作れない。

**局面パネルの再同期（F-01 対応）。** `ViewportControllerOptions` へ `onViewportChange: (state: ViewportState) => void` を追加し、`update()` の末尾で呼ぶ。`src/main.ts` はこれを `game.syncServeControls()` へ接続する（`src/game.ts` に `this.ui.updateServeControls(this.state)` だけを行う public メソッドを追加する）。縦横を跨いだ直後にサーブパネルのマウント条件を再評価しないと、次のゲーム状態更新までパネルが出ない。`ViewportController` は `Renderer` より前に生成されるため、描画側へは直接接続しない（§4.4）。

### 4.3 縦画面レイアウト（`src/styles.css`）

  align-items: start;

}

#### 4.3.1 stage 内オーバーレイ（2026-11-08 確定）

`#board` / `#flash` / `#situation` / `#pointBanner` / `#hint` は `.stage #… { position: absolute }`（`src/styles.css:169-176`）で `.stage`（`position: relative; overflow: hidden`）に対して配置される。canvas も `.stage #cv` が同じ規則で stage を満たす。したがって縦画面でもすべて **stage 相対**であり、操作レールへはみ出さない。以下は stage 辺長 S に対する契約であり、S を CSS でどう確定するか（F-03）とは独立である。

- **縦専用の縦方向オフセットは追加しない。** 縦の最小 stage 高（S = 360）は既存最小横画面の stage 高 320px より大きく、`#board` の `top: 8px` ＋ 高さ 44px、`#flash` の `top: 54px`（状況チップ表示中は 78px）、`#situation` の `top: 54px`、`#pointBanner` の `top: 18%`、`#hint` の `bottom: 10px + safe-area` はいずれも既存最小構成以上の余裕を持つ。
- **検査対象は横方向に限定する。** 縦の最小 stage 幅（S = 360）は既存最小横画面の stage 幅 392px より 32px 狭い。`#flash` と `#situation` は `white-space: nowrap` ＋ `max-width: 76%` のため、S = 360 では 273.6px を超える文言が折り返さず `overflow: hidden` で切れる。
- **E2E 契約**: 最小構成と 390×844 で、`#board` / `#flash` / `#situation` / `#pointBanner` が `scrollWidth <= clientWidth` を満たし、各矩形が `#stage` 矩形の内側（左右余白 ≥ 2px）に収まる。最長文言（デュース・マッチポイントの状況チップ、得点理由トースト）で検査する。
- **超過時の対応順序**: ① 縦画面のみ `#flash` / `#situation` の `max-width` を 92% へ広げる → ② それでも超える場合は縦画面のみ `white-space: normal` とし、`#situation` を `height: auto; min-height: 20px` へ変更して 2 行を許容する。font-size の縮小、要素の非表示、文言の短縮は行わない（注意点24 の「欠陥を隠さない」）。

### 4.4 canvas のリサイズ（F-05 対応）

**1.2 版の「コード変更なし」は撤回する。**

`src/render.ts:resize()` は `canvas.clientWidth` / `clientHeight` を読む。一方 `ViewportController.schedule()` は `requestAnimationFrame` へ遅延してから `body.dataset.viewport` を書く（`src/view/orientation.ts`）。したがって `window.resize` / `visualViewport.resize` ハンドラは**変更前のレイアウト**を読み、新しい dataset と新しい stage 寸法はその後の rAF で適用される。次の resize が来なければ Renderer の `width` / `height` / `camera` / backing store は旧値のまま残る。`orientationchange` を伴わないサイズ変更（デスクトップのウィンドウリサイズ、Playwright の viewport 変更）がこの経路に該当する。既存の 250ms 再 resize は `orientationchange` 内だけなので救済しない。

恒久対策は `ResizeObserver` で canvas 自身を監視することとする。

- `Renderer` のコンストラクタで `new ResizeObserver(() => this.resize()).observe(this.canvas)` を登録する。`.stage #cv { position: absolute; inset: 0 }` により canvas は stage を満たすので、`resize()` が実際に読む要素をそのまま監視する。
- `ResizeObserver` のコールバックはレイアウト確定後・描画前に発火するため、dataset 変更 → レイアウト → 再 resize → 最初の描画フレーム、の順序が保証される。`ViewportController` と `Renderer` を相互接続する必要がない（`ViewportController` は `Renderer` より前に生成されるため、接続は構造上できない）。
- `typeof ResizeObserver === "undefined"` の環境では登録しない。既存の `window.resize` / `visualViewport.resize` 購読と `orientationchange` ＋ 250ms 再 resize は**そのまま残す**。`resize()` は冪等であり、`layerKey`（幅×高さ@dpr）が変わったときだけ静的レイヤを再生成する既存挙動を使う。
- `Renderer` へ `destroy()` を追加し、`ResizeObserver.disconnect()` と既存 3 購読の解除を行う。テスト側の順序ハーネスが購読を解除できるようにするため。

回転時に `visualViewport` のサイズ確定が遅れる端末があるため、`window.setTimeout(this.resize, 250)` は維持する（`src/render.ts:298`）。

v0.4.0 では Service Worker のキャッシュ名を `table-tennis2-v0.4.0` へ更新する。対応ブラウザでのコンソール警告を避けるため、viewport meta は共通の指定のみを使い、ソフトウェアキーボードによる表示領域の変化は既存の `visualViewport.resize` で再評価する。

### 4.6 入力・ラケット・接触

**変更なし。** 根拠：

- `src/control/paddle.ts:baseCenter()` は `stageX * width` と `stageY * height − offset * height` で、stage 矩形に対する正規化座標を使う。stage が正方形になっても式は同じ。
- `POINTER_OFFSET_TOUCH = 0.06` は stage 高さ比。S = 390 の縦画面では 23.4px で、横 844×390（390 × 0.06 = 23.4px）と同一。
- `STRIKE_MIN_DISPLACEMENT = 0.04` / `STRIKE_MIN_SPEED = 1.1` / `GESTURE_MIN_SPEED = 0.55` も stage 高さ比。S = 390 で横 844×390 と同一の px しきい値になる。S = 360 では 10% 小さい px しきい値（= わずかに出しやすい）になるが、これは横 568×320（高さ 320）で既に起きている既存の挙動範囲の内側である。
- `src/view/input-math.ts:normalizeStageX()` と `src/control/stroke.ts:normalizeStagePoint()` は canvas 矩形基準。変更不要。

### 4.7 停止理由

`src/view/suspension.ts` は変更しない。`viewportBlocked` は `isViewportBlocked()` の結果で駆動されるため、`portrait` では停止せず、`portrait-too-small` では従来どおり停止する。回転して縦 ↔ 横を跨いだときは、どちらもプレイ可能なら停止せずレイアウトだけ切り替わる。

ただし**回転時に stage 辺長が変わるため、ラリー中の回転は捕球半径[cm]を 9.12〜10.45cm の範囲で変化させる**。これは横画面内のリサイズでも既に起きる既存挙動であり、新しい保証は追加しない。回転直後に `input.reset()` を行う既存動作（`src/input.ts:reset()`）を維持する。
