## 1. 判定

**着手不可。** 必要速度フロアを追加する方向は、遠距離のpassive PUSHを回復させる点で支持できる。しかし、設計式を適用すると「維持する」と指定された既存校正テストが失敗する。新しい到達率条件にも未達例があり、補助倍率の更新契機と非変更保証の範囲も確定していない。下記4件を同じ未リリース設計書へ反映してから再レビューする。

本レビューは設計書と実装・テストの照合、および製品ソースをメモリ内だけで変換した数値検証である。v0.2.4の実装完了や実機での操作性改善を判定したものではない。

## 2. 指摘事項

### R-01 [P1] 必要速度フロアと既存PUSH校正の維持条件が両立しない

- **設計箇所**: 対象設計書 L250–262（速度フロア）、L464（既存3例・閾値維持）、L505–506（既存unit全件成功）。
- **実装根拠**: [direct-calibration.test.ts](../tests/direct-calibration.test.ts) L87–104は、品質0.85と0.25のミス率差を全4技で10ポイント以上とする。母集団は同ファイルL26–29、L63–84の3打点×400試行、LCG seed `20260805`。
- **確認結果**: 現行の関連unitは23/23成功。設計§5.2.1のフロアだけを追加し、既定の`errorScale = 1`、既存の母集団・乱数・製品intentを維持すると、PUSHは品質0.85で1,200/1,200成功、品質0.25で1,122/1,200成功となる。ミス率差は **6.5ポイント** で、既存の **10ポイント以上** を満たさない。DRIVE / CHOP / SMASHの同条件はそれぞれ27.92 / 17.75 / 35.42ポイントである。
- **影響**: 設計どおりに実装してもG1を満たせない。低品質PUSHをどの程度失敗させるべきかが未決定のまま、実装者が物理式かテスト閾値を独断で変更することになる。
- **修正方針**: PUSHの速度回復で既存の品質校正が変わることを明記し、旧閾値を維持するための式・定数を再設計するか、意図した変更としてPUSHの旧契約をsupersedeし、新しい品質別閾値を実測して確定する。他3技の閾値まで一括して緩めない。
- **再レビュー条件**: 旧母集団と遠距離母集団を分離して校正し、品質別成功数・ミス率差・採用閾値を同じスクリプトで再現できること。§9.1とG1を、その採否判断と一致させる。

### R-02 [P2] 補助倍率の設定がpointer種別の確定・変更・resetに追従しない

- **設計箇所**: 対象設計書 L323–329、L428–429。最終補助倍率はpointer種別と難易度で決まるが、`setAssistScale()`の設定契機は`newGame()` / `selectLevel()`だけである。
- **実装根拠**: [paddle.ts](../src/control/paddle.ts) L90ではpointer種別は`null`、L114–116では入力開始時に種別を取得し、L238–239とL282–300では回復・reset時に消去する。L370–373の現行`getAssistScale()`はその時点の種別から算出する。[game.ts](../src/game.ts) L284–301は入力とresetを伝達し、L253–278は`getAssistScale()`を描画に使う。既存[paddle-pose.test.ts](../tests/paddle-pose.test.ts)にはfollow期間中の種別切替とreset後のassist消去の試験がある。
- **影響**: 試合開始時にはまだtouch / mouse / penが分からない。開始時に`null`を保存すれば最初の入力後も補助輪郭が表示されず、仮のpointer種別を選べば異なる端末で輪郭と判定の倍率がずれる。試合中にtouchからmouseへ切り替わった場合も保存値が古いままになる。接触側でも保存値を使う実装なら、判定自体の倍率が誤る。
- **修正方針**: 難易度係数だけを保持し、現在のpointer種別と組み合わせて描画・判定に共通の最終倍率を返すか、pointer種別が確定・変更・失効する全契機で最終倍率を更新する。pointer未確定時、release猶予中、猶予失効後、reset後の`null`契約を明示する。
- **再レビュー条件**: 全難易度で「初回入力」「touch→mouse/pen」「release→再入力」「reset→再入力」を通し、描画値・debug値・`sweptPaddleContact()`入力が一致する結合テストを設計へ追加する。固定倍率30組のU-C2だけではライフサイクルを検証できない。

### R-03 [P2] U-A1の90%以上は指定打点の一部で未達で、再現に必要な入力も欠けている

- **設計箇所**: 対象設計書 L88–96（測定条件）、L385–391（修正後の到達率）、L473（U-A1）。
- **確認条件**: `buildShotIntent()`によるpassive PUSH、`from = {x:0, y:10, z:-178}`、incoming spin / sideとも0、接触offset 0、品質0.40、`errorScale = 1`。U-A1指定のmulberry32 seed `20260903`を各セルで初期化し、各400試行。式は§5.2.1の速度フロアをそのまま適用した。
- **確認結果**: 成功は **353/400 = 88.25%** で、U-A1の全接触面90%以上に届かない。6接触面×3高さ×3品質の54セルでは、この1セルが未達だった。
- **影響**: 設計書は「全定数が実測確定」とする一方、U-A1にはincoming spin / side、狙い、難易度・誤差係数、seedの再初期化単位がない。実装者が標準的な無回転入力を選ぶと閾値に届かず、別の入力を選べば結果が変わる。§3.1のAI統計もサンプリング分布・`lastBounceZ`・player位置・採用除外条件・分位点の算出法が未定義であり、同じseedだけでは§6の統計を再現できない。
- **修正方針**: 表ごとの生成器または完全な入力定義・実行コマンドを保存する。U-A1は上記セルを含む明示的な母集団で再測定し、必要なら物理定数か目標率を再設計する。incoming spinが変わる製品経路は、基準となる無回転校正と分けて検査する。
- **再レビュー条件**: 第三者が保存された生成器で同じ成功数を再現でき、全セルが確定済み閾値を満たすこと。§6の93%という代表値だけで、`y=10`を含むU-A1の全セル合格を代替しない。

### R-04 [P2] 「上級・対象外モデルは不変」と新しい誤差係数が矛盾する

- **設計箇所**: 対象設計書 L176、L274、L281–298、L447–448、L466、L478、L509。
- **実装根拠**: [physics.ts](../src/physics.ts) L341–459では`solveShot()`の誤差処理は速度モデルの分岐後に全モデルへ適用される。設計の上級`precision = 0.45`は、`pace = 1`でもDRIVEだけでなくSTOP / FLICK / LOBの最終速度ベクトルを変える。direct側も初級・中級の`errorScale`が全モデルの最終弾道を変える。
- **確認結果**: AI DRIVE、`from={x:0,y:26,z:178}`、aimX=25、depth=90、quality=0.8、extraError=0、全乱数0.7では、現行`vz=-899.858873`に対し`pace=1, precision=0.45`は`vz=-891.675007`。STOP / FLICK / LOBも同条件で不一致だった。したがって、上級の製品パラメータを使ってU-B1の「全要素一致」を要求することはできない。
- **関連する母集団の変化**: 既存[reachable-contact.test.ts](../tests/reachable-contact.test.ts)へ新pace / precision / missと難易度別assistを注入すると採用件数は **30,362→30,869** になった。最小縦marginはfine **2.659px**、touch **6.254px** と、今回の数値検証では到達不能は増えなかった。ただし、旧母集団の件数・弾道がそのまま不変という説明は成立しない。
- **影響**: 意図した難易度変更まで回帰として判定するか、逆に既定引数だけの試験を上級製品経路の不変証明として扱うことになる。§8の「弾道が変わらない」、U-B1、G1の文言が同時に満たせない。
- **修正方針**: 不変の対象を「基準速度モデル・乱数順」「`pace=1, precision=1`の旧solver互換」「構造フロア単独で`drawn >= need`となる入力」に限定して記述する。上級precision / miss、初級・中級errorScaleによる最終弾道の変化は意図した変更として明記し、全プロファイルを適用した到達性は別の回帰基準として再測定する。legacy不変も`solveShot(direction=+1, pace=1, precision=1)`のプレイヤー側に範囲を限定する。
- **再レビュー条件**: 旧互換の負の対照と、新プロファイルの製品経路テストが区別され、それぞれの比較対象・引数・母集団が一意であること。§4.3、§8、§9、G1/G2で非変更範囲を統一する。

## 4. R-01 / R-03の再現手順

作業ディレクトリを`D:\my-app2\sitar\table-tennis2`とし、以下のJavaScriptをNode.js 24の`node --input-type=module`へ標準入力する。PowerShellでは`@'`と`'@ | node --input-type=module`で囲める。ファイルを書き換えず、現行関数と速度フロア追加後の関数を比較する。

```js
import fs from "node:fs";
import { pathToFileURL } from "node:url";
import { stripTypeScriptTypes } from "node:module";

const base = pathToFileURL(process.cwd() + "/");
const dataUrl = (s) => "data:text/javascript;base64," + Buffer.from(s).toString("base64");
const readJs = (p) => stripTypeScriptTypes(fs.readFileSync(p, "utf8").replaceAll("\r\n", "\n"));
let physics = readJs("src/physics.ts");
const before = "speed = lerp(shot.speed.sp[0] * 0.72, shot.speed.sp[1], intent.power);";
if (physics.split(before).length !== 2) throw new Error("対象ソースがレビュー時から変わっています");
physics = physics.replace(before,
  "speed = Math.max(lerp(shot.speed.sp[0] * 0.72, shot.speed.sp[1], intent.power), solveSpeed(from, targetX, targetZ, 0.55, spin, side).speed * 1.03);");
physics = physics.replaceAll('"./config.ts"', JSON.stringify(new URL("src/config.ts", base).href));
const proposedUrl = dataUrl(physics);
const proposed = await import(proposedUrl);
const { buildShotIntent } = await import(new URL("src/control/shot-intent.ts", base));

let calibration = readJs("tests/direct-calibration.test.ts")
  .split('test("v0.2.1 fixed population:')[0];
calibration = calibration.replace(/"(\.\.\/src\/[^\"]+)"/g, (_, p) => JSON.stringify(
  p.endsWith("/physics.ts") ? proposedUrl : new URL(p, new URL("tests/", base)).href));
const { cohort } = await import(dataUrl(calibration + "\nexport { cohort };"));
const high = cohort("PUSH", 0.85, 20260805);
const low = cohort("PUSH", 0.25, 20260805);
console.log({ id: "R-01", high, low, missGap: high.landed / high.total - low.landed / low.total });

function mulberry32(seed) {
  return () => {
    let t = seed += 0x6D2B79F5;
    t = Math.imul(t ^ t >>> 15, t | 1);
    t ^= t + Math.imul(t ^ t >>> 7, t | 61);
    return ((t ^ t >>> 14) >>> 0) / 4294967296;
  };
}
const failures = [];
for (const z of [-30, -60, -90, -120, -150, -178]) {
  for (const y of [10, 17, 26]) {
    for (const q of [1, 0.7, 0.4]) {
      const random = mulberry32(20260903);
      const from = { x: 0, y, z };
      const intent = buildShotIntent({
        contactOffsetX: 0, contactOffsetY: 0,
        contactQuality: q, timingQuality: q, ballHeight: y,
        strikeMetrics: { vx: 0, vy: 0, speed: 0, displacement: 0,
          directionX: 0, directionY: 0, verticality: 0, curvature: 0,
          age: 0, active: false },
      }, -70);
      let landed = 0;
      for (let i = 0; i < 400; i++) {
        const shot = proposed.solveDirectPlayerShot({
          from, incoming: { spin: 0, side: 0 }, intent, random,
        });
        if (!shot) throw new Error("非有限解");
        const land = proposed.simLand({ ...from, ...shot });
        if (!land.net && land.z > 0 && proposed.onTable(land.x, land.z)) landed++;
      }
      if (landed < (q >= 0.7 ? 400 : 360)) failures.push({ z, y, q, landed, total: 400 });
    }
  }
}
console.log({ id: "R-03", failures });
```

期待出力はR-01の`high.landed=1200`、`low.landed=1122`、`missGap≈0.065`、R-03の未達セル`{z:-178,y:10,q:0.4,landed:353,total:400}`。TypeScript除去APIのExperimentalWarningは検証プロセスの通知であり、ゲームのconsole warningではない。
