## 1. 目的・背景

### 1.1 ユーザー報告

「プレイ面で操作が難しく、ラリーが継続しにくい」。

### 1.2 調査で確定した原因

現行コードを製品経路のまま実測した結果、報告は操作感の問題ではなく、**返球が物理的に相手コートへ届かない構造的欠陥**が主因であると確定した。測定条件と数値は §3 に示す。

| ID | 確定した原因 | 影響 |
|---|---|---|
| R1 | プレイヤーの接触面 `solveContactPlane(ball,"P")` は実 AI 返球の **99% で最遠 clamp `-178`** になる。台端から 41cm 後方 | 返球距離が常に 266cm 前後になる |
| R2 | `solveDirectPlayerShot()` の passive PUSH 速度 `lerp(430×0.72, 510, 0.12) = 334 cm/s` は、その距離を**到達不能**。相手コート到達率 **0%** | 「置くだけ返球」は必ず自陣に落下して失点する |
| R3 | 同じ理由で active PUSH（power 0.5）と CHOP（ツッツキ）も **到達率 0%** | 上方向の速いフリック（DRIVE / SMASH）以外に有効な返球手段が存在しない |
| R4 | AI 返球の飛行時間・画面速度が**難易度でほぼ変わらない**（返球猶予 p50 = 0.387 / 0.383 / 0.283 秒） | 初級でも上級と同じ反応速度を要求される |
| R5 | AI の 1 球あたり自滅率が**難易度とともに増加**する（5.63% / 11.28% / 14.43%）。難易度逆転 | 初級ほど AI がミスせず、上級ほど AI が勝手に自滅する |

R2 / R3 は v0.2.0 で direct 経路にのみ導入した速度下限 `sp[0] × 0.72` に由来する。**legacy 経路（`?controlModel=legacy`）は同じ接触面から PUSH / CHOP / DRIVE いずれも到達率 100%** であり、この欠陥は direct 経路固有である（§3.3）。

R4 / R5 は `LEVELS` の各値が AI の位置取り・技選択・狙い幅にしか効かず、**球速・AI 精度・プレイヤー側の操作難度のいずれも難易度で変化しない**ことに由来する。

### 1.3 目的

1. direct 経路のすべての技が、実ゲームで発生する接触面から相手コートへ到達し得る状態にする。
2. 「置くだけ返球（passive PUSH）」を、成功が既定でミスが接触品質に依存する、実用的な防御手段にする。
3. 初級 / 中級 / 上級を、返球猶予・接触補助・返球誤差・AI 自滅率の 4 軸すべてで単調に分離する。
4. 上級の**操作契約**（補助倍率・品質下限・プレイヤー誤差・返球猶予・画面速度）を v0.2.3 から変えない。AI の精度だけは意図して上げる。

## 3. 現状分析（測定結果）

### 3.1 測定条件

すべて現行 `master`（`17d7507`）のソースを製品経路のまま呼び出して測定した。**第三者が同じ数値を再現できるよう、生成器を `scripts/measure-play-balance.mjs` として実装時にリポジトリへ保存する**（§7 の 11-7）。以下はその生成器の仕様である。

**生成器 A: AI 統計（§3.4 / §6 の AI 側指標）**

- 乱数: mulberry32、seed `20260903`。**1 難易度につき 1 回だけ初期化**し、母集団生成・AI 判断・弾道解決で同じ列を消費する（セルごとの再初期化はしない）。
- 入射球の母集団（1 試行につき順に消費）: `x = (r()×2−1)×45`、`y = 16 + r()×26`、`z = 150 + r()×28`、`lastBounceZ = 40 + r()×70`、AI ラケット `state.x = x + (r()×2−1) × LEVELS[level].reach × 0.7`、`playerX = (r()×2−1)×60`。固定値は `vx = 0`、`vy = −120`、`vz = 300`、`spin = 0.2`、`side = 0`、`hitter = "P"`、`bounces = 1`。
- 経路: `OpponentAi.decideShot()` → `solveShot()` → `simLand()` → `solveContactPlane(ball,"P")` → `integrate()` の実接触経路。
- 除外条件: `decideShot()` が `null`（AI が届かない）を返した試行は母集団から除外し、自滅率の分母にも入れない。着地が「ネット / 台外 / 自陣」の試行は**自滅としてカウントし、飛行時間・画面速度の統計からは除外**する。プレイヤー接触面へ到達しない試行も同様に統計から除外する。
- `blunder` は **`OpponentAi.decideShot()` が返した値をそのまま使う**（製品経路）。外部で再抽選しない。再抽選は乱数列を製品からずらすため採らない。
- §3.4 の現行値は、`LEVELS.miss` を旧値（0.11 / 0.08 / 0.02）へ戻したうえで `--baseline`（`pace = 1` / `precision = 1`）を付けて実行すると再現できる。
- 分位点: 昇順ソート後 `s[floor(p × n)]`（線形補間なし）。
- 画面指標の参照 viewport: 640 × 360（`createProjectionCamera` / `projectWorldPoint`）。奥行き窓は `2 × contactDepthTolerance(vz) / |vz|`。
- 試行数: N = 6,000（§3.4 / §6）、N = 8,000（自滅率の候補比較）。

**生成器 B: プレイヤー返球（§3.2 / §6 の到達率、U-A1）**

- 乱数: mulberry32、seed `20260903`。**セル（接触面 z × 打点 y × 品質 q の組）ごとに再初期化**し、各セル 400 試行。
- 入力: `from = { x: 0, y, z }`、`incoming = { spin: 0, side: 0 }`（無回転基準）、`contactOffsetX = contactOffsetY = 0`、`ballHeight = y`、`lastBounceZ = −70`、`strikeMetrics` は全要素 0 かつ `active: false`（passive 経路）。
- 経路: `buildShotIntent()` → `solveDirectPlayerShot()` → `simLand()`。`intent` はセルごとに 1 回生成して 400 試行で共有する。
- 成功判定: `!land.net && land.z > 0 && onTable(land.x, land.z)`。
- `errorScale` は難易度別の値を使う。難易度非依存の表（§3.2）では `errorScale = 1`。

`incoming.spin ≠ 0` を含む製品経路は基準校正と分離し、§9.2 U-D1 で別に検査する。

### 3.2 プレイヤー返球の到達率（現行）

`solveDirectPlayerShot()` の着地が「ネットを越え、台上で、相手コート（z > 0）」となる割合。打点 `y = 17〜20`、`x = 0`。

| 技 / power | 接触品質 | z=-30 | z=-60 | z=-90 | z=-110 | z=-150 | z=-178 |
|---|---|---|---|---|---|---|---|
| passive PUSH（置くだけ） | 1.00 | 100% | 100% | 100% | **0%** | **0%** | **0%** |
| passive PUSH | 0.40 | 100% | 100% | 92% | 26% | **0%** | **0%** |
| active PUSH power 0.5 | 1.00 | 100% | 100% | 100% | 100% | **0%** | **0%** |
| active CHOP power 0.5 | 1.00 | 100% | 100% | 100% | 100% | 100% | **0%** |
| active DRIVE power 0.3 | 1.00 | 100% | 100% | 100% | 100% | 100% | 100% |
| active DRIVE power 1.0 | 0.40 | 88% | 76% | 68% | 67% | 68% | 67% |

実接触面の分布は次のとおりで、上表の左 3 列はほぼ発生しない。

| 難易度 | 接触面 z の p50 | z ≤ -110 の割合 | z ≤ -150 の割合 | 打点 y の p50 |
|---|---|---|---|---|
| 初級 | -178 | 99.5% | 97.2% | 20.6cm |
| 中級 | -178 | 98.9% | 93.3% | 17.4cm |
| 上級 | -178 | 99.4% | 95.3% | 14.9cm |

**結論**: 実ゲームで発生する接触面では、passive PUSH・active PUSH・CHOP の到達率は 0% である。

必要速度を `solveSpeed()` で逆算すると、`z=-178, y=17` から `targetZ=88` へは仰角 0.55rad で **508 cm/s** を要する。PUSH の速度帯は direct 経路で 334〜510 cm/s、CHOP は 284〜470 cm/s であり、帯の上端でようやく足りるか、まったく足りない。

### 3.3 legacy 経路との差

`solveShot(direction = +1)` を通る legacy 経路の同条件の到達率。

| 技 | z=-60 | z=-110 | z=-150 | z=-178 |
|---|---|---|---|---|
| PUSH | 100% | 100% | 100% | 100% |
| CHOP | 100% | 100% | 100% | 100% |
| DRIVE | 100% | 100% | 100% | 100% |
| LOB | 100% | 95% | 91% | 88% |

legacy の PUSH は `sp[0] = 430` をそのまま下限に使う。direct 経路だけが `sp[0] × 0.72 = 310` を下限に持つ。**欠陥は direct 経路固有であり、legacy 経路は変更しない。**

### 3.4 難易度分離の現状

| 指標（AI 実接触経路 N=6,000） | 初級 | 中級 | 上級 | 判定 |
|---|---|---|---|---|
| AI 1 球あたり自滅率 | 5.63% | 11.28% | 14.43% | **逆転**（難しいほど AI が自滅） |

### 3.5 既存テストが欠陥を検出できなかった理由

`tests/direct-calibration.test.ts` の固定母集団は 3 例すべて `z: -100` を打点にしている。§3.2 のとおり `z = -100` は到達率が 100% から 0% へ落ちる境界のすぐ手前であり、実ゲームの打点 `z = -178` を含んでいない。これは Obsidian 注意点 5「代表打点テストが実ゲームの遠距離打点を含んでいなかった」の再発である。本書では固定母集団に実接触面の端を必ず含める（§9.2）。

## 4. 全体方針

### 4.1 二層の修正

1. **構造層（全難易度共通）** — 到達不能を除去する。`absolute` 速度モデルに、打点から狙い着地点までの必要速度をフロアとして与える。フロアは `Math.max` の片側制約であり、速度を下げない。既に成立していた弾道の狙い・回転・誤差式は変えない。
2. **難易度層** — 到達可能になった上で、AI の球速と精度、プレイヤーの接触補助と誤差を難易度で分離する。

### 4.2 採用しなかった代替案

| 代替案 | 却下理由 |
|---|---|
| passive の `power` を 0.12 → 0.85 へ引き上げる | 速度が距離に依存しない問題は残る。浅い接触面では過剰速度になり、置くだけ返球が強打になる |
| `CONTACT_PLANE_FAR` を 178 → 132 へ縮める | 実測で打点 y が 17.4cm → 9.4cm へ**低下**し、条件が悪化する。接触面は結果であって原因ではない |
| AI の絶対速度に難易度倍率を直接掛ける（`speed × pace`） | 実測で AI 返球が相手コートへ届かなくなり、初級で AI 自滅 92.9% となった。`solveAngle()` の仰角上限 0.85 では距離を稼げない |
| `LEVELS.miss` だけを増減する | §3.4 のとおり基礎誤差に埋もれ、単独では自滅率の逆転を解消できない |

### 4.3 非変更の範囲（厳密な定義）

「変わらない」と主張できるのは次の 3 つに限る。それ以外は**意図した変更**であり、回帰ではない。

| # | 不変の対象 | 成立条件 |
|---|---|---|
| N-1 | 速度モデルの構造と乱数消費順 | 全経路・全難易度で無条件（§5.4） |
| N-2 | 旧 solver との数値一致 | `solveShot(pace = 1, precision = 1)` および `solveDirectPlayerShot(errorScale = 1)` の**既定引数呼び出し**に限る |
| N-3 | 構造フロアの無効化 | `drawn ≥ need` を満たす入力に限る。技種別では決まらない（§5.2.1） |

**上級の製品パラメータは N-2 を満たさない。** `aiPrecision = 0.45` は `solveShot()` の誤差適用が速度モデル分岐の**後**にあるため、`pace = 1` でも DRIVE だけでなく STOP / FLICK / LOB / SMASH の最終速度ベクトルを変える。実測（`from = {x:0, y:26, z:178}`、aimX 25、depth 90、quality 0.8、extraError 0、全乱数 0.7）:

| 技 | `precision = 1` の vz | `precision = 0.45` の vz |
|---|---|---|
| DRIVE | -899.858873 | -891.675007 |
| STOP | -447.327484 | -443.866604 |
| FLICK | -703.447580 | -697.042068 |
| LOB | -298.663878 | -298.635056 |
| SMASH | -1321.520437 | -1310.347614 |

同様に、初級・中級の `playerErrorScale` は direct 側の全モデルの最終弾道を変える。

**上級で維持するのは操作契約と体感指標**である。`assistScale = 1.00` / `contactQualityFloor = 0.40` / `playerErrorScale = 1.00` は v0.2.3 と同値であり、返球猶予 p50 は 0.288s → 0.279s、画面速度 p50 は 2,926 → 3,032 px/s に留まる。上級で意図して変わるのは AI の精度（`aiPrecision` / `miss`）だけである。

legacy 経路の不変も `solveShot(direction = +1, pace = 1, precision = 1)` のプレイヤー側呼び出しに限定する。

`tests/reachable-contact.test.ts` の母集団は `miss` 変更により採用件数が変わる。設計レビュー時の暫定実測は **30,362 件 → 30,869 件**、最小縦 margin は fine 2.659px / touch 6.254px（いずれも正、到達不能 0 件）。件数は実装時に再測定して確定し、**受入条件は件数一致ではなく「到達不能 0 件かつ最小 margin > 0」**とする（§9.1）。

## 5. 詳細仕様

### 5.1 難易度別プロファイル `LEVEL_PLAY`

`src/config.ts` に新設する。`LEVELS` は既存の意味（AI の位置取り・技選択・狙い幅）を保ち、本プロファイルは球速・精度・操作補助だけを担う。

```ts
export interface LevelPlayProfile {
```

### 5.2 必要速度フロア（構造層）

`src/physics.ts` に純粋関数を追加する。**乱数を消費しない。**

```ts
export function minimumViableSpeed(
  from: Pick<BallVector, "x" | "y" | "z">,
  targetX: number,
  targetZ: number,
  spin: number,
  side: number,
  margin: number,
): number {
  return solveSpeed(from, targetX, targetZ, SHOT_MIN_SPEED_ELEV, spin, side).speed * margin;
}
```

#### 5.2.1 `solveDirectPlayerShot()` の `absolute` 分岐

```
現行: speed = lerp(sp[0] × 0.72, sp[1], power)
新規: speed = Math.max(
        lerp(sp[0] × 0.72, sp[1], power),
        minimumViableSpeed(from, targetX, targetZ, spin, side, PLAYER_SHOT_SPEED_MARGIN),
      )
```

- `targetX` / `targetZ` / `spin` / `side` は現行の算出をそのまま使う。フロアは同じ狙いに対する必要速度である。
- `solveAngle()` へ渡す速度だけが変わる。仰角・方位の解法、`ensureNetClear()`、誤差適用、`arc` / `touch` モデルは変更しない。
- **片側制約**であり、`drawn ≥ need` の入力では現行と全要素一致する。この不変は**技種別ではなく述語 `drawn ≥ need` で成立する**。DRIVE power 1.0 と SMASH power 1.0 は検査した 9 打点すべてで一致するが、**DRIVE power 0.3 は `z = -178, y = 10` でフロアが binding し、現行と一致しない**。U-A3 はこの述語で母集団を分割して検査する（§9.2）。

`solveSpeed()` の探索範囲は `[250, 1300]` である。必要速度がこの上限を超える打点では 1300 で飽和し、フロアは実質無効になる。§3.2 の最深接触面での必要速度は 508 × 1.16 = 590 cm/s であり上限に対して十分な余裕があるが、飽和境界は §9.2 U-A4 で固定する。

#### 5.2.2 `solveShot()` の `absolute` 分岐（AI 側）

```
現行: speed = 抽選速度 drawn（SMASH は打点補正後）
新規: need  = minimumViableSpeed(from, targetX, targetZ, spin, side, AI_SHOT_SPEED_MARGIN)
      speed = pace >= 1 ? drawn : lerp(Math.min(need, drawn), drawn, pace)
```

- `pace = 1`（上級）では `solveSpeed()` を呼ばず、現行と**バイト単位で同一の弾道**になる。
- `Math.min(need, drawn)` により、抽選速度がもともと必要速度を下回る場合は `lerp(drawn, drawn, pace) = drawn` となり、pace は速度を下げない。これが「pace を掛けると AI が届かなくなる」（§4.2）を構造的に防ぐ。
- `pace = 0` でも速度は必要速度 × 1.05 を下回らない。

#### 5.2.3 `PLAYER_SHOT_SPEED_MARGIN = 1.16` の確定根拠

フロアは passive PUSH の到達不能を解消すると同時に、**低品質 PUSH のミスも消す**。これは Obsidian 注意点 6「後付け保証が接触品質によるミスを消した」と同じ失敗であり、既存契約で検出される。

`tests/direct-calibration.test.ts` は品質 0.85 と 0.25 のミス率差を全 4 技で 10 ポイント以上と定めている（母集団: 3 打点 `z = -100` × 400 試行、LCG seed `20260805`、計 1,200 試行）。同母集団で余裕率を振った実測値。

| 余裕率 | DRIVE | CHOP | PUSH | SMASH | 判定 |
|---|---|---|---|---|---|
| 現行（フロアなし） | 0.2792 | 0.1750 | 0.3708 | 0.3542 | 基準 |
| 1.03 | 0.2792 | 0.1775 | **0.0650** | 0.3542 | PUSH 不合格 |
| 1.10 | 0.2792 | 0.2083 | **0.0875** | 0.3542 | PUSH 不合格 |
| 1.14 | 0.2792 | 0.2333 | 0.1042 | 0.3542 | 合格（余裕 0.4pt） |
| **1.16** | **0.2792** | **0.2408** | **0.1142** | **0.3542** | **採用（余裕 1.4pt）** |
| 1.20 | 0.2792 | 0.2717 | 0.1267 | 0.3542 | 合格だが浅い接触面が劣化 |

同時に `highRate`（品質 0.85 の台内率）は 1.16 で 4 技とも 1.0000 であり、既存条件（SMASH 0.70 以上 / 他 0.85 以上）を満たす。

**したがって既存 4 技の閾値・母集団・seed は一切変更しない。** 余裕率を上げると `solveAngle()` がより低い仰角を選び、弾道が平坦になって誤差が着地へ効きやすくなるため、品質差が回復する。

1.18 以上を採らない理由: 最悪セルが最深打点 `z = -178` から**最浅打点 `z = -30` へ移り**（1.18 で中級 81.75%、1.20 で 66.75%）、近い球を過剰速度でアウトにする。1.16 は最悪セルが「深く低い球」という本来難しい状況に留まる最大値である。

##### 採用しなかった機構: 接触品質による速度損失

`speed × lerp(k, 1, contactQuality)` で低品質の速度を落とし、品質差を回復させる案を測定した。物理的には自然だが、**高品質側の速度も落ちるため CHOP の品質差が崩壊する**（`k = 0.94` で 0.1775 → 0.0650、`k = 0.90` で 0.0090）。スコープ外の技を壊すため却下する。

#### 5.2.4 誤差スケール

```
solveShot():
  現行: error = shot.err + (1 - contactQuality) × 0.055 + extraError
  新規: error = (shot.err + (1 - contactQuality) × 0.055) × precision + extraError

solveDirectPlayerShot():
  現行: error = shot.err + qualityLoss² × 0.16
  新規: error = (shot.err + qualityLoss² × 0.16) × errorScale
```

`extraError`（AI blunder 0.075）にはスケールを掛けない。明示的なミスと通常ショットの保証範囲を分離するためである。

| `solveShot()` | `pace: number` | `1` | `Game.makeShot()`。AI は `LEVEL_PLAY[level].aiPace`、legacy プレイヤーは `1` |
| `solveShot()` | `precision: number` | `1` | AI は `LEVEL_PLAY[level].aiPrecision`、legacy プレイヤーは `1` |

#### 5.3.1 補助倍率のライフサイクル契約

最終補助倍率は **pointer 種別と難易度の積**であり、pointer 種別は試合開始時点では未確定で、入力開始・切替・release 猶予失効・reset で変化する。したがって**最終倍率を保存してはならない**。`PaddleController` が保持するのは難易度係数だけとする。

```ts
// PaddleController
private levelAssistScale = 1;

public setLevelAssistScale(scale: number): void {
  this.levelAssistScale = scale;
}

public getAssistScale(): number | null {
  if (!this.pointerType) return null;                       // 現行の null 契約を維持
  const base = this.pointerType === "touch"
    ? CONTACT_ASSIST_TOUCH
    : CONTACT_ASSIST_FINE;
  return base * this.levelAssistScale;                      // 変更点はこの乗算だけ
}
```

- `pointerType` の取得・消去の契機（`applyInput()` の入力開始、`advanceFrame()` の recover 完了、`reset()`）は**現行のまま変更しない**。
- `Game` は `newGame()` と `selectLevel()` で `setLevelAssistScale(LEVEL_PLAY[level].assistScale)` を呼ぶ。難易度係数はゲーム設定であり、pointer ライフサイクルと独立している。
- **描画・debug・判定はすべて `getAssistScale()` を単一ソースとする。** `Game.directPlayerContact()` は `sweptPaddleContact()` の `assistScale` にこの戻り値を渡す。`null` の場合は接触判定を行わない（`sweptPaddleContact()` 側の既存 `pointerType === null` ガードと同じ結果になる）。
- `RenderScene.directPaddleAssist` の生成条件（`getAssistScale() !== null`）は変更しない。

これにより次が保証される。

| 局面 | `pointerType` | `getAssistScale()` | 補助輪郭 |
|---|---|---|---|
| 試合開始直後（入力なし） | `null` | `null` | 非表示。接触不成立 |
| 初回入力後 | 確定 | base × 難易度係数 | 表示。判定と一致 |
| touch → mouse / pen 切替 | 新種別 | 新 base × 難易度係数 | 即時追従 |
| release 猶予中（follow） | 保持 | 保持値 | 表示継続 |
| 猶予失効 → recover 完了 / reset | `null` | `null` | 非表示 |

`src/utils.ts` への `contactAssistScale()` 追加は不要になるため行わない。

### 6.1 置くだけ返球（passive PUSH）の到達率

**製品で実際に到達しうる接触品質**、すなわち各難易度の `contactQualityFloor` と `playerErrorScale` を適用した実測（生成器 B、接触面 6 × 打点高さ 3 = 18 セル × 400 試行 = 7,200 試行）。品質 0.25 は品質下限 0.40 により**製品では発生しない**ため、代表値には使わない。

|---|---|---|---|---|---|
| 初級 | 0.55 | 0.60 | **100.0%** | **100.0%** | 全セル 100% |
| 中級 | 0.47 | 0.85 | **98.6%** | **91.0%** | z=-178, y=10 |
| 上級 | 0.40 | 1.00 | **91.4%** | **75.3%** | z=-178, y=10 |

置くだけ返球は初級で確実に返り、上級では最深・最低打点で 4 回に 1 回失敗する。到達率は難易度と品質の双方に対して単調であり、「常に成功帯へ入る」保証にはしない（Obsidian 注意点 6）。最悪セルが最深かつ最低の打点であることは、難しい状況ほど失敗しやすいという意図と一致する。
