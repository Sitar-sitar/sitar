## 1. 結論

### 判定: 着手保留（設計修正後に GO）

設計の方向性は良く、特に以下は適切である。

- view 層中心に変更範囲を閉じる方針
- カメラ・物理・AI・接触判定・乱数消費順を不変とする契約
- 描画の静的キャッシュ化による性能予算の確保
- `prefers-reduced-motion`、色以外の情報提示、ロールバック方針
- 単体 / E2E / design-qa / 公開確認まで含む受入設計

一方、前提コミットの実装と設計書を突き合わせると、実装前に直すべき重大な矛盾が 3 件、重要な不整合が多数ある。特に以下 3 件は、現行設計のまま実装すると「実装できない」「受入条件を正しく判定できない」「表示が実際のゲーム挙動と食い違う」のいずれかが発生するため、Phase 12 着手前に設計書を修正すべきである。

1. ゲーム最終得点では `phase` が同一 `point()` 呼び出し内で `over` になるため、`phase === "point"` を前提とした死球残留が成立しない。
2. v0.2.4 には `renderMsP95` 計測機構が存在しないため、「実装着手前に `cf89521` の dataset を読む」という性能ベースライン手順は実行不能。
3. サーブ着地帯の測定母集団が実際のプレイヤーサーブ入力範囲を覆っておらず、さらに製品側には長さの fallback があるため、選択中の帯が実際のサーブ長と一致する保証がない。

## 3. P0：実装前に必ず設計修正が必要

### P0-01 最終得点時に「死球残留」が成立しない

- **設計**: §5.4.4 は `phase === "point"` のとき死球を描画し、`pointTimer` で 0.5 秒保持 + 0.75 秒フェード、`POINT_INTERVAL = 1.25` 維持を前提にしている。
- **現行実装**: `Game.point()` は `state.phase = "point"`、`state.pointTimer = POINT_INTERVAL`、HUD 更新の後、`isGameOver(...)` が真なら**同じ関数呼び出し内で `state.phase = "over"`** とする。`pointTimer` の減算は `tick()` の `phase === "point"` のときだけ行われる。
- **問題**: ゲームを決める最終得点では次の描画フレームまでに `phase` は既に `over` である。`phase === "point"` だけで死球を描くと、最も重要な最終得点だけ死球が表示されない。単純に `over` でも描画すると `pointTimer` が減らないため alpha が進まず、フェードが成立しない。
- **必須修正案**: 死球は `GameState.pointTimer` と `phase` に直接依存させず、`point` の視覚イベントから Renderer 側に得点時の最終 `x / y / z` と `simulationTime`（必要なら理由）をスナップショットし、Renderer 管理の effect として寿命を持たせる。ゲームルール・タイミングを変更せず、最終得点でも同じ表示ができる。
- **追加すべきテスト**: E-V6 通常得点で死球が表示され所定時間後に消える、E-V7 ゲーム終了得点でも死球が表示される、`over` 遷移後に effect が永続化しないこと。

### P0-02 性能ベースラインの採取手順が実行不能

- **設計**: §9.5 は実装着手前に `cf89521` を起動し `?debugInput=1` の `body.dataset.renderMsP95` から v0.2.4 の性能を取得するとしている。
- **現行実装**: 前提コミットの `Renderer` には `renderMsP50` / `renderMsP95` / `effectsLive` を計測・公開する処理は存在しない。これらは v0.3.0 で新設する仕様である。
- **問題**: 基準版に存在しない観測点を基準版から読む手順になっており、G1 の「v0.3.0 ≤ v0.2.4」を設計書記載の手順では再現できない。
- **必須修正案**: 推奨は外部計測。Playwright から `requestAnimationFrame` / Performance API を使った計測 harness を注入し、同一 harness を `cf89521` と v0.3.0 の両方へ適用する（基準版コードを変更しない、同一測定器で比較できる、計測機能追加自体のオーバーヘッドを除外できる）。代替はベースライン専用の一時ブランチに計測コードだけを入れる方法だが、再現性・監査性は外部 harness の方が高い。
- **あわせて修正すべき点**: 「AI サーブ放置で 10 秒間のラリー」という条件は不適切。プレイヤーが返球しなければラリーは短時間で終了し、新規エフェクトを十分に負荷できない。最低でも「通常描画性能（同一の安定場面を連続描画）」と「演出ストレス性能（contact / bounce / net / smash が一定頻度で発生する決定論シナリオ）」の 2 シナリオを分けるべき。

### P0-03 サーブ着地帯が実挙動と一致する保証がない

- **設計**: 測定スクリプトはサーブ原点 x `-40, 0, 40`、aimX `-40, -20, 0, 20, 40`、9 球種 × 3 長さ、`solveServe()` が `ok` のものだけ採用して `SERVE_ZONE_Z` を作る。
- **現行実装**: 実際のプレイヤーサーブは `ball.x = player.x * 0.5`、`aim = player.x * 0.6 + flick.vx * 40`。`PADDLE_LIMIT = 104` のためフリックなしでも原点 x は最大およそ ±52、aim は最大およそ ±62.4 となり設計書の測定範囲を外れる。さらに `findServeSolution()` は指定条件で解が得られないと aim を 0 に、次に**指定 length を `"middle"` に** fallback する。
- **問題**: UI は `selectedServeLength` の帯を表示するが、製品側の実サーブは条件により middle へ fallback できる。「短い」の帯を表示した直後に実際には middle のサーブになる可能性を設計上排除できていない。測定スクリプトは `ok` だけを集めるため失敗率を隠してしまう。
- **必須修正案**: 測定条件を製品の実入力 envelope と一致させる。`player.x` の到達範囲、`flick.vx` の現実的 / 最大入力範囲を網羅し、各条件で「requested length のまま解けたか」を記録する。fallback 発生率を 0 にできることを受入条件にするか、UI を「目安」と明示する。各難易度の既存 `serveErr` を含む誤差後着地点も Monte Carlo で確認する。
- **U-V8 の修正**: 「`ok` な解だけから帯を再計算して定数と一致」では不十分。母集団全件数、requested length 成功率、fallback 件数、selected length と resolved length の一致率、誤差適用後の包含率も assert する。

## 4. P1：高リスクの仕様矛盾・検出力不足

### P1-01 静的 L0 と「照明の脈動」が矛盾

- §5.1.2 は照明を L0 静的 backdrop に置き `layerKey` 変化時しか再描画しないが、§5.1.4 / §5.11.1 は照明の微かな脈動を `performance.now()` で動かすとしている。静的キャッシュ内の照明は毎フレーム変化できない。
- **修正**: 照明脈動を削除して完全静的にするか、静的ハローとは別の動的光 overlay をレイヤ順へ追加するか、いずれかに明記する。性能重視なら前者を推奨。

### P1-02 `serve` と Feedback の前提が現行コードと不一致

- 設計の `VisualEvent` 表は `doServe()` を「現行どおり音なし」としているが、現行 `doServe()` は `this.feedback.hit(0.35)` を呼ぶ。「VisualEvent と Feedback を 1 対 1 に対応」という設計原則とイベント表の記述が食い違っている。
- **修正**: `serve` は既存 `feedback.hit(0.35)` と対応と記載し、「音なし」の記述を削除する。`feedback.ts` の内容自体は変更しない。

### P1-03 得点理由の現状分析とバナー仕様が不足

- 設計書は主に `ネット` / `アウト` / `返せず` を現行理由として扱うが、`judgeBounce()` には既に `サーブフォルト` と `自陣に落下` が存在する。未知 reason fallback があるためクラッシュはしないが、既知の現行値を「将来値」扱いにしている。
- **修正**: `pointBannerText()` の正式表を最低 5 理由へ拡張する（例: サーブフォルト → 「あなたの得点 / あいてがサーブフォルト」「あいての得点 / サーブフォルト」、自陣に落下 → 「あなたの得点 / あいてが自陣側へ落とした」「あいての得点 / 自陣側へ落とした」。文言は UI 方針に合わせて最終決定）。U-V7 も全現行理由を対象にする。

### P1-04 「初級ではギリギリが出ない」は成立しない

- 品質ラベルは `< 0.60` をギリギリとするが、現行 `LEVEL_PLAY.easy.contactQualityFloor` は 0.55。初級でも `0.55 <= q < 0.60` は成立し、ギリギリは出る。
- **修正**: ゲーム値を変えない方針なので、「初級ではギリギリが出ない」を削除し、「初級ではギリギリの発生範囲が 0.55〜0.60 に狭い」など事実に合わせる。

### P1-05 品質ラベルの「部分色」が既存 `Ui.flash()` 契約では表現できない

- 現行 `Ui.flash()` は文字列 1 つ・色 1 つ・`textContent`・要素全体へ `style.color` という API。設計は打球名の既存色を維持しつつ末尾の品質ラベルに品質別の別色を要求しているように読める。API を変えず単一 `textContent` のままでは打球名と品質ラベルを別色にできない。
- **修正案**: (1) トースト全体を品質色にする、(2) `Ui.flash()` API は維持しつつ内部 DOM を `span` 分割し品質を別 API / structured metadata で指定、(3) 品質ラベルは文字だけとし色分けを要件から外す。最小変更は 3。

### P1-06 一時停止中に「視覚演出が止まる」という契約が統一されていない

- 設計 §8 は「一時停止・非表示・viewport gate 中にエフェクトが進まない」とするが、現行ループでは suspended 中も `ui.tickFlash(plan.frameDelta)`、`renderer.render()`、swing の減衰が rAF ごとに走る。さらに新規仕様では score pulse は `setTimeout`、待機揺らぎ / スマッシュ脈動は `performance.now()` を使う。`simulationTime` 系だけ止めても DOM / performance.now 系は止まらない。
- **修正**: 「止める対象」を明確に分離する。推奨は、情報表示時間は pause 中保持、装飾 animation は pause 中静止、`performance.now()` を直接使う場合も `state.paused` / suspension を effect policy に渡す、DOM timeout ではなく update loop ベースか pause 時に class を強制停止。

### P1-07 ラリー節目 pulse が `updateHud()` で毎 tick 再発火し得る

- 現行 `tick()` は rally 中、固定ステップごとに `ui.updateHud(this.state)` を呼ぶ。設計を単純に `state.rally % 5 === 0` で pulse とすると `rally === 5` の間、毎 tick pulse が再付与される。
- **修正**: 必ずエッジ検出にする（`previousRally !== state.rally` かつ `state.rally > 0` かつ `state.rally % RALLY_PULSE_EVERY === 0`）。同じ rally 値で `updateHud()` を 20 回呼んでも pulse 開始回数は 1 回、とする単体テストを追加。

### P1-08 `data-serve-zone` の仕様が文書内で矛盾

- §5.9.1 は「`Ui.updateHud()` で常時 `selectedServeLength` を反映」、E-V4 は「AI サーブ時・ラリー中は属性が消える」としており、両方は同時に成立しない。
- **修正**: 「player serve + `!ball.live` + `!paused` のときだけ設定、それ以外は `delete document.body.dataset.serveZone`」と明示し、E-V4 はこの契約を検査する。

### P1-09 最終得点では 1.1 秒の得点バナーを保証できない

- `POINT_BANNER_SEC = 1.1`、`RESULT_DELAY_MS = 1000ms`、game over では 1.0 秒後に result overlay 表示のため、最終得点だけバナーが 1.1 秒見える保証がない。
- **修正**: `RESULT_DELAY_MS` を変えない N-5 を優先するなら、最終得点だけ 0.9〜1.0 秒以内、または result overlay 上でも point banner が見えるレイヤ設計、のどちらかを明記。G2 で最終得点も確認する。

### P1-10 `E-V3` は reduced-motion の検出テストとして弱い / 実質空振りの可能性

- E-V3 は reduced motion で得点後 `data-effects-live="0"` を見るが、reduced でも bounce ring は有効、point 自体は Canvas effect なし、`effectsLive` の定義は「生存粒子数」であるため、0 であることが何を証明するか曖昧。point 直後に粒子が元々無ければ full motion でも 0 になり得る。
- **修正**: `effectPolicy(true)` の完全一致は unit、E2E は reduced で contact 発生後も spark count 0、full では同じ操作で spark count > 0、net event で reduced の wobble が 0、pulse class が付かない、を直接検査する。`effectsLive` は `particlesLive` 等へ意味を限定するか、種別ごとの dataset にする。

## 5. P2：設計明確化・保守性・観測性

### P2-01 `MatchSituation` の型定義場所が二重指定

- §5.8.3 のコード例は `rules.ts` で `export type MatchSituation`、§7 12-0 は `types.ts` に追加としている。
- **修正**: 型は 1 箇所に固定する。推奨は `types.ts` に型、`rules.ts` に `matchSituation()` 実装。

### P2-02 `getRenderScene()` を drain API にすると getter が副作用を持つ

- 設計では `getRenderScene()` が event buffer を返して空にするが、現在の `getRenderScene()` は状態スナップショット取得 API として読むだけの性格が強い。将来 debug・テスト・2 つ目の描画 consumer が先に呼ぶだけでイベントが消える。
- **推奨**: `getRenderScene()` は非破壊、`drainVisualEvents()` を Renderer 専用に分ける。またはイベントへ monotonically increasing sequence を付け Renderer が既読 ID を持つ。

### P2-03 複数 fixed step 発生時のイベント時刻補正が未定義

- `VisualEvent.time` は `simulationTime` を持つが、Renderer は 1 フレームに複数 tick 分のイベントをまとめて受け取る可能性がある。古い event を何秒経過した状態で spawn するかが定義されていない。
- **修正**: spawn 時に `age = max(0, scene.simulationTime - event.time)` を反映し、TTL を超えた event は生成しない。

### P2-04 net event の x/y は「ネット面交点」を使うと明記すべき

- 現行 `updatePhysics()` はネット判定時に previous / current から ratio と交点 `x` / `y` を既に計算しているが、衝突後 `ball.z = 0` にし速度も変更する。
- **修正**: `VisualEvent.net` は必ず補間済み交点 x/y を発行すると設計へ明記する。同様に contact event は solver 用に補正した y ではなく実接触位置を使う。

### P2-05 `data-situation` の null 時処理を明記

- CSS は `body[data-situation]` でトースト位置を変更する。null のときに `body.dataset.situation = ""` とすると属性自体は残るので CSS selector が成立する。
- **修正**: null では必ず `delete document.body.dataset.situation` とする。E-V5 で属性の不存在も検査する。

### P2-06 score pulse の前回値管理と newGame 初期化が未定義

- 得点増加側だけ pulse するには previous score が必要。試合終了後に 11-9 などから新規試合の 0-0 へ戻るため、単純な差分監視ではリセット挙動を誤る可能性がある。
- **修正**: `next > previous` のときだけ pulse、`newGame` / title 表示時の baseline 更新方法を明記、score 減少では pulse しない。

### P2-07 `serve` / `point` VisualEvent の consumer が弱い

- 設計では `serve` に Canvas effect の具体的利用先がなく、`point` は Canvas effect を行わない。それでも event buffer に載せるため API とテストが増える。
- **修正**: 各 event の consumer を表へ追加し、DOM が使う / Renderer が使う / 将来用なので今回は作らない、を明確にする。YAGNI を優先するなら未使用 event は追加しない。

## 6. テスト設計に追加すべき項目

### 必須

- **E-V6 最終得点**: game-winning point を発生させ、point banner が表示、dead ball が表示、result overlay への遷移、effect が永続しないことを検査。
- **E-V7 pause 中の視覚時計**: pause 中に 1 秒以上待っても particle / ring の simulation age が進まない、banner / toast の方針どおり保持または消化、ambient animation が仕様どおり停止、を検査。
- **E-V8 score / rally pulse の edge**: 同じ score / rally で update が連続しても 1 回、score が増えた瞬間だけ 1 回、rally 5 → 5 では再発火しない、rally 10 で再度 1 回。
- **U-V13 serve-zone coverage**: 実製品の入力 envelope 全件、fallback 数、requested / resolved length 一致率、error 適用後包含率。

### 推奨

- **キャッシュ再生成テスト**: `layerKey()` の値だけでなく、同じ key で L0 / L1 draw が再実行されない、width / height / dpr のいずれか変更で各 1 回再生成、orientationchange の即時 + 250ms resize でも同じ key なら余分に描かない、を spy で確認。
- **描画順テスト**: Canvas pixel diff を CI に入れなくても、ball z > 0 → net → ball z <= 0 の draw command order を injectable context / command recorder で検査できる。ネット前後関係は今回の中心要件なので `ballBehindNet()` 単体だけより強い。

## 7. 性能評価の見直し

現行設計の良い点：静的描画を L0 / L1 へ寄せる、particle 上限を持つ、p95 を見る、CI の時間揺らぎを考慮して hard gate にしない。

### 7.1 Renderer 時間と frame time を分ける

`Renderer.render()` の時間だけでは DOM banner、class toggle、layout / style、CSS animation による jank を捉えられない。記録値として renderer p50 / p95、rAF frame interval p50 / p95、50ms 超 long frame 数を分ける。

### 7.2 cold path を別計測

静的レイヤ再生成は通常フレームから外れるが、resize、orientation change、DPR 変更時に大きなコストが出る。通常 p95 と cache rebuild 単発時間を別に記録する。

## 10. 総評

今回の設計書は、単なる「見た目刷新」のメモではなく、非破壊契約、乱数分離、描画レイヤ、reduced-motion、性能予算、unit / E2E / manual / deployment、rollback まで踏み込んでおり、設計の骨格はかなり良い。ただし変更規模が大きいため、見た目の設計より状態遷移と観測方法の整合性がリリース品質を左右する。特に今回見つかった P0 は、実装品質の問題ではなく「仕様どおり正しく実装しても受入条件を満たせない」種類の問題である。そのため、先に正本を修正してから実装へ進むのが安全である。

**最終判定: 現設計のまま Phase 12 着手は非推奨。P0 / P1 是正後は GO 可能。**
