## 判定

**No-Go。P2 が5件あり、現状の設計をそのまま実装へ渡せない。** 正方形 stage と同じ高さの横画面 stage で `f` / `cy` が一致する計算は確認できた。一方、その正方形を実際の DOM 寸法として成立させる契約、パネル表示、レールの高さ、safe area、描画サイズの同期が不足している。

本レビューは設計と現行コードの整合性を対象とする。以下は未実装機能への設計指摘であり、現行 v0.3.0 に縦画面機能が存在しないこと自体を不具合とはしていない。設計本文・製品コードは変更していない。

## F-01 [P2] 常時表示と既存の hidden 制御を両立させる経路がない

- 対象: 設計 §3.4、§4.3（121、215行）、§6。
- 根拠: [src/ui.ts](../src/ui.ts) の `updateServeControls()`（417行付近）は、player serve 待ちかつ非 pause の場合以外に `serveControls.hidden = true` を設定する。[src/styles.css](../src/styles.css) の20行には `[hidden] { display: none !important; }` がある。
- 発生条件: 縦画面で player serve から rally / AI serve / pause へ移ったとき。
- 問題: 設計が指定する `pointer-events: none; opacity: .45` は `hidden` を解除しない。通常の `display` 上書きでも既存の `!important` に負けるため、サーブパネルは常時表示されず占有高も消える。§6 の変更表に `src/ui.ts` は含まれておらず、既存 CSS との優先順位も未定義である。固定の grid 行が残れば stage が直ちに変動するとは限らないが、常時表示・同じ占有高という受入契約には違反する。
- 必要な修正: パネルの表示条件と操作可能条件を分ける。縦では表示を保ち、既存の `button.disabled` を有効条件に連動させる方針を定義する。CSS で解決する場合も `[hidden]` との優先順位、pause 時、縦横切替直後の状態同期を明記する。横画面の表示条件は維持する。
- 再確認: player serve / rally / AI serve / pause と、pause 中の縦横切替で、パネルの実寸・表示・disabled を検査する。

## F-02 [P2] 272px の内訳が284pxあり、操作要素を収められない

- 対象: 設計 §3.4（123行）、§4.3（208〜217行）、§7、§8.2。
- 根拠: 設計自身の内訳は `16 + 3×44 + 2×6 + 44 + 44 + 36 = 284px`。272px では12px不足する。さらに、現行 CSS ではパネルの border / padding、長さ行の `margin-top`、レールの gap がそれぞれ存在する。
- 発生条件: 縦画面で球種3行・長さ1行・試合操作1行を、各44px以上で同時に表示するとき。viewport を大きくしてもレールは272px固定なので解消しない。
- 問題: `overflow: hidden` と「縮小・非表示・スクロール化はしない」「下端余白2px以上」を同時に満たせない。現行の player serve 専用 CSS は `body[data-phase="serve"][data-server="P"]` であり、横画面に限定されていない。音・振動の非表示、padding / gap 圧縮が縦にも残るため、「試合操作を1行で常時表示」の実装も曖昧である。
- 必要な修正: border-box の総高を数値で再計算し、レール高を増やすか spacing の正確な内訳を改める。レール高が変わる場合は `portraitStageSide()`、最小 viewport、ガード、境界表も同時に更新する。既存の player serve セレクタを縦でどう上書きするか明記する。
- 再確認: 最小幅で全12個のサーブボタンと試合操作を検査し、各44×44px、パネルと子要素の下端、2px余白、非クリップを serve / rally 両方で確認する。

## F-03 [P2] stage 辺長の式が CSS の実寸指定に接続されていない

- 対象: 設計 §4.1（144行）、§4.3（191〜205行）、§4.4。
- 根拠: `portraitStageSide()` は gate 判定へ使う仕様だけであり、その戻り値を stage 寸法へ設定する経路がない。提示 CSS は `width: auto; height: auto; max-width: 100%; max-height: 100%; aspect-ratio: 1 / 1; margin-inline: auto` とする。一方、[index.html](../index.html) の stage 内要素と [src/styles.css](../src/styles.css) の169〜176行では canvas / HUD が絶対配置で、内容による stage のサイズ確保を期待できない。
- 発生条件: 初回の縦表示、および 430×660 のように高さが stage 辺長の上限となるレターボックス表示。
- 問題: `aspect-ratio` と最大サイズ指定だけでは、両軸 auto の要素に「利用可能幅と利用可能高さの小さい方」という使用寸法は与えられない。auto margin と非 stretch の行配置もあり、内容寸法へ縮む経路がある。したがって `portraitStageSide() >= 360` の判定成功から実 stage が同じ辺長になることを導けず、§3 の投影パリティの前提が成立しない。**縮退の具体的なブラウザ使用寸法は今回未実測であり、この部分は CSS sizing の静的解析に基づく指摘である。**
- 必要な修正: safe area 控除後の利用可能幅・高さを用いて辺長を確定し、CSS の明示サイズまたは CSS custom property 等で両軸に渡す契約を定める。gate の計算と DOM の実寸が別式にならないようにする。
- 再確認: 390×844 → stage 390×390、430×660 → 388×388（現行の272pxを使う場合・safe area 0）を実 DOM で assert する。canvas の client size も一致させる。正方形であることだけでなく、期待辺長との一致を検査する。

## F-04 [P2] safe area を引かない gate が360px未満の stage を許可する

- 対象: 設計 §4.1（144〜169行）、§7（295行）、§8.2（326行）。
- 根拠: [src/styles.css](../src/styles.css) の `.app-shell`（81〜89行）は上下左右の `env(safe-area-inset-*)` を padding として確保する。[src/view/orientation.ts](../src/view/orientation.ts) の `currentViewport()` が読む viewport サイズから、この padding は控除されない。
- 反例: viewport 360×632、上24px・下34px・左右0pxという **説明用 inset** では、設計式は `min(360, 632−272) = 360` でプレイを許可する。しかし shell 内で使える stage 辺は `min(360, 632−24−34−272) = 302`。これは特定機種の実測値ではなく、非ゼロ inset に対する算術上の反例である。
- 問題: 幅360pxの gate を左右到達保証の根拠としているのに、実 stage は360px未満になり得る。stage を360pxのまま強制すれば、今度は固定高レールと safe area が画面内に収まらない。
- 必要な修正: gate / stage / rail の3者で同じ content box 寸法を使う。縦横 inset を明示的に入力へ含めるか、shell の利用可能寸法を計測して分類する。§4.2 の「高さ幅+272以上」という文言も、レターボックスを許す §4.1 と一致しないため、実際の必要サイズ条件へ揃える。
- 再確認: inset 0 と非ゼロの境界で、gate 開放時には実 stage が必ず360px以上となること、操作レールが safe area に侵入しないことを確認する。

## F-05 [P2] dataset によるレイアウト変更後の再 resize が保証されない

- 対象: 設計 §4.3（185〜192行）、§4.4（222〜224行）、§8.2（325行）。
- 根拠: [src/view/orientation.ts](../src/view/orientation.ts) の `schedule()` は `requestAnimationFrame` へ処理を遅延し、`update()` で初めて `body.dataset.viewport` を変更する。[src/render.ts](../src/render.ts) の81〜84行・277〜299行は window / visualViewport の `resize` を受けて、その場で canvas の client size を読む。stage の `ResizeObserver` や dataset 変更完了後の通知はない。
- 発生条件: デスクトップのウィンドウリサイズ、または E2E の viewport 変更など、`orientationchange` を伴わずに portrait / landscape の境界を跨ぐ場合。
- 問題: `resize` ハンドラは旧 dataset による CSS レイアウトを読み、その後の rAF で新 dataset と新 stage 寸法が適用される。次の resize が来なければ Renderer の width / height / camera / backing store は旧値のままになる。250ms の再 resize は `orientationchange` 内だけなので、この経路を救済しない。入力の canvas rect と描画・接触用 viewport が不一致になる。
- 確認: 実際の `Renderer` を Node へ読み込み、window listener / canvas をスタブ化したイベント順序ハーネスで再現。resize 中の canvas を390×390、次のフレームで625×390に変更すると、DOM相当サイズは625×390でも `renderer.getViewport()` は390×390のまま残った。ブラウザ実測ではなく、現行 Renderer と設計の遅延レイアウト変更を組み合わせた検証である。
- 必要な修正: stage / canvas の実寸変更を監視するか、viewport の dataset 更新と layout 確定後に Renderer の resize を実行する。§4.4 の「コード変更なし」は撤回し、変更対象・解除処理を定義する。
- 再確認: `orientationchange` を発火しない縦→横→縦で、stage rect、canvas client size、backing store / DPR、Renderer の viewport が一致することを検査する。gate の hidden と試合状態保持だけでは検出できない。
