## 3. 指摘事項

### P1-01: 非同期保存結果を既存の遅延結果画面へ反映する契約が成立していない

**対象**

- 設計書 §4.5.3（294行）
- 設計書 §4.6（301〜324行）
- `src/game.ts:1019-1026`
- `src/ui.ts:232-242`

**根拠**

現行コードでは、ゲーム終了後に `Game.point()` が `RESULT_DELAY_MS` のタイマーを開始し、タイマー満了時に `Game` 自身が `ui.showResult(this.state)` を呼ぶ。一方、設計書は次の3つを同時に要求している。

1. `recordMatchResult()` は結果表示タイマーとは独立に保存を開始する。
2. `onRecorded(boolean)` を受けた `main.ts` が再集計し、結果画面を更新する。
3. `Ui.showResult()` へ `recordLabel` 引数を1つ追加する。

このままでは、保存完了が結果表示より早い場合と遅い場合のどちらが `showResult()` を呼ぶか、集計ラベルをどこに保持するかが決まらない。`recordLabel` だけでは表示に必要なプレイヤー名も渡せない。さらに `store` または `player` が未設定なら設計例はコールバックなしでreturnするため、「戦績機能なし」と「保存失敗」を結果画面で区別できない。遅い保存が「もう一度」で始めた次試合の結果表示を上書きする世代競合も防げない。

**必要な修正**

1. 1試合ごとの不変スナップショットを定義する。少なくとも `matchId`、`playerId`、`playerName`、難易度、スコア、最大ラリー、開始・終了時刻を試合終了時に固定する。
2. 結果表示の所有者を1か所へ決める。推奨は、`Game` が試合終了スナップショットを通知し、`main.ts` が保存と集計を担当し、`Game` は保存層を直接参照しない構成である。
3. 結果の保存状態を `unavailable` / `pending` / `saved` / `failed` のように明示し、それぞれの表示文言を定義する。
4. `Ui.showResult(...)` と、表示後に保存状態だけを更新するメソッドの引数を確定する。プレイヤー名と通算ラベルの供給元も明記する。
5. `matchId` または世代番号で、過去試合の非同期完了が次試合・別プレイヤーの画面を更新しないようにする。

**解消条件**

保存が結果表示より前／後に完了する両順序、保存不可、保存失敗、保存中に「もう一度」を開始する順序について、呼び出しシーケンスと期待表示が一意に決まり、自動テスト条件として記載されていること。

### P1-02: プレイヤーCRUDと選択状態の遷移が未定義で、削除後に不整合または孤児戦績を作り得る

**対象**

- 設計書 §4.3（204〜223行）
- 設計書 §4.5（251〜290行）
- 設計書 §4.7（327〜335行）
- 設計書 §10-1（471行）

**根拠**

設計書は追加・選択・改名・削除を受け入れ条件にしているが、`PlayerUiHandlers` の型と各ハンドラの手順が無い。追加用の `#playerInput` はあるものの、改名ボタンを押した後に名前をどの要素へ入力し、確定・取消するかも定義されていない。

特に選択中プレイヤーの削除では、次の状態を同時に整合させる必要がある。

- `players` と、そのプレイヤーの `matches`
- `settings.selectedPlayerId`
- `Game` が保持する現在プレイヤー
- `#playerName`、`#playerRecord`、`#hudPlayerName`
- プレイヤー一覧の選択表示

しかし `deletePlayer(id)` の契約は `players` と `matches` だけを同一トランザクションで削除し、代替プレイヤーの選択と `settings` 更新を扱わない。IndexedDBには外部キー制約がないため、削除済みプレイヤーを `Game` が保持したまま記録すると孤児の `matches` を作れる。加えて、戦績の連鎖削除は取り消せないにもかかわらず、設計書 §10-1 ではまだユーザー確認事項のままである。

**必要な修正**

1. 戦績をプレイヤーと一緒に削除するかを、実装前の確定事項にする。
2. `PlayerUiHandlers` の型と、追加・選択・改名・削除・取消それぞれの入力、成功、失敗、再描画を定義する。
3. 改名UIの要素、フォーカス、確定・取消操作を定義する。`prompt()` 等へ実装者判断で逃がさない。
4. 選択中プレイヤー削除時は、代替プレイヤー決定、`settings` 更新、削除、返却値を一貫した保存層契約にする。可能なら1トランザクションで完結させる。
5. `recordMatch` は対象プレイヤーの存在を検証するか、試合開始時に固定した有効なプレイヤースナップショットだけを受け付ける。
6. 非同期操作中の二重押下を防ぎ、失敗時は保存済み状態を再取得してUIを復元する。

**解消条件**

全CRUDについて、保存層・選択設定・`Game`・DOMの遷移順が表またはシーケンスで一意に定まり、選択中プレイヤー削除後にも有効な1人が選択され、削除済みIDの戦績を追加できないことがテスト条件に含まれていること。

### P2-01: `maxRally` が再試合時に前試合の最終ラリーを取り込む

**対象**

- 設計書 §4.6-1（298行）
- `src/game.ts:317-335`
- `src/game.ts:406-426`

**根拠**

設計書は `newGame()` で `maxRally = 0` にした後、`startServe()` で `rally` を0へ戻す直前に `maxRally = Math.max(maxRally, rally)` を実行する。現行 `newGame()` は `rally` をリセットせず `startServe()` を呼ぶため、再試合やタイトル復帰後の新試合では、前試合の最終 `rally` が新試合の `maxRally` に入る。

**必要な修正**

- ポイント終了時にそのポイントの `rally` を `maxRally` へ反映し、`startServe()` はリセットだけを行う設計にする、または新試合開始とポイント間サーブ開始を区別する。
- `newGame()` では `rally` と `maxRally` をともに0へ初期化し、前試合の値を参照しない順序を明記する。

**解消条件**

「長いラリーを含む試合 → もう一度 → 短いラリーだけで決着」の2試合連続テストで、2試合目の `maxRally` に1試合目の値が混入しないこと。

### P2-02: フォールバック境界が `open()` だけで、初期化後の失敗を扱えない

**対象**

- 設計書 §3.2（67〜71行）
- 設計書 §4.3（217〜223行）
- 設計書 §4.7（327〜335行）
- 設計書 §8.3-7（441行）

**根拠**

`StatsStore.open()` が `null` を返す場合だけ戦績機能なしモードへ移るが、open成功後の `listPlayers()`、`addPlayer("ゲスト")`、設定読書き、`listMatches()`、各CRUDも、quota、transaction abort、データ破損等で失敗し得る。起動フローにはこれらをまとめて戦績機能なしへ落とす境界がなく、初期化中に操作ボタンを押せるかどうかも未定義である。

また、ChromeのシークレットウィンドウではストレージAPI自体は利用でき、終了時に消去されるのが通常であるため、「シークレットで開く」だけでは `open() === null` の経路を再現できない。IndexedDBのquotaやprivate browsing時の扱いはブラウザ依存であることも公式資料に明記されている。

**必要な修正**

1. 初期状態を `loading` として戦績・プレイヤー操作を無効にし、初期化完了後だけ有効化する。
2. `open` から初回プレイヤー確定・初回集計までを1つの `try/catch` 境界に置き、失敗時のUI・`Game`状態を定義する。
3. 操作ごとの失敗はゲームを継続し、直前の保存済み状態を再取得する方針を定義する。
4. フォールバックテストは、依存注入した失敗ストア、またはPlaywrightの初期化スクリプトでIndexedDBアクセスを明示的に失敗させるなど、再現可能な方法へ変更する。

**解消条件**

open失敗、初回読込失敗、ゲスト作成失敗、記録失敗、再集計失敗の各ケースについて、ゲーム継続とユーザー向け表示が一意に定まり、自動テストで再現できること。

参考: [MDN IndexedDB basic terminology](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Basic_Terminology) / [MDN Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

### P2-03: テスト計画が戦績保存の中核契約を自動検証しない

**対象**

- 設計書 §8.1（412〜419行）
- 設計書 §8.2（421〜429行）
- 設計書 §9（451〜465行）

**根拠**

追加予定の単体4件はラケット座標と集計関数だけである。E2E 3シナリオも、追加、名前の空・重複、空の戦績画面までしか確認しない。次の受け入れ条件は自動検証されない。

- 改名
- 選択のリロード後永続化

- 必要テストを追加した後の実数で `pass 21` / `E2E 27` を更新する。

**解消条件**

§9の戦績関連受け入れ条件が、どの単体／E2E／手動確認で担保されるか対応表になり、保存・削除・失敗・競合の中核契約が自動テスト対象になっていること。

### P2-04: `crypto.randomUUID()` はREADME記載の非HTTPS LAN実機確認で使えない

**対象**

- 設計書 §4.2（160、171行）
- `README.md:43`

**根拠**

設計書はプレイヤーIDと試合IDを `crypto.randomUUID()` で採番する。Web Cryptography Level 2では `randomUUID()` はSecure Context限定である。一方、READMEは同一ネットワーク内のスマートフォンからPCのIPアドレスで `npm run dev` へ接続する手順を案内している。`http://192.168.x.x:3038/` のようなLAN IPはlocalhost／loopbackではなく、通常はSecure Contextにならないため、プレイヤー作成または試合記録時に `randomUUID` が利用できない。

**必要な修正**

- ID生成を純粋なヘルパーへ分離し、`crypto.randomUUID` が使える場合は使用し、使えない場合は非Secure Contextでも利用可能な `crypto.getRandomValues()` からUUID相当の衝突しにくいIDを生成する。
- `randomUUID` が未定義のブラウザ条件を自動テストへ追加する。
- 代わりにLAN実機確認をHTTPS化する場合は、READMEと手動確認手順へ証明書・接続方法を含める。

**解消条件**

公開HTTPS、localhost、非HTTPS LAN IPの3経路でID採番方針が明記され、少なくとも `randomUUID` 不在ケースが自動テストされること。

参考: [W3C Web Cryptography Level 2](https://www.w3.org/TR/webcrypto-2/) / [W3C Secure Contexts](https://www.w3.org/TR/secure-contexts/)

### P3-01: 表示名の「12文字」がHTMLと保存層で異なる単位になる

**対象**

- 設計書 §4.3（220行）
- 設計書 §4.5.1（262行）

**根拠**

保存層は `[...name].length` でUnicodeコードポイント数を数え、絵文字を1文字として扱う。一方、HTMLの `maxlength="12"` はUTF-16コード単位で制限するため、サロゲートペアを使う絵文字は保存層へ届く前に2文字相当として制限される。UIと保存層で「1〜12文字」の意味が一致しない。

**必要な修正**

- コードポイント数を契約にするなら `maxlength` に依存せず、入力イベントと保存層で同じ関数を使う。
- ユーザーが認識する文字数を契約にするなら `Intl.Segmenter` 等で書記素クラスタを数える方針を明記する。

**解消条件**

通常文字、絵文字、結合文字について、UIと保存層が同じ上限判定を返すこと。

## 4. 確認できた妥当な点

- 第2期リファクタリングは `master` の `0a8d5f8` へ統合済みで、`src/utils.ts`、定数集約、`OpponentAi` 分離という本設計の技術的前提は満たされている。
- ラケットの横位置だけを既存投影から使い、縦位置とサイズを純粋関数化する方針は、`Game.playerContact` を変えず描画差分を局所化する目的に合う。
- `paddle()` の式を変えず、プレイヤー側のscaleだけを逆算する方針は、相手ラケットの非破壊条件と整合する。
- IndexedDBの副作用を `storage.ts`、集計を `stats.ts` に分離する方針は、現行の小規模フラット構成で過剰な層を増やさない。
- `textContent` に限定し、DOMExceptionをユーザーへ直接表示しない方針は妥当である。
- アプリシェル内容を変えず固定名 `app.js` / `app.css` を維持し、キャッシュ名だけを `table-tennis-v3` へ上げる方針は現行Service Worker契約と整合する。
- 公開を明示承認後に限定し、Actions・Pages deployment・HTTP・Chromeを分けて確認する方針は共通公開ルールと整合する。
