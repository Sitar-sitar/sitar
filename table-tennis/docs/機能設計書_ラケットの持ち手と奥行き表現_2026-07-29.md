## 1. 目的・背景

### 1.1 持ち手がない

`Renderer.paddle()`（`src/render.ts:495-531`）は楕円1枚とハイライトしか描いていない。プレイヤー・相手の両方がこの関数を使うため、**どちらのラケットも「色の付いた円」にしか見えず、卓球ラケットとして認識しづらい**。v0.3.0 で腕の描画を廃止した（旧設計 §4.1.3-6）結果、向きを示す手掛かりが完全に無くなったことも読み取りづらさを強めている。

### 1.2 奥行きの動きがない

**物理モデル側には既に奥行きがある。** `player.z` は打球ごとに `contactPlane("P")` で決まり（`src/game.ts:613` / `src/game.ts:788`）、`CONTACT_PLANE_NEAR`（`62`）〜`CONTACT_PLANE_FAR`（`178`）の範囲で前後に動く。打球判定もこの `player.z` 平面の通過で行われている（`src/game.ts:863`）。

一方、描画は `player.z` を**横位置の投影にしか使っていない**（`src/render.ts:539-542`）。縦位置は `paddleScreenY()` の画面高固定比率、大きさは `paddleScreenRadius()` の画面短辺固定値であり、いずれも奥行きに依存しない。**「手前で水平に動くだけ」に見えるのは仕様ではなく、モデルが持っている奥行きが絵に出ていないため**である。

### 1.3 ユーザー要望

1. ラケットに持ち手を追加する（フェーズA）
2. 台側など奥行きのある動きを表現する（フェーズB）

なお「プレイヤーが自分の意思で前後に動く」操作は、縦方向のドラッグが既にショット種別判定（`src/input.ts:168` の `vy` → `src/game.ts:946-970`）に使われており、入力チャネルの設計判断が別途必要になる。**今回は扱わない**（§2.2・2026-07-29 ユーザー選択）。

## 3. 全体方針

### 3.1 持ち手は共有関数 `paddle()` に「向き」を渡して描く

`paddle()` に持ち手を実装し、**向き（ラジアン）を引数で受け取る**。プレイヤーと相手で描き分けたい理由は向きだけであり、形状は同じだからである。

- プレイヤー: 持ち手は画面下向きを基準にし、スイング種別と量に応じて傾ける（§4.2.5）。
- 相手: 持ち手は**手から腕の付け根へ向く**（`drawOpponent` が既に持っている腕の始点を使う）。腕の線と持ち手が繋がって見え、相手ラケットの向きも自然になる。

代替案として「プレイヤー側だけに持ち手を描く（`handle: boolean` 引数）」も検討したが採らない。ラケットは2本とも同じ道具であり、片方だけ円のまま残す理由がない。相手ラケットの見た目が変わることは旧設計 §5 の非破壊項目に抵触するため、§0 で明示的に supersede する。

### 3.2 奥行きは「画面空間のパラメータ」で表現し、横位置は物理平面の投影を使う

奥行き比 `depth`（0＝最も奥／ネット寄り、1＝最も手前／自陣寄り）を求め、**縦位置・大きさ・影のみ**を `depth` の線形式で決める。**横位置は従来どおり物理平面 `player.z` の投影値を使い、本設計でも変更しない。**

縦位置・大きさに完全な透視投影（`project(player.x, 一定の高さ, player.z).y`）を採らない理由:

- 現行カメラで試算すると、`z = -62`（ネット寄り）では画面高の約 0.52、`z = -178`（自陣寄り）では約 0.80 に描かれる。**振れ幅が画面高の約 28% に達し**、指の位置（画面下部）から大きく離れる。v0.3.0 で確定した「ラケットは画面下部で分離して動く」という操作感を壊す。
- 打点平面はプレイヤーが選べず、AI の返球ごとに自動で決まる。振れ幅が大きいほど、意図しない上下動として見える。
- 線形式ならカメラ内部の値に依存せず、**純粋関数として単体テストできる**（v0.3.0 で確立した方針を維持できる）。

一方、横位置に `project()` を使い続ける理由は**打球判定との一致**である。`project()` の X 倍率は `camera.f / (z - camera.z)` であり、Z が違えば同じワールド X でも画面 X が変わる。ボールは実際の `ball.z` で投影され、打球は「ボールが平面 `player.z` を通過した時点で `|ball.x - player.x| <= P_REACH`」で成立する（`src/game.ts:863` / `:939`）。したがって**ラケットの横位置を `player.z` 以外の Z で投影すると、画面上で重なって見える位置と打球が成立する位置がずれる**（§3.3・§7.1-2）。

### 3.3 奥行きの追従値 `viewZ` は縦位置・大きさ・影にだけ使う（横位置には使わない）

`player.z` は打球ごとに**瞬間的に**書き換わる（`src/game.ts:613` / `:788`）。これをそのまま縦位置・大きさに使うとラケットがワープする。かといって `player.z` 自体を補間すると、判定平面の位置が時間変化し、**打球判定の挙動を変えてしまう**。

そこで `PaddleState` に**描画専用の `viewZ`** を追加し、固定ステップの `tick()` で `stepViewZ()`（§4.2.7）によって `z` へ追従させる。**用途は縦位置・大きさ・影に限定する。**

| 描画要素 | 使う Z | 理由 |
|---|---|---|
| 横位置（X） | `player.z`（物理平面） | ボールと同じ投影倍率になり、打球成立位置と画面上の位置が一致する |
| 縦位置・大きさ・影 | `viewZ`（追従値） | 奥行き変化を滑らかに見せる。判定に影響しない |

**不変条件（本設計の最重要契約）**: 打球が成立する瞬間、ボールとラケットは**同一の投影倍率** `projectScale(f, camera.z, player.z)` で描かれる。したがって `ball.x === player.x` なら画面上 X は完全に一致し、それ以外でも画面上の距離は `|ball.x - player.x| * scale` に等しい。これは v0.3.0 と同じ挙動であり、`viewZ` の追従状態に依存しない。

> **代替案（横位置にも `viewZ` を使う）を退けた理由**: 320×568px・`player.x = 104` で試算すると、`player.z = -178` に対して `viewZ = -152` では画面上 X が **41.6px**、`viewZ = -62` では **123.2px** ずれる。後者は判定半径 `P_REACH = 31` を投影した幅より大きく、「重なって見えないのに打てる／重なって見えるのに打てない」状態を作る。奥行き遷移中に横の遠近と縦の遠近が一瞬食い違う点は、視覚的に検知できない範囲として受け入れる（§7.1-2）。

### 3.4 位置決めは純粋関数として `src/utils.ts` に置く

Canvas 描画そのものは自動テストしない。**位置・大きさ・角度・追従を決めるロジックだけを純粋関数へ切り出し**、単体テストの対象にする（v0.3.0 §3.1 で確立した方針の継続）。`Renderer` と `Game` は関数の戻り値を使うだけにする。

純粋関数化できない「結線」（初期値・リセット・呼び出し箇所・投影に渡す引数）は、既存の `scripts/check-app.mjs` と同じ方式で**ソース契約検査**として固定する（§4.8）。

### 4.2 純粋関数（`src/utils.ts`）

#### 4.2.1 `projectScale`（新規・フェーズB）

```ts
export function projectScale(
  focal: number,
  cameraZ: number,
  z: number,
): number;
```

- `focal / Math.max(24, z - cameraZ)` を返す。**`Renderer.project()`（`src/render.ts:106-114`）が現在インラインで行っている計算をそのまま切り出したもの**であり、値は変わらない。
- `Renderer.project()` はこの関数を呼ぶ形に書き換える。切り出す目的は、§3.3 の不変条件（同じ Z なら同じ倍率）を **DOM や Canvas なしで単体テストできるようにする**ことである（U16）。

#### 4.2.2 `paddleDepthRatio`（新規・フェーズB）

```ts
export function paddleDepthRatio(z: number): number;
```

- `clamp((Math.abs(z) - CONTACT_PLANE_NEAR) / (CONTACT_PLANE_FAR - CONTACT_PLANE_NEAR), 0, 1)` を返す。
- 戻り値 `0` ＝ 最も奥（ネット寄り・`abs(z) <= 62`）、`1` ＝ 最も手前（自陣寄り・`abs(z) >= 178`）。
- `Math.abs` を使う理由: プレイヤー側の `z` は常に負だが、符号に依存しない定義にしておくとテストが書きやすく、将来相手側へ流用できる。

#### 4.2.3 `paddleScreenY`（シグネチャ変更・フェーズB）

```ts
export function paddleScreenY(
  height: number,
  swing: number,
  swingType: number,
  depth: number,
): number;
```

- 基準位置: `height * (PADDLE_SCREEN_Y - PADDLE_DEPTH_RISE * (1 - depth))`
- スイングのオフセットは**現行の式をそのまま基準位置に加算する**（`swingType === 1` は `- height * PADDLE_SWING_LIFT * swing`、`-1` は `+ height * PADDLE_SWING_DROP * swing`、それ以外は `- height * PADDLE_SWING_PUSH * swing`）。
- `swing <= 0` のときはスイングのオフセットを加えない（現行と同じ）。奥行きの補正は `swing` の有無にかかわらず常に効く。
- **画面内に収める制限はここでは行わない**。半径に依存するため §4.2.6 で分離する。

#### 4.2.4 `paddleScreenRadius`（シグネチャ変更・フェーズB）

```ts
export function paddleScreenRadius(
  width: number,
  height: number,
  depth: number,
): number;
```

- `clamp(Math.min(width, height) * PADDLE_SCREEN_SIZE, PADDLE_SIZE_MIN, PADDLE_SIZE_MAX) * (1 - PADDLE_DEPTH_SHRINK * (1 - depth))` を返す。
- **clamp を先に、奥行き係数を後に掛ける**。順序を逆にすると、小さい画面では常に下限に貼り付いて奥行きによる縮小が消えるため。
- この結果、最小の見かけ半径は `PADDLE_SIZE_MIN * 0.7 = 12.6px` になる。視認性の下限としてこれを許容する。

#### 4.2.5 `paddleHandleAngle`（新規・フェーズA）

```ts
export function paddleHandleAngle(swing: number, swingType: number): number;
```

- 基準は `Math.PI / 2`（Canvas 座標系で真下向き）。
- `swing <= 0` なら基準をそのまま返す。
- `swingType === 1`（スマッシュ）: `+ PADDLE_HANDLE_TILT * swing`
- `swingType === -1`（ツッツキ）: `- PADDLE_HANDLE_TILT * 0.6 * swing`
- それ以外（ドライブ・押し出し・ロブ）: `+ PADDLE_HANDLE_TILT * 0.35 * swing`

> **`swingType` の実装値についての注意**: 旧設計 §4.1.2 は「`1` ＝ドライブ／スマッシュ」と書いているが、実装（`src/game.ts:764-765`）は `CHOP → -1` / `SMASH → 1` / **その他（DRIVE・PUSH・LOB）→ `0`** である。本設計は**実装値を正**として扱う。旧設計の記述は実装と食い違っているが、挙動は現行のままで問題がないため今回は修正しない。

#### 4.2.6 `paddleBottomExtent` / `clampPaddleScreenY`（新規・フェーズA）

小画面（特に横向き）でラケットの持ち手が Canvas 下端からはみ出すのを防ぐ。

```ts
export function paddleBottomExtent(radius: number): number;
export function clampPaddleScreenY(
  y: number,
  height: number,
  radius: number,
): number;
```

- `paddleBottomExtent(radius)` は `radius * PADDLE_BLADE_SCALE * (PADDLE_HANDLE_INSET + PADDLE_HANDLE_LENGTH) + PADDLE_EDGE_MARGIN` を返す。`radius` は `paddleScreenRadius()` の戻り値（`paddle()` が内部で `PADDLE_BLADE_SCALE` 倍したブレード半径を使うため、ここでも同じ係数を掛ける）。
- `clampPaddleScreenY(y, height, radius)` は `Math.min(y, height - paddleBottomExtent(radius))` を返す。
- **持ち手が真下を向くとき（`swing = 0`）が縦方向の最大到達**であり、傾けるほど到達は浅くなる。したがってこの制限は全スイング状態に対して安全側になる。
- 適用順は「`paddleScreenY()`（奥行き＋スイング）→ `clampPaddleScreenY()`」とする。ツッツキ（下方向オフセット）も制限の対象に入る。

検算（対応最小ビューポート・§8.3）:

| ビューポート | `depth` | 半径 | 制限前の Y | 下端到達 | 制限後の Y |
|---|---|---|---|---|---|
| 320×240（横） | 1（`swing = 0`） | 18 | 206.4 | 244.65（**はみ出す**） | 197.75 |
| 320×240（横） | 1（ツッツキ `swing = 1`） | 18 | 217.2 | 255.45（**はみ出す**） | 197.75 |
| 320×568（縦） | 1（`swing = 0`） | 18 | 488.5 | 526.7 | 488.5（制限なし） |

影は制限の対象外とする。影の下端は `height * (PADDLE_SCREEN_Y + PADDLE_SHADOW_GAP) + radius * 0.28` であり、320×240 では `234.24px` と Canvas 内に収まる（`depth` が小さいほど上に寄るため、`depth = 1` が最下）。

#### 4.2.7 `stepViewZ`（新規・フェーズB）

```ts
export function stepViewZ(viewZ: number, z: number, dt: number): number;
```

- `moveToward(viewZ, z, P_DEPTH_SPEED * Math.max(0, dt))` を返す。
- 1 ステップの移動量は `P_DEPTH_SPEED * dt` を超えず、目標 `z` を通り越さない（`moveToward` の既存契約）。
- `Game.tick()` はこの関数を呼ぶだけにし、追従ロジックを `Game` 側に書かない（U18 で検証するため）。

#### 4.2.8 `paddleShadowY`（新規・フェーズB）

```ts
export function paddleShadowY(height: number, depth: number): number;
```

- `height * (PADDLE_SCREEN_Y - PADDLE_DEPTH_RISE * (1 - depth)) + height * PADDLE_SHADOW_GAP * (1 - PADDLE_DEPTH_SHRINK * (1 - depth))` を返す。
- 第1項はスイングを含まない基準位置（§4.2.3 の `swing <= 0` 相当）。**影はスイングで上下しない**（現行も固定位置）。
- 第2項の距離が奥ほど縮むため、奥のラケットほど影が近くに寄り、接地感が保たれる。

### 4.3 `Renderer.paddle()` の持ち手（フェーズA・`src/render.ts`）

```ts
private paddle(
  point: ProjectedPoint,
  scale: number,
  color: string,
  angle: number,
): void;
```

描画順（**持ち手を先、ブレードを後**にして根元をブレードで隠す）:

1. `radius = Math.max(6, 9.6 * scale * PADDLE_BLADE_SCALE)`（**定数化のみで値は現行と同一**）。
2. `context.save()` → `translate(point.x, point.y)` → `rotate(angle)`。
3. 持ち手: `roundRect(radius * PADDLE_HANDLE_INSET, -w / 2, radius * PADDLE_HANDLE_LENGTH, w, w * 0.35)` を塗る（`w = radius * PADDLE_HANDLE_WIDTH`）。塗り色 `#7a4a24`、`strokeStyle = "rgba(0,0,0,.35)"` / `lineWidth = Math.max(1, radius * 0.1)` で縁取る。
4. グリップ帯: 持ち手の外側 40% に `rgba(255,255,255,.12)` を重ね、握り部分の質感を出す。
5. `context.restore()`。
6. ブレード（現行の楕円・縁・ハイライト）を**現行のまま**描く。

`roundRect` は既存のプライベートメソッドを再利用する（パス操作のみで構成されており、`translate` / `rotate` 下でも正しく動く）。

### 4.4 `Renderer.drawPlayerPaddle()` の書き換え（フェーズB）

```ts
const swing = player.swing > 0 ? Math.sin(player.swing * Math.PI) : 0;
const depth = paddleDepthRatio(player.viewZ);
const x = this.project(player.x, 0, player.z).x;   // ★ 判定平面。viewZ を使わない
const radius = paddleScreenRadius(this.width, this.height, depth);

  paddleScreenY(this.height, swing, player.swingType, depth),
  this.height,
  radius,

const shadowY = paddleShadowY(this.height, depth);
```

1. **横位置の投影には `player.z` を使う**（§3.3 の不変条件）。`viewZ` を `project()` へ渡してはならない。この結線は §4.8 のソース契約検査で固定する。
2. 影: 中心 `(x, shadowY)`、半径 `(radius * (0.9 - swing * 0.2), radius * 0.28)`、`rgba(0,0,0,alpha)`（`alpha = 0.28 - swing * 0.16`）。**式は現行のまま**で、`radius` と `shadowY` が奥行きに応じて変わる。
3. スマッシュ可能リング（2重円）: 現行のまま。中心 `(x, y)`、半径基準は新しい `radius`。
4. 本体: `this.paddle({ x, y, s: 1 }, radius / 9.6, "#cb4335", paddleHandleAngle(swing, player.swingType))`。
