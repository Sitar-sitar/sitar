## 1. 目的・背景

### 1.1 ラケット表示

現在の `Renderer.drawPlayerPaddle()`（`src/render.ts:532-580`）は、ラケットの投影点から画面下端へ向けて太いグラデーション線を引いている（`src/render.ts:548-565`）。線の終点は `point.x * 0.7 + width * 0.15, height + 20` で、ラケットの位置によらず画面下部のほぼ中央付近へ収束する。このため、**ラケットが画面手前中央から生えた腕の先に付いているように見え、左右に動かしたときに腕が扇状に振れる**。プレイヤー自身の身体は描いていないため、この腕は何を表しているかが分からない要素になっている。

ユーザー要望は「画面下部から分離して動く挙動」。腕の描画をやめ、ラケット単体が画面下部を左右に動く表現へ改める。

### 1.2 プレイヤー名・戦績

現状、プレイヤーは常に `あなた` の固定表記（`index.html:61`）で、試合結果はリロードで消える。同じ端末を家族で共有して遊ぶため、**誰が遊んでいるかを選べること**と、**プレイヤー別に勝敗を残せること**が求められている。

保存先は「この端末内のみ」で確定（2026-07-27 ユーザー確認）。端末間の自動同期は行わない。理由: 現在の公開構成は GitHub Pages の静的ホスティングでサーバを持たず、同期のためだけにバックエンドを新規採用することは CLAUDE.md §2（実績のない技術は実需が出るまで採用しない）に反するため。

## 3. 全体方針

### 3.1 ラケットは「画面下部固定の高さ ＋ ボールと揃う横位置」で描く

- **横位置（x）は現行どおり 3D 投影値を使う**。理由: ボールの投影と同じ変換を通すため、ラケットとボールの横位置が視覚的に一致する。画面幅に対する線形マッピングへ変えると、打点が合っているのに見た目がずれる。
- **縦位置（y）は投影値を捨て、画面高に対する固定比率を基準にする**。ここが「画面下部から分離して動く」の実体。スイング種別（ドライブ／スマッシュ・ツッツキ・押し出し）に応じて基準位置から上下へオフセットする。
- **大きさは投影スケールではなく画面短辺基準の固定値**にする。縦位置を固定した以上、遠近によるサイズ変化は根拠を失うため。
- **接地影を描かず、ラケット直下に薄い楕円のドロップシャドウを置く**。床に接地していない「浮いた道具」であることを示し、腕が無くても宙に浮いて見えないようにする。
- 画面位置の計算は `Renderer` から**純粋関数として切り出し**、単体テストの対象にする。Canvas 描画そのものは自動テストしないため、位置決めロジックだけでもテストできる形にする。

代替案として「3D 投影のまま腕だけ削除」も検討したが、その場合ラケットは台の手前の空中に留まり、ユーザー要望の「画面下部」にはならないため採らない（2026-07-27 ユーザー選択）。

### 3.2 保存は IndexedDB。副作用は `storage.ts` に閉じ、集計・状態遷移は純粋関数に分ける

- `src/storage.ts`（副作用あり・try-catch はここで完結）と `src/stats.ts`（純粋な集計・整列・表示整形・結果表示の状態遷移）に分ける。CLAUDE.md §3（lib＝副作用 / utils＝純粋関数）と §6（lib層で try-catch、UI にはユーザー向けメッセージのみ）に従う。
- IndexedDB は非同期 API であり、ゲームループ（`requestAnimationFrame`）とは独立して動かす。**記録の成否がゲーム進行を止めてはならない**。
- **非同期の完了順に依存する判断はすべて純粋関数へ出す**（§4.6.3 `resolveResultRecord` / `formatResultRecordText`）。Node のテストランナーには IndexedDB も DOM も無いため、順序・世代競合・失敗表示はこの純粋関数の単体テストで決定論的に検証する。`storage.ts` 自体は E2E（実ブラウザ）と手動確認で担保する。

### 3.3 UI はタイトル画面を起点にする

プレイヤーの選択・戦績閲覧・改名・削除は試合中に必要ない。既存のオーバーレイ方式（`.ov` クラス）に合わせて、タイトル画面からプレイヤー管理・戦績の2つのオーバーレイを開く。試合中の HUD は名前の表示だけ。**プレイヤーの変更操作はタイトル画面からのみ可能**とし、試合中にプレイヤーが差し替わる状態を作らない（§4.6.1 の試合スナップショットが成立する前提）。

### 3.4 個人データの扱い

- 保存するのは**ユーザーが自分で入力した表示名と、そのプレイヤーの試合結果**のみ。生年月日・メールアドレス等は扱わない。
- 保存先はブラウザのローカル領域のみ。外部送信は行わない。
- 名前はリポジトリにも設計書にも実装ログにも書かない（CLAUDE.md §8・§9）。テストで使う名前は `テスト太郎` のような架空の固定値にする。
- 名前の描画は `textContent` のみを使い、`innerHTML` を使わない（既存 `src/ui.ts` の方針を踏襲）。

### 3.5 実装の前提（充足済み）

[リファクタリング計画書_2026-07-27](./リファクタリング計画書_2026-07-27.md) の R1〜R5 は `0a8d5f8` で `master` へ統合済みであり、本設計の前提は満たされている。

- `src/utils.ts` が存在する（R2 で作成）。§4.1・§4.3 の純粋関数をここに追加する。
- `src/config.ts` にゲーム定数が集約されている（R4）。§4.1.1 の表示定数もここに追加する。
- `src/game.ts` から AI が分離済み（R5・`src/ai.ts` 171行）。本設計は `game.ts` に試合終了通知を追加するため、先に肥大の解消が済んでいる方が差分が読みやすい。

## 4. 詳細仕様

### 4.1 ラケット表示（Phase A）

#### 4.1.1 追加する定数（`src/config.ts`）

| 定数名 | 値 | 意味 |
|---|---|---|
| `PADDLE_SCREEN_Y` | `0.86` | 画面高に対するラケット中心の基準位置（1.0＝画面下端） |
| `PADDLE_SWING_LIFT` | `0.10` | ドライブ／スマッシュ時に基準位置から上へ動く量（画面高比） |
| `PADDLE_SWING_DROP` | `0.045` | ツッツキ時に下へ動く量（画面高比） |
| `PADDLE_SWING_PUSH` | `0.03` | 押し出し時に上へ動く量（画面高比） |
| `PADDLE_SCREEN_SIZE` | `0.055` | 画面短辺に対するラケット半径 |
| `PADDLE_SIZE_MIN` | `18` | ラケット半径の下限（px） |
| `PADDLE_SIZE_MAX` | `46` | ラケット半径の上限（px） |

値の根拠: 現行の 3D オフセット比（`swing * 26` / `-swing * 14` / `swing * 8`＝ 26 : 14 : 8）を画面高比へ移し替えたもの。実機確認で調整してよい範囲であり、調整した場合は本設計書の §変更履歴に実測値を残す。

#### 4.1.2 追加する純粋関数（`src/utils.ts`）

```ts
export function paddleScreenY(
  height: number,
  swing: number,
  swingType: number,
): number;
```

- `swing` は 0〜1（`PaddleState.swing`）、`swingType` は `1`＝ドライブ／スマッシュ、`-1`＝ツッツキ、`0`＝押し出し。
- 戻り値は画面上の y 座標（px）。
- 仕様: 基準を `height * PADDLE_SCREEN_Y` とし、`swingType === 1` なら `- height * PADDLE_SWING_LIFT * swing`、`swingType === -1` なら `+ height * PADDLE_SWING_DROP * swing`、それ以外は `- height * PADDLE_SWING_PUSH * swing` を加える。
- `swing <= 0` のときは基準位置をそのまま返す。

```ts
export function paddleScreenRadius(width: number, height: number): number;
```

- `clamp(Math.min(width, height) * PADDLE_SCREEN_SIZE, PADDLE_SIZE_MIN, PADDLE_SIZE_MAX)` を返す（`clamp` は R2 で追加済みのもの）。

#### 4.1.3 `drawPlayerPaddle` の書き換え（`src/render.ts`）

変更後の処理順:

1. `const projected = this.project(player.x, 0, player.z)` で**横位置だけ**を得る（第2引数の高さは 0 固定。y は使わない）。
2. `const x = projected.x` / `const y = paddleScreenY(this.height, player.swing, player.swingType)` / `const radius = paddleScreenRadius(this.width, this.height)`。
   - `player.swing` は現行同様 `Math.sin(player.swing * Math.PI)` で山型に整形した値を渡す（`swing` の生値ではない）。
3. ドロップシャドウ: 中心 `(x, this.height * 0.955)`、半径 `(radius * 0.9, radius * 0.28)` の楕円を `rgba(0,0,0,.28)` で塗る。スイングで持ち上がるほど薄く小さくする（`swing` に応じて alpha を `0.28 → 0.12`、横半径を `0.9 → 0.7` へ線形補間）。
4. `scene.smashable` のときのリング2重描画は現行の見た目を維持し、中心を `(x, y)`・半径基準を新しい `radius` に変更する。
5. `this.paddle({ x, y, s: 1 }, radius / 9.6, "#cb4335")` でラケット本体を描く。

   > `Renderer.paddle()` は現行 `radius = Math.max(6, 9.6 * scale * 1.25)` で半径を算出している（`src/render.ts:500`）。**相手ラケットの見た目を変えないため、`paddle()` のシグネチャと式は変更しない**。プレイヤー側は上式で `scale` を逆算して渡す。
6. **削除**: `src/render.ts:548-565` のグラデーション生成とストローク（腕）。`context.lineCap = "round"` の設定もこのブロックとともに削除する。

削除後、`drawPlayerPaddle` は `player.z` を横位置の投影にのみ使う。`player.swing * 8` による奥行き揺らぎ（`src/render.ts:545`）は縦位置を固定した時点で意味を失うため削除する。

#### 4.1.4 ラケットとボールの整合

ラケットの描画位置が変わっても、**打球判定（`Game.playerContact`）は一切変更しない**。判定は 3D 座標（`player.z` 平面と `P_REACH`）で行われており、表示だけを変える。表示と判定のズレはユーザーの操作感に影響するため、§8.4 の実機確認で「ボールがラケットの横位置に重なった瞬間に打てる」ことを確認する。

#### 4.3.1 ID 採番（`createId()`）

`crypto.randomUUID()` は Secure Context 限定である（[W3C Web Cryptography Level 2](https://www.w3.org/TR/webcrypto-2/) / [W3C Secure Contexts](https://www.w3.org/TR/secure-contexts/)）。一方 `README.md:43` は `http://192.168.x.x:3038/` のような LAN IP での実機確認を案内しており、この経路は Secure Context にならない。`crypto.randomUUID` だけに依存すると、LAN 実機確認でプレイヤー作成・試合記録が失敗する。

`createId()` は次の順で採番する。

1. `typeof globalThis.crypto?.randomUUID === "function"` なら `crypto.randomUUID()`。
2. そうでなく `typeof globalThis.crypto?.getRandomValues === "function"` なら、`crypto.getRandomValues(new Uint8Array(16))` を `formatUuidV4()` へ渡す。`getRandomValues` は Secure Context 制限が無く、非HTTPS の LAN IP でも使える。
3. どちらも無ければ `Math.random()` から16バイトを作り `formatUuidV4()` へ渡す（最終フォールバック。衝突確率は本用途で許容する）。

整形は純粋関数として `src/utils.ts` に置き、単体テストの対象にする。

```ts
// utils.ts
export function formatUuidV4(bytes: ArrayLike<number>): string;
```

- 16要素未満なら `Error("UUIDには16バイトが必要です。")` を投げる。
- 各バイトを `& 0xff` した上で、7バイト目の上位4ビットを `0100`（version 4）、9バイト目の上位2ビットを `10`（variant）に強制する。
- `8-4-4-4-12` の小文字16進文字列を返す。同じ入力からは常に同じ出力を返す（決定論的）。

#### 4.3.2 名前の正規化・検証

`src/utils.ts` に純粋関数を置き、**保存層と UI が同じ関数を使う**。

```ts
// utils.ts
export function normalizePlayerName(raw: string): string;
```

- `raw.trim()` を返す。
- 契約は **Unicode コードポイント数で1〜12**（`[...name].length` で数える）。範囲外なら `Error("名前は1〜12文字で入力してください。")` を投げる。
- `index.html` の入力要素には `maxlength` を**付けない**。`maxlength` は UTF-16 コード単位で制限するため、サロゲートペアを含む絵文字が保存層へ届く前に2文字相当として弾かれ、UI と保存層で「12文字」の意味が食い違うため。
- 結合文字（例: `か` ＋ 濁点）は合成されない限り2コードポイントとして数える。書記素クラスタ（`Intl.Segmenter`）は採用しない。理由: 実装差とテスト負荷が増える割に、この用途では利益が小さい。この割り切りを仕様として明記する。

`StatsStore.addPlayer` / `renamePlayer` は先頭で `normalizePlayerName()` を呼び、正規化後の名前を保存する。重複（`name` インデックスの制約違反）は `Error("同じ名前のプレイヤーがすでにいます。")` に変換して投げる。**UI にはこのメッセージだけを見せ、DOMException をそのまま出さない**（CLAUDE.md §6）。

#### 4.3.3 一覧の標準順

主キーはランダム ID のため、object store の主キー順は作成順にならない。`listPlayers()` と、`PlayerSelection.players` を返すすべての API は次の**標準順**で返す。

```ts
// stats.ts（純粋関数）
export function sortPlayers(players: readonly PlayerRecord[]): PlayerRecord[];
```

- 第1キー: `createdAt` 昇順（ISO 8601 の辞書順で比較する）
- 第2キー: `id` 昇順（同時刻の決定論的な決着）
- 入力配列を破壊しない（`slice()` してから並べ替える）。

「先頭のプレイヤー」「代替プレイヤー」はすべてこの標準順の先頭を指す。

#### 4.3.4 各 API の契約

| API | 契約 |
|---|---|
| `open()` | IndexedDB が使えない場合（`indexedDB` が未定義、`open` が例外を投げる、`onerror`、`onblocked`）に **例外を投げず `null` を返す**。呼び出し側（`main.ts`）は `null` を「戦績機能なしモード」として扱う |
| `listPlayers()` | 標準順（§4.3.3）で全件返す |
| `addPlayer(name)` | 正規化・検証 → `createId()` で採番 → `players` へ `add`。作成した `PlayerRecord` を返す |
| `renamePlayer(id, name)` | 正規化・検証 → 対象が存在しなければ `Error("プレイヤーが見つかりません。")` → `put`。更新後の `PlayerRecord` を返す |
| `deletePlayer(id)` | §4.3.5 |
| `getSelectedPlayerId()` | `settings` の `selectedPlayerId` を返す。未設定なら `null` |
| `setSelectedPlayerId(id)` | `settings` へ `put`。存在しない `id` は `Error("プレイヤーが見つかりません。")` |
| `ensureSelection()` | §4.3.6 |
| `recordMatch(record)` | `players` に `record.playerId` が**存在することを同一トランザクション内で検証**し、無ければ `Error("記録先のプレイヤーが見つかりません。")`。存在すれば `createId()` で採番して `matches` へ `add` し、保存した `MatchRecord` を返す。IndexedDB には外部キー制約が無いため、この検証が孤児レコードの唯一の防波堤になる |
| `listMatches(playerId)` | `playerId` インデックスで全件取得し、`playedAt` の**新しい順**に並べて返す |

#### 4.3.5 `deletePlayer(id)`：削除・代替選択・設定更新を1トランザクションで完結させる

**プレイヤーを削除すると、そのプレイヤーの戦績（`matches`）も一緒に削除する**（2026-07-28 ユーザー確認・§10-1）。参照先の無い孤児データを残さないため。**削除は取り消せない**ので、UI 側で2段階の確認を置く（§4.5.3）。

`["players", "matches", "settings"]` の `readwrite` トランザクション1本で、次の順に実行する。

1. `players` の件数を数える。1件なら中断し `Error("最後のプレイヤーは削除できません。")` を投げる（選択中プレイヤーが存在しない状態を作らないため）。
2. 対象が存在しなければ中断し `Error("プレイヤーが見つかりません。")` を投げる。
3. `players.delete(id)`。
4. `matches` の `playerId` インデックスをカーソルで走査し、該当レコードを全削除する。
5. `settings.selectedPlayerId` が削除対象と一致する場合のみ、残ったプレイヤーを §4.3.3 の標準順に並べた**先頭**を `settings` へ `put` する。一致しない場合は `settings` を変更しない。
6. トランザクション完了後に `{ players: 残った一覧（標準順）, selectedPlayerId: 更新後の選択ID }` を返す。

呼び出し側（`main.ts`）は返却値だけを使って UI と `Game` を更新する。**削除後に別途 `listPlayers()` を読み直さない**（読み直しの間に別操作が挟まる余地を作らないため）。

#### 4.3.6 `ensureSelection()`：起動時の選択確定

起動フロー（§4.7）で必要な「0人ならゲスト作成」「無効な選択IDなら先頭へ寄せる」を保存層の1メソッドに閉じ込め、判断がUI側に散らないようにする。

1. `listPlayers()` を読む。
2. 0人なら `addPlayer("ゲスト")` で自動作成する（2026-07-28 ユーザー確認・§10-4）。名前は後から改名できる。
3. `getSelectedPlayerId()` を読む。`null`、または一覧に存在しない ID なら、標準順の先頭を選択し `setSelectedPlayerId()` で `settings` を更新する。
4. `{ players, selectedPlayerId }` を返す。

#### 4.5.3 プレイヤー一覧の行と操作

各行は3つのモードを持ち、モード切り替えは `Ui` 内で完結する（DOM 操作のみ）。**確定操作のときだけ `PlayerUiHandlers` を呼ぶ**。同時にモードを持てる行は1つだけで、他の行は表示モードへ戻す。

| モード | 表示 | 操作 |
|---|---|---|
| 表示（既定） | 名前ボタン（選択中は `aria-current="true"`）／`改名`／`削除` | 名前ボタン → `select(id)`。`改名` → 改名モード。`削除` → 削除確認モード |
| 改名 | `input[type=text]`（初期値＝現在の名前）／`保存`／`やめる` | `input` に `focus()` と `select()` を行う。`保存` または Enter → `rename(id, 入力値)`。`やめる` または Escape → 表示モードへ戻す（保存層は呼ばない） |

- 改名入力に `maxlength` は付けない。検証は確定時に `normalizePlayerName()` で行い、エラーは `#playerError` に出す（§4.3.2）。

- 難易度別: `初級` / `中級` / `上級` それぞれの試合数と勝数（0件でも行を出す）

- 0件のときは通算欄に `記録なし` を出す

### 4.6 ゲーム側の記録連携（Phase B）

#### 4.6.1 責務の分離

**`Game` は保存層（`StatsStore`）を一切参照しない。**

| 担当 | 責務 |
|---|---|
| `Game` | 試合の進行、試合スナップショット（`MatchResult`）の確定、`onMatchEnd` 通知、`RESULT_DELAY_MS` 後の結果画面表示 |
| `main.ts` | `StatsStore` の生成、保存、再集計、`Ui.setResultRecord()` / `Ui.updatePlayerBar()` の呼び出し |
| `Ui` | 結果画面の描画。保存状態の表示は世代（`matchSeq`）で照合して反映する |

理由: 保存の成否・完了順は `Game` の関心ではなく、`Game` が保存層を持つと「結果表示の所有者」が2か所になる。

#### 4.6.2 `src/game.ts` の変更

1. `GameState` に `maxRally: number` を追加する。更新規則は次のとおりで、**`startServe()` は `maxRally` に触れない**。
   - `point()` の冒頭（得点を加算する前）で `this.state.maxRally = Math.max(this.state.maxRally, this.state.rally)` を実行する。
   - `newGame()` で `this.state.rally = 0` と `this.state.maxRally = 0` を**明示的に**セットしてから `startServe()` を呼ぶ。現行 `newGame()` は `rally` をリセットせずに `startServe()` を呼ぶため、この明示リセットが無いと前試合の最終 `rally` が新試合へ持ち越される。
   - `startServe()` は従来どおり `this.state.rally = 0` のみを行う。
2. `Game` に次のフィールドを持つ。
   - `matchSeq: number`（`newGame()` ごとに +1。結果表示の世代番号）
   - `matchPlayer: PlayerRecord | null`（**試合開始時に固定**した対戦プレイヤー）
   - `matchStartedAt: number`（`performance.now()`）/ `matchStartedAtIso: string`
   - `currentPlayer: PlayerRecord | null`（`setPlayer()` が書き込む「次の試合で使うプレイヤー」）
3. `public setPlayer(player: PlayerRecord | null): void` を追加する。コンストラクタ引数ではなくセッターにする理由: `StatsStore.open()` は非同期であり、ゲームの生成をその完了まで待たせないため。**`setPlayer()` は進行中の試合には影響しない**（`matchPlayer` は `newGame()` でのみ固定される）。§3.3 によりプレイヤー変更操作はタイトル画面限定のため、試合中に差し替わることはない。
4. `newGame()` で `matchSeq += 1` / `matchPlayer = currentPlayer` / `matchStartedAt` / `matchStartedAtIso` を確定する。
5. `public onMatchEnd?: (result: MatchResult) => void;` を追加する。`point()` 内で `isGameOver()` が真になった時点で、**結果表示タイマーより先に同期的に**スナップショットを確定して通知する。

```ts
// types.ts
export interface MatchResult {
  matchSeq: number;
  playerId: string | null;
  playerName: string | null;
  level: LevelId;
  won: boolean;
  scoreP: number;
  scoreA: number;
  maxRally: number;
  startedAt: string;    // 試合開始時刻 ISO 8601
  playedAt: string;     // 試合終了時刻 ISO 8601
  durationSec: number;  // 0 以上の整数
}
```

```ts
// game.ts（point() の末尾）
if (isGameOver(this.state.scP, this.state.scA)) {
  this.state.phase = "over";
  const seq = this.matchSeq;
  this.onMatchEnd?.(this.buildMatchResult());
  window.setTimeout(() => {
    if (this.state.phase === "over" && this.matchSeq === seq) {
      this.cancelServeTimer();
      this.ui.showResult(this.state, seq);
    }
  }, RESULT_DELAY_MS);
}
```

- `matchSeq === seq` の確認を追加する理由: 古い試合のタイマーが、次の試合の結果画面を上書きしないようにするため。
- 途中でタイトルへ戻った試合（`backToTitle()`）は `onMatchEnd` を呼ばない。**決着した試合だけを記録する**。
- `buildMatchResult()` は `matchPlayer` から `playerId` / `playerName` を取り、`durationSec` は `Math.max(0, Math.round((performance.now() - this.matchStartedAt) / 1000))` とする。

#### 4.6.3 結果画面の保存状態表示（順序と世代の契約）

```ts
// types.ts
export type RecordStatus = "unavailable" | "pending" | "saved" | "failed";
export interface ResultRecord {
  matchSeq: number;
  status: RecordStatus;
  label: string;   // status === "saved" のときだけ意味を持つ
}
```

```ts
// stats.ts（純粋関数）
export function resolveResultRecord(
  current: ResultRecord | null,
  incoming: ResultRecord,
): ResultRecord {
  if (current !== null && incoming.matchSeq < current.matchSeq) {
    return current;               // 古い試合の遅延完了を破棄する
  }
  return incoming;
}

export function formatResultRecordText(
  record: ResultRecord | null,
  matchSeq: number,
): string;
```

`formatResultRecordText` の対応表:

| 条件 | 文言 |
|---|---|
| `record === null` または `record.matchSeq !== matchSeq` | `""`（何も出さない） |
| `unavailable` | `この端末では戦績を保存できません` |
| `pending` | `戦績を保存しています…` |
| `saved` | `record.label`（例 `テスト太郎 の通算 5勝3敗`） |
| `failed` | `戦績を保存できませんでした` |

`Ui` 側の保持と反映:

```ts
public showResult(state: GameState, matchSeq: number): void;  // 既存シグネチャに引数を1つ追加
public setResultRecord(record: ResultRecord): void;
```

- `Ui` は `resultRecord: ResultRecord | null`（既定 `null`）と `resultSeq: number`（既定 `-1`）を持つ。
- `setResultRecord(record)` は `resultRecord = resolveResultRecord(resultRecord, record)` を代入し、`#rRecord.textContent = formatResultRecordText(resultRecord, resultSeq)` を実行する。
- `showResult(state, matchSeq)` は既存の描画に加えて `resultSeq = matchSeq` を代入し、同じ整形を実行する。
- これにより、**保存完了が結果表示より早くても遅くても同じ表示になる**。表示前に届いた結果は `resultRecord` に保持され、`showResult` 時に反映される。

#### 4.6.4 試合終了時のシーケンス（`main.ts`）

`main.ts` は `game.onMatchEnd` に次の処理を結線する。`await` を挟むが**ゲームループは待たない**。

| # | 条件 | 動作 |
|---|---|---|
| 1 | `statsPhase !== "ready"`、`store === null`、または `result.playerId === null` | `setResultRecord({ matchSeq, status: "unavailable", label: "" })` して終了 |
| 2 | 上記以外 | `setResultRecord({ matchSeq, status: "pending", label: "" })` を**同期的に**呼ぶ（結果表示より必ず先） |
| 3 | `store.recordMatch(...)` 成功 | `store.listMatches(playerId)` → `summarize()` → `setResultRecord({ matchSeq, status: "saved", label: "<名前> の通算 <formatRecordLabel>" })`。`result.playerId` が現在の選択プレイヤーと一致する場合のみ `ui.updatePlayerBar()` も更新する |
| 4 | `recordMatch` または再集計が失敗 | `setResultRecord({ matchSeq, status: "failed", label: "" })`。`#playerBar` は変更しない。ゲームは継続する |

順序ごとの期待表示:

| 順序 | 結果画面の `#rRecord` |
|---|---|
| 保存完了 → 結果表示 | `<名前> の通算 …`（`showResult` 時に反映） |
| 結果表示 → 保存完了 | `戦績を保存しています…` → `<名前> の通算 …` |
| 保存不可（戦績機能なし） | `この端末では戦績を保存できません` |
| 保存失敗 | `戦績を保存しています…` → `戦績を保存できませんでした` |
| 保存中に「もう一度」→ 次試合が先に決着 | 古い `matchSeq` の完了は `resolveResultRecord` が破棄し、新しい試合の表示を上書きしない |

### 4.7 起動時の流れ（`src/main.ts`）

1. `Game` を生成してループを開始する（従来どおり。戦績の準備を待たない）。`ui.setStatsPhase("loading")` を呼び、プレイヤー・戦績のボタンを無効にしておく。
2. 次の一連を**1つの `try/catch` 境界**で実行する（`bootstrapStats()`）。
   1. `StatsStore.open()`。`null` なら `unavailable` へ。
   2. `store.ensureSelection()`（§4.3.6。0人ならゲスト自動作成、無効な選択IDなら標準順の先頭へ寄せて `settings` を更新）。
   3. 選択中プレイヤーの `store.listMatches()` → `summarize()`。
   4. `ui.updatePlayerBar(name, stats)` / `game.setPlayer(player)` / `ui.setStatsPhase("ready")`。
3. 上記のどこで失敗しても `catch` で `ui.setStatsPhase("unavailable")` と `game.setPlayer(null)` を実行する。HUD 名は既定の `あなた` のままにする。**`open()` の失敗だけでなく、初回読込・ゲスト作成・初回集計の失敗も同じ経路でフォールバックする。**
4. 初期化完了後の個別操作（追加・選択・改名・削除・記録）の失敗は、フォールバックへ落とさずゲームを継続する。
   - `ui.setPlayerError(message)` にユーザー向け文言を出す。
   - **保存済みの状態を `store.listPlayers()` と `store.getSelectedPlayerId()` で取り直して UI を再描画する**（楽観的更新を残さない）。
   - 取り直しにも失敗した場合のみ `ui.setStatsPhase("unavailable")` へ落とす。
5. すべての非同期操作は開始時に `ui.setPlayersBusy(true)`、終了時（成功・失敗とも）に `ui.setPlayersBusy(false)` を呼ぶ。

CRUD 操作の状態遷移（成功時）:

| 操作 | 保存層 | `settings` | `Game` | DOM |
|---|---|---|---|---|
| 追加 | `addPlayer(name)` | 変更なし | 変更なし | `#playerList` 再描画、`#playerInput` を空に、`#playerError` を空に |
| 選択 | `setSelectedPlayerId(id)` | 更新 | `setPlayer(player)` | `#playerList` 再描画、`updatePlayerBar(name, stats)`（`#playerName` / `#playerRecord` / `#hudPlayerName`） |
| 改名 | `renamePlayer(id, name)` | 変更なし | 選択中なら `setPlayer(更新後)` | `#playerList` 再描画、選択中なら `updatePlayerBar` |
| 削除 | `deletePlayer(id)` → `PlayerSelection` | 選択中を削除した場合のみ更新（保存層が実施） | 返却値の選択IDのプレイヤーで `setPlayer()` | 返却値で `#playerList` 再描画、`updatePlayerBar` |

削除の順序は「保存層で削除・代替選択・`settings` 更新を1トランザクションで完了 → 返却値で `Game` と DOM を更新」で固定する。DOM を先に更新しない。

### 4.8 Service Worker（Phase B）

`sw.js` の `CACHE_NAME` を `table-tennis-v2` → `table-tennis-v3` に更新する。`APP_SHELL` の内容（ファイル名）は変わらないため、`scripts/check-app.mjs:74-88` の検査は現行のまま通る。キャッシュ名を上げないと、既存ユーザーの端末に旧 UI が残る。
