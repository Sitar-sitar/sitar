# 設計書：プレイヤー名の設定・プレイヤー別戦績の記録・プレイヤーラケットの表示改修

プレイヤーラケットが画面手前中央から腕のように伸びて見える描画を、画面下部で分離して動く表現へ改める。あわせて、この端末で遊ぶ人をプレイヤーとして登録・選択できるようにし、試合結果をプレイヤー別に記録して振り返れるようにする。バックエンドを持たない現在の公開構成（GitHub Pages）を維持したまま、記録はブラウザの IndexedDB に保存する。

## 1. 目的・背景

### 1.1 ラケット表示

現在の `Renderer.drawPlayerPaddle()`（`src/render.ts:532-580`）は、ラケットの投影点から画面下端へ向けて太いグラデーション線を引いている（`src/render.ts:548-565`）。線の終点は `point.x * 0.7 + width * 0.15, height + 20` で、ラケットの位置によらず画面下部のほぼ中央付近へ収束する。このため、**ラケットが画面手前中央から生えた腕の先に付いているように見え、左右に動かしたときに腕が扇状に振れる**。プレイヤー自身の身体は描いていないため、この腕は何を表しているかが分からない要素になっている。

ユーザー要望は「画面下部から分離して動く挙動」。腕の描画をやめ、ラケット単体が画面下部を左右に動く表現へ改める。

### 1.2 プレイヤー名・戦績

現状、プレイヤーは常に `あなた` の固定表記（`index.html:61`）で、試合結果はリロードで消える。同じ端末を家族で共有して遊ぶため、**誰が遊んでいるかを選べること**と、**プレイヤー別に勝敗を残せること**が求められている。

保存先は「この端末内のみ」で確定（2026-07-27 ユーザー確認）。端末間の自動同期は行わない。理由: 現在の公開構成は GitHub Pages の静的ホスティングでサーバを持たず、同期のためだけにバックエンドを新規採用することは CLAUDE.md §2（実績のない技術は実需が出るまで採用しない）に反するため。

## 3. 全体方針

### 3.1 ラケットは「画面下部固定の高さ ＋ ボールと揃う横位置」で描く

- **横位置（x）は現行どおり 3D 投影値を使う**。理由: ボールの投影と同じ変換を通すため、ラケットとボールの横位置が視覚的に一致する。画面幅に対する線形マッピングへ変えると、打点が合っているのに見た目がずれる。
- **縦位置（y）は投影値を捨て、画面高に対する固定比率を基準にする**。ここが「画面下部から分離して動く」の実体。スイング種別（ドライブ／スマッシュ・ツッツキ・押し出し）に応じて基準位置から上下へオフセットする。
- **大きさは投影スケールではなく画面短辺基準の固定値**にする。縦位置を固定した以上、遠近によるサイズ変化は根拠を失うため。
- **接地影を描かず、ラケット直下に薄い楕円のドロップシャドウを置く**。床に接地していない「浮いた道具」であることを示し、腕が無くても宙に浮いて見えないようにする。
- 画面位置の計算は `Renderer` から**純粋関数として切り出し**、単体テストの対象にする。Canvas 描画そのものは自動テストしないため、位置決めロジックだけでもテストできる形にする。

代替案として「3D 投影のまま腕だけ削除」も検討したが、その場合ラケットは台の手前の空中に留まり、ユーザー要望の「画面下部」にはならないため採らない（2026-07-27 ユーザー選択）。

### 3.2 保存は IndexedDB。副作用は `storage.ts` に閉じ、集計は純粋関数に分ける

- `src/storage.ts`（副作用あり・try-catch はここで完結）と `src/stats.ts`（純粋な集計のみ）に分ける。CLAUDE.md §3（lib＝副作用 / utils＝純粋関数）と §6（lib層で try-catch、UI にはユーザー向けメッセージのみ）に従う。
- IndexedDB は非同期 API であり、ゲームループ（`requestAnimationFrame`）とは独立して動かす。**記録の成否がゲーム進行を止めてはならない**。試合結果の書き込みは「撃ちっぱなし（失敗しても続行）」とし、失敗時は結果画面に1行の注意文を出すだけにする。
- Node のテストランナーには IndexedDB が無いため、**単体テストは `stats.ts` の集計関数に対して行う**。`storage.ts` は E2E と手動確認で担保する。

### 3.3 UI はタイトル画面を起点にする

プレイヤーの選択・戦績閲覧は試合中に必要ない。既存のオーバーレイ方式（`.ov` クラス）に合わせて、タイトル画面からプレイヤー管理・戦績の2つのオーバーレイを開く。試合中の HUD は名前の表示だけ。

### 3.4 個人データの扱い

- 保存するのは**ユーザーが自分で入力した表示名と、そのプレイヤーの試合結果**のみ。生年月日・メールアドレス等は扱わない。
- 保存先はブラウザのローカル領域のみ。外部送信は行わない。
- 名前はリポジトリにも設計書にも実装ログにも書かない（CLAUDE.md §8・§9）。テストで使う名前は `テスト太郎` のような架空の固定値にする。
- 名前の描画は `textContent` のみを使い、`innerHTML` を使わない（既存 `src/ui.ts` の方針を踏襲）。

### 3.5 実装順序

**[リファクタリング計画書_2026-07-27](./リファクタリング計画書_2026-07-27.md) の R1〜R5 を完了してから本設計に着手する。** 本設計は次の前提に依存する。

- `src/utils.ts` が存在する（R2 で作成）。§4.1 の純粋関数をここに追加する。
- `src/config.ts` にゲーム定数が集約されている（R4）。§4.1 の表示定数もここに追加する。
- `src/game.ts` から AI が分離済み（R5）。本設計は `game.ts` に試合結果の記録処理を追加するため、先に肥大の解消が済んでいる方が差分が読みやすい。

## 4. 詳細仕様

### 4.1 ラケット表示（Phase A）

#### 4.1.1 追加する定数（`src/config.ts`）

| 定数名 | 値 | 意味 |
|---|---|---|
| `PADDLE_SCREEN_Y` | `0.86` | 画面高に対するラケット中心の基準位置（1.0＝画面下端） |
| `PADDLE_SWING_LIFT` | `0.10` | ドライブ／スマッシュ時に基準位置から上へ動く量（画面高比） |
| `PADDLE_SWING_DROP` | `0.045` | ツッツキ時に下へ動く量（画面高比） |
| `PADDLE_SWING_PUSH` | `0.03` | 押し出し時に上へ動く量（画面高比） |
| `PADDLE_SCREEN_SIZE` | `0.055` | 画面短辺に対するラケット半径 |
| `PADDLE_SIZE_MIN` | `18` | ラケット半径の下限（px） |
| `PADDLE_SIZE_MAX` | `46` | ラケット半径の上限（px） |

値の根拠: 現行の 3D オフセット比（`swing * 26` / `-swing * 14` / `swing * 8`＝ 26 : 14 : 8）を画面高比へ移し替えたもの。実機確認で調整してよい範囲であり、調整した場合は本設計書の §変更履歴に実測値を残す。

#### 4.1.2 追加する純粋関数（`src/utils.ts`）

```ts
export function paddleScreenY(
  height: number,
  swing: number,
  swingType: number,
): number;
```

- `swing` は 0〜1（`PaddleState.swing`）、`swingType` は `1`＝ドライブ／スマッシュ、`-1`＝ツッツキ、`0`＝押し出し。
- 戻り値は画面上の y 座標（px）。
- 仕様: 基準を `height * PADDLE_SCREEN_Y` とし、`swingType === 1` なら `- height * PADDLE_SWING_LIFT * swing`、`swingType === -1` なら `+ height * PADDLE_SWING_DROP * swing`、それ以外は `- height * PADDLE_SWING_PUSH * swing` を加える。
- `swing <= 0` のときは基準位置をそのまま返す。

```ts
export function paddleScreenRadius(width: number, height: number): number;
```

- `clamp(Math.min(width, height) * PADDLE_SCREEN_SIZE, PADDLE_SIZE_MIN, PADDLE_SIZE_MAX)` を返す（`clamp` は R2 で追加済みのもの）。

#### 4.1.3 `drawPlayerPaddle` の書き換え（`src/render.ts`）

変更後の処理順:

1. `const projected = this.project(player.x, 0, player.z)` で**横位置だけ**を得る（第2引数の高さは 0 固定。y は使わない）。
2. `const x = projected.x` / `const y = paddleScreenY(this.height, player.swing, player.swingType)` / `const radius = paddleScreenRadius(this.width, this.height)`。
3. ドロップシャドウ: 中心 `(x, this.height * 0.955)`、半径 `(radius * 0.9, radius * 0.28)` の楕円を `rgba(0,0,0,.28)` で塗る。スイングで持ち上がるほど薄く小さくする（`swing` に応じて alpha を `0.28 → 0.12`、横半径を `0.9 → 0.7` へ線形補間）。
4. `scene.smashable` のときのリング2重描画は現行の見た目を維持し、中心を `(x, y)`・半径基準を新しい `radius` に変更する。
5. `this.paddle({ x, y, s: 1 }, radius / 9.6, "#cb4335")` でラケット本体を描く。

   > `Renderer.paddle()` は現行 `radius = Math.max(6, 9.6 * scale * 1.25)` で半径を算出している（`src/render.ts:500`）。**相手ラケットの見た目を変えないため、`paddle()` のシグネチャと式は変更しない**。プレイヤー側は上式で `scale` を逆算して渡す。
6. **削除**: `src/render.ts:548-565` のグラデーション生成とストローク（腕）。`context.lineCap = "round"` の設定もこのブロックとともに削除する。

削除後、`drawPlayerPaddle` は `player.z` を横位置の投影にのみ使う。`player.swing * 8` による奥行き揺らぎ（`src/render.ts:545`）は縦位置を固定した時点で意味を失うため削除する。

#### 4.1.4 ラケットとボールの整合

ラケットの描画位置が変わっても、**打球判定（`Game.playerContact`）は一切変更しない**。判定は 3D 座標（`player.z` 平面と `P_REACH`）で行われており、表示だけを変える。表示と判定のズレはユーザーの操作感に影響するため、§8 の実機確認で「ボールがラケットの横位置に重なった瞬間に打てる」ことを確認する。

### 4.3 保存層（`src/storage.ts`・Phase B）

```ts
export interface PlayerRecord { id: string; name: string; createdAt: string; }
export interface MatchRecord {
  id: string; playerId: string; playedAt: string; level: LevelId;
  won: boolean; scoreP: number; scoreA: number; maxRally: number; durationSec: number;
}

export class StatsStore {
  public static async open(): Promise<StatsStore | null>;
  public listPlayers(): Promise<PlayerRecord[]>;
  public addPlayer(name: string): Promise<PlayerRecord>;
  public renamePlayer(id: string, name: string): Promise<void>;
  public deletePlayer(id: string): Promise<void>;
  public getSelectedPlayerId(): Promise<string | null>;
  public setSelectedPlayerId(id: string): Promise<void>;
  public recordMatch(record: Omit<MatchRecord, "id">): Promise<void>;
  public listMatches(playerId: string): Promise<MatchRecord[]>;
}
```

仕様:

- `open()` は IndexedDB が使えない場合（`indexedDB` が未定義、プライベートブラウジングで拒否、`onerror`）に **例外を投げず `null` を返す**。呼び出し側（`main.ts`）は `null` を「戦績機能なしモード」として扱う。
- 名前の正規化と検証はこの層で行う。`name.trim()` が空、または 12 文字超（`[...name].length` で数える。絵文字を1文字として数えるため）なら `Error("名前は1〜12文字で入力してください。")` を投げる。重複（`name` インデックスの制約違反）は `Error("同じ名前のプレイヤーがすでにいます。")` に変換して投げる。**UI にはこのメッセージだけを見せ、DOMException をそのまま出さない**（CLAUDE.md §6）。
- `deletePlayer(id)` は同一トランザクションで `matches` の該当 `playerId` のレコードも削除する。**削除は取り消せない**ため、UI 側で確認ステップを置く（§4.5）。
- `recordMatch` の失敗は例外を投げるが、呼び出し側（`Game`）は catch して進行を止めない（§4.6）。
- 最後の1人になったプレイヤーは削除できない（`Error("最後のプレイヤーは削除できません。")`）。選択中プレイヤーが存在しない状態を作らないため。

### 4.4 集計（`src/stats.ts`・Phase B）

副作用なし。単体テストの対象。

```ts
export interface LevelSummary { matches: number; wins: number; }
export interface PlayerStats {
  matches: number;
  wins: number;
  losses: number;
  winRate: number;                       // 0〜1。matches が 0 のときは 0
  maxRally: number;                      // 全試合の最大。0 件なら 0
  byLevel: Record<LevelId, LevelSummary>;
  recent: MatchRecord[];                 // playedAt の新しい順に最大10件
}

export function summarize(matches: readonly MatchRecord[]): PlayerStats;
export function formatRecordLabel(stats: PlayerStats): string;  // 例: "5勝3敗"
```

- `summarize` は入力配列を破壊しない（`slice()` してから並べ替える）。
- `byLevel` は `easy` / `mid` / `hard` の3キーを常に持つ（該当試合が無くても `{ matches: 0, wins: 0 }`）。
- `winRate` は小数のまま返し、表示側で百分率に整形する（丸めの責務を表示に寄せる）。

- `setStatsAvailable(false)` のとき、`#openPlayers` と `#openStats` を `disabled` にし、`#playerBar` に `この端末では戦績を保存できません。` を表示する。ゲーム本体は通常どおり遊べる。
- 既存メソッドのシグネチャは変更しない。

#### 4.5.3 結果画面

`Ui.showResult()` に引数を1つ増やし（`recordLabel: string`）、`#rSub` の既存文言の後ろに `／ <名前> の通算 5勝3敗` を追記する。記録に失敗した場合は `／ 戦績を保存できませんでした` を出す。

### 4.6 ゲーム側の記録連携（Phase B・`src/game.ts`）

1. `GameState` に `maxRally: number` を追加する。`startServe()` で `rally` を 0 に戻す直前に `maxRally = Math.max(maxRally, rally)` を更新し、`newGame()` で `maxRally = 0` にリセットする。
2. `Game` に `matchStartedAt: number`（`performance.now()`）を持ち、`newGame()` で更新する。
3. `Game` は `StatsStore | null` と「現在のプレイヤー」をコンストラクタ経由ではなく**セッター**で受け取る（`setPlayer(player: PlayerRecord | null)` / `setStore(store: StatsStore | null)`）。理由: `StatsStore.open()` は非同期であり、ゲームの生成をその完了まで待たせないため。
4. `point()` 内で `isGameOver()` が真になったとき、結果表示のタイマー（`RESULT_DELAY_MS`）とは独立に記録を実行する。

```ts
private recordMatchResult(): void {
  const store = this.store;
  const player = this.player;
  if (!store || !player) { return; }
  void store
    .recordMatch({
      playerId: player.id,
      playedAt: new Date().toISOString(),
      level: this.state.level,
      won: this.state.scP > this.state.scA,
      scoreP: this.state.scP,
      scoreA: this.state.scA,
      maxRally: Math.max(this.state.maxRally, this.state.rally),
      durationSec: Math.round((performance.now() - this.matchStartedAt) / 1000),
    })
    .then(() => { this.onRecorded?.(true); })
    .catch(() => { this.onRecorded?.(false); });
}
```

5. 記録の成否は `onRecorded` コールバックで `main.ts` へ返し、`main.ts` が最新の集計を取り直して結果画面と `#playerBar` を更新する。**ゲームループは記録の完了を待たない**。
6. 途中でタイトルへ戻った試合（`backToTitle()`）は記録しない。決着した試合だけを記録する。

### 4.7 起動時の流れ（`src/main.ts`）

1. `Game` を生成してループを開始する（従来どおり。戦績の準備を待たない）。
2. `StatsStore.open()` を実行する。
   - `null`（利用不可）: `ui.setStatsAvailable(false)` を呼んで終了。ゲームは通常動作。
   - 成功: プレイヤー一覧を読む。
3. プレイヤーが0人なら `ゲスト` を自動作成して選択する。名前は後から改名できる。
4. `settings.selectedPlayerId` が有効なら、そのプレイヤーを選択する。無効（削除済み等）なら先頭のプレイヤーを選択して `settings` を更新する。
5. 選択中プレイヤーの集計を取り、`ui.updatePlayerBar()` と HUD 名を更新し、`game.setPlayer()` / `game.setStore()` を呼ぶ。

### 4.8 Service Worker（Phase B）

`sw.js` の `CACHE_NAME` を `table-tennis-v2` → `table-tennis-v3` に更新する。`APP_SHELL` の内容（ファイル名）は変わらないため、`scripts/check-app.mjs:74-88` の検査は現行のまま通る。キャッシュ名を上げないと、既存ユーザーの端末に旧 UI が残る。

## 8. テスト・検証

### 8.1 単体テスト（`tests/game-core.test.ts` に追加）
