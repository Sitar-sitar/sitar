**この段階で確定した内容（コード変更はまだ行っていない）**

- 初回設計レビューの全10件（P1 2件・P2 5件・P3 3件）を機能設計書へ反映した。主な確定事項は次のとおり。
  1. 試合終了 → 保存 → 集計 → 結果表示の所有者を分離した。`Game` は保存層を参照せず、試合スナップショット `MatchResult` を `onMatchEnd` で通知するだけにする。保存と再集計は `main.ts`、表示は `Ui` が担当する。
  2. 結果画面の保存状態を `unavailable` / `pending` / `saved` / `failed` の4値にし、`matchSeq` による世代照合と純粋関数 `resolveResultRecord` / `formatResultRecordText` で、保存完了と結果表示のどちらが先でも、また「もう一度」で次試合が始まっても表示が壊れないようにした。
  3. プレイヤーCRUDの状態遷移（保存層 → `settings` → `Game` → DOM）を表で確定した。`deletePlayer` は削除・戦績の連鎖削除・代替選択・`settings` 更新を単一トランザクションで完結させ、`recordMatch` は同一トランザクションでプレイヤー存在を検証して孤児レコードを防ぐ。
  4. `maxRally` の更新を `point()` へ移し、`newGame()` で `rally` / `maxRally` を明示リセットする。現行実装のままでは前試合の最終ラリーが次試合へ持ち越される。
  5. 戦績機能の状態を `loading` / `ready` / `unavailable` の3状態にし、`open` から初回集計までを単一 try/catch 境界へ入れた。初期化後の個別失敗はゲームを継続し、保存済み状態を再取得して復元する。
  6. ID採番を `crypto.randomUUID` → `crypto.getRandomValues` → `Math.random` の多段フォールバックにした。`randomUUID` は Secure Context 限定のため、README が案内する非HTTPSのLAN実機確認で失敗するため。
  7. 実装単位を「1ファイルごとに `npm run check`」から「常に型検査が通る垂直スライス S1〜S7」へ変更した。型が壊れる変更（`GameState.maxRally` の必須化、`Ui.showResult()` の引数追加）を参照側と同じスライスに入れる。
  8. 表示名の上限を Unicode コードポイント1〜12に統一し、`maxlength` を廃止した。型の正本を `types.ts` に一元化し、プレイヤー一覧の標準順を `createdAt` 昇順 → `id` 昇順に定義した。
- 設計書 §10 の未確定事項6件を全件確定した。ユーザー判断は次の3件。

  - 初回起動時は `ゲスト` を自動作成する（名前入力を必須にしない）。
  - 試合時間（`durationSec`）を記録し、直近10試合にも表示する。
- 検証件数を実数に合わせて更新した。着手時点の単体17件（`app-contract` 3・`game-core` 9・`opponent-ai` 5）＋追加12件＝**29件**、E2E は既存6シナリオ×3環境＝18件に10シナリオを追加して16シナリオ×3環境＝**48件**を完了基準にする。
