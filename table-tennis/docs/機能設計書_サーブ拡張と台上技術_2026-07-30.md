## 3. 全体方針

### 3.1 フェーズは一方向依存で、追い越さない

**Phase 1 → Phase 2 → Phase 3**。Phase 2 は Phase 1 の `swingTypeOf`（§4.1.1）を拡張し、Phase 3 は Phase 2 の打点平面の引き下げ（§4.2.6）が無いと短い球を返せず成立しない。

### 3.2 判断ロジックと解生成は純粋関数へ出す

v0.3.0・v0.4.0 で確立した方針を継続する。今回移すのは次の4つで、いずれも `Game` の内部状態を参照しない。

| 関数 | 現在の所在 | 移す理由 |
|---|---|---|
| `swingTypeOf(shot)` | `game.ts:764-765` のインライン | A-1 の修正対象そのもの。B-1 の検証境界にもなる |
| `classifyPlayerShot(...)` | `game.ts:946-970` のインライン | Phase 3 で分岐が増える |
| `isShortBall(...)` | 新規 | Phase 3 の中核判定 |
| `solveShot(...)` | `game.ts:687-758`（`makeShot` の前半） | **打った球が実際にネットを越えて相手コートへ入るか**を自動検証するため（§4.3.4） |

### 3.3 サーブは「縦回転 × 横回転」の直積として並べる

| | 横左 | 横なし | 横右 |
|---|---|---|---|
| **上回転** | `topspin-left`（新） | `topspin` | `topspin-right`（新） |
| **回転なし** | `side-left` | `knuckle` | `side-right` |
| **下回転** | `backspin-left`（新） | `backspin` | `backspin-right`（新） |

既存5種の識別子・ラベル・回転値は**変更しない**。UI も 3×3 のマトリクスとして自然に並ぶ。`ServeType` を合成型へ作り替える案は、既存の `SERVE_PROFILES` / `AI_SERVE_WEIGHTS` / `chooseWeightedServe` / E2E がすべて文字列リテラル前提であり差分が大きすぎるため採らない（CLAUDE.md §1）。

### 3.4 サーブの長短は探索パラメータの差し替えとして実装し、**設計時に校正を完了させる**

`solveServe` は「1バウンド目の距離候補 × 速度候補」を総当たりし、2バウンド目が目標zにどれだけ近いかで最良解を選ぶ。長短はこの**目標zと探索範囲を長さごとに差し替える**だけで実現でき、物理モデルにも判定にも手を入れない。

**初回レビューの指摘（P1-01）を受け、設計値の校正は設計段階で完了させた。** §4.2.2 の値は、現行の `solveAngle` / `simLand` / `tableBounce` をそのまま使って **9球種 × 3長さ × 2方向 × 3狙い＝162通り**を実測し、**162通りすべてが成立する**ことを確認済みの確定値である（§4.2.3 に実測結果）。実装者が物理値を探索する余地は残さない。

校正の過程で分かった重要な性質を2つ記録する。

1. **長いサーブほど1バウンド目を自陣の奥（ネットから遠い側）に取る必要がある。** 当初案（`long` の距離候補 `[96, 82]` ＝ 1バウンド目が z ≒ -50）は、ネットまでの残り距離が短すぎて**バウンド後にネットへ当たる**。実測では `long` 54通り中36通りが不成立だった。距離候補を `[62, 50]`（1バウンド目 z ≒ -84〜-96）に改めると全通り成立する。短いサーブは逆で、1バウンド目をネット寄りに取る（`[124, 110]`）。
2. **狙い（`aimX`）の反映率は長さに依存させる必要がある。** `serveTry` は `aimX * 0.35` で1バウンド目の横目標を決めているが、2バウンド目までの横移動は跳ね返り後の飛距離に比例する。長いサーブでは同じ係数だと**横に出て台から外れる**（`x` が `HW = 76.25` を超える）。反映率を長さごとの `aimScale` にする。

### 3.5 短いサーブを返せるようにするため、打点平面の手前側限界を下げる

`contactPlane()` は打点の z を `[CONTACT_PLANE_NEAR(62), CONTACT_PLANE_FAR(178)]` に制限している（`src/game.ts:667-677`）。短いサーブは2バウンド目が `|z| ≒ 24〜44` に落ち、その後 `|z| ≒ 55` 付近で2度目のバウンド（失点）に達する。打点平面が `62` に固定されていると、**ボールが打点平面へ届く前に2バウンドし、短いサーブが自動的に得点になる**。

そこで `CONTACT_PLANE_NEAR` を `62 → 30` へ下げる。既存の中・長サーブは打点の自然な z が 70〜100 付近であり、`clampPlane` の下限に触れないため**挙動は変わらない**。

### 3.6 各フェーズのゲートを「ローカル完了 / 公開承認 / 公開完了」の3段に分ける

初回レビューの指摘（P1-02）を受けて正規化する。**公開の有無に関わらずフェーズを締められる**ようにし、公開はフェーズの締めとは独立に追跡する。

| ゲート | 到達条件 | 効果 |
|---|---|---|
| **G1 ローカル完了** | 当該フェーズ全スライスの実装、`npm run check` green、§8.3 の当該フェーズ手動確認、コミット済み | **これだけで実装ログのフェーズを締め、次フェーズへ進める**。締めチェックリストの「検証結果」には `公開: 未実施（承認待ち）` と明記する |
| **G2 公開承認** | ユーザーが公開を明示指示 | `master` への push を実行してよくなる |
| **G3 公開完了** | Actions run success、Pages deployment の SHA 一致、公開資産 HTTP 200 かつローカル `dist` と一致、Chrome 再読込確認 | 実装ログの当該フェーズへ追記し、ステータスを「完了（公開済み）」へ更新。設計書と索引のステータスも更新 |

この分離は v0.3.0 の「実装済み（公開待ち）→ 実装済み（公開済み）」運用と同じであり、実装フェーズ記録ルール §3 とも矛盾しない（G1 の時点で検証は完了しており、未実施なのは公開だけで、それを明記するため）。

**複数フェーズを未公開のまま積んでから公開してもよい。** その場合も版数と Service Worker のキャッシュ名は各フェーズで上げ、公開確認（G3）は最終コミットに対して1回行う。公開時点の最新キャッシュ名が配られるだけで、途中の名前が飛ぶことに問題はない。

#### 4.2.2 [P2] サーブの長短（C-2）

```ts
// types.ts
export type ServeLength = "short" | "middle" | "long";

export interface ServeLengthProfile {
  id: ServeLength;
  label: string;
```

| 長さ | ラベル | `targetZ` | `distances` | `speedBase` | `speedStep` | `aimScale` |
|---|---|---|---|---|---|---|
| `short` | 短い | `34` | `[124, 110]` | `160` | `24` | `0.5` |
| `middle` | 中 | **`70`** | **`[82, 60]`** | **`300`** | **`66`** | **`0.35`** |
| `long` | 長い | `124` | `[62, 50]` | `420` | `70` | `0.16` |

`solveServe` と `serveTry` のシグネチャを次のように変える。

```ts
export function solveServe(
  from: Pick<BallVector, "x" | "y" | "z">,
  aimX: number,
  spin: number,
  side: number,
  direction: number,
  length: ServeLengthProfile,   // 追加

```

内部の変更は3点のみで、探索構造とスコア計算は現行のまま。

1. `targetZ = direction * length.targetZ`
2. 距離ループを `length.distances`、速度を `length.speedBase + index * length.speedStep`（10段）

### 4.3 Phase 3：台上技術

#### 4.3.1 [P3] `lastBounceZ` の所有先とライフサイクル（P2-03 の解消）

**所有先は `BallState`** とし、未記録状態を表現できる型にする。

```ts
// types.ts（BallState へ追加）
lastBounceZ: number | null;
```

| 場面 | 値 |
|---|---|
| 初期化（`Game` のフィールド初期値） | `null` |
| `startServe()`（点間リセット） | `null` |
| `makeShot()`（自分が打った直後） | `null`（**打球で無効化する**。前のラリーのバウンドを次の分類へ持ち越さない） |
| `judgeBounce()` の入口 | `this.ball.lastBounceZ = this.ball.z`（**台上でバウンドした瞬間の z**） |

`null` を短球と誤認しないため、`isShortBall()` は `null` を受け取ったら **`false`** を返す。数値 `0` を未記録の代用にしない（`0` はネット直下の実座標と区別できないため）。

```ts
// rules.ts
export function isShortBall(
  lastBounceZ: number | null,
  ballY: number,
  receiver: Side,
): boolean;
```

- `lastBounceZ === null` なら `false`。
- 受け手側のバウンドであること（`receiver === "P"` なら `lastBounceZ < 0`、`"A"` なら `> 0`）。
- `Math.abs(lastBounceZ) <= SHORT_BOUNCE_Z`（新定数 `58`）かつ `ballY <= SHORT_BALL_MAX_Y`（新定数 `22`）で `true`。
- 高さ条件を入れる理由: 短く落ちても大きく弾んで高くなった球は台上技術の対象ではなく、通常の攻撃対象だから。

**結線の固定**: `judgeBounce()` での記録と `startServe()` / `makeShot()` でのリセットは純粋関数では守れないため、`scripts/check-app.mjs` にソース契約検査を追加する。

| # | 検査内容 |
|---|---|
| C7 | `src/game.ts` の `judgeBounce()` 内に `this.ball.lastBounceZ = this.ball.z` がある |
| C8 | `startServe()` と `makeShot()` の両方に `lastBounceZ = null` の代入がある |

#### 4.3.2 [P3] ショット分類の純粋関数化と2つの新技

```ts
// rules.ts
export function classifyPlayerShot(input: {
  flick: Flick | null;
  ballY: number;
  short: boolean;
}): ShotId;
```

現行の分岐（`src/game.ts:946-970`）をそのまま移し、**先頭に短球の分岐を足す**。

```
short === true:
  下フリック（downward > 0.42 * sp）  → STOP
  上フリック（upward   > 0.42 * sp）  → FLICK
  それ以外・フリック無し               → PUSH
short === false:
  現行どおり（LOB / SMASH / DRIVE / CHOP / PUSH）
```

`SHOTS` に2件追加する。

| ID | `sp` | `spin` | `dep` | `err` | `lab` |
|---|---|---|---|---|---|
| `STOP` | `[230, 270]` | `-0.5` | `26` | `0.02` | ストップ |
| `FLICK` | `[640, 720]` | `0.75` | `78` | `0.022` | フリック |

`makeShot` は `targetZ` を `max(24, min(HL - 14, depth))` に丸めるため、`dep = 26` は**ネットのすぐ向こう**に落ちる。STOP の球威は **`sp`（低速）と `dep`（浅い着地点）で決まる**（`pw` は Phase 1 で削除済み。§4.1.6）。

`swingTypeOf` に追加: `FLICK → 1`、`STOP → -1`。

#### 4.3.3 [P3] AI の台上処理（P1-03・P2-02 の解消）

**挿入位置**: 短球分岐は現行の**射程・高さ guard の後**、既存のショット種別分岐の**前**に置く。guard より前に置くと、横に届かない球や高さ範囲外の球でも AI が返球してしまう（`opponentContact()` 側に同等の guard は無い）。

**乱数契約**: 短球分岐に入ったとき **`const tableTopRoll = this.random()` を1回だけ引き**、全難易度・全境界でその値を使う。難易度によらず**消費は常に1回**とする（easy も引く。難易度を変えても乱数列がずれないようにするため）。

```
（射程・高さ guard は現行のまま）
if (isShortBall(ball.lastBounceZ, ball.y, "A")) {
  const roll = this.random();          // 難易度によらず必ず1回
  easy: type = "PUSH"
  mid : roll < 0.35 ? "STOP" : "PUSH"
  hard: roll < 0.35 ? "FLICK" : roll < 0.7 ? "STOP" : "PUSH"
  depth = shotDepthFor(type)           // ↓
  aim   = 現行と同じ式
  return { type, aim, depth, quality, blunder }
}
（以降、現行のショット種別分岐）
```

**`depth` の決定（P1-03 の核心）**: 現行 `decideShot()` はショット種別と無関係に `LEVELS[level].depth * (0.82 + 0.3 * random())`（mid で約 78〜106）を返し、`opponentContact()` がそのまま `makeShot()` へ渡す。**種別を `STOP` にするだけでは `SHOTS.STOP.dep = 26` は使われず、ストップが短く止まらない。**

短球分岐では**技に対応した `depth` を明示的に返す**。

| 種別 | AI の `depth` |
|---|---|
| `STOP` | `SHOTS.STOP.dep * (0.9 + 0.2 * random())` ＝ 約 `23.4 〜 31.2` |
| `FLICK` | `SHOTS.FLICK.dep * (0.85 + 0.3 * random())` ＝ 約 `66.3 〜 89.7` |
| `PUSH` | `SHOTS.PUSH.dep * (0.85 + 0.3 * random())` ＝ 約 `74.8 〜 101.2` |

この `depth` 用の乱数は `tableTopRoll` とは別に1回引く（**短球分岐の総消費は2回**: 種別選択1 + depth 1。既存の長球経路は種別分岐で1〜2回・depth で1回という現行の消費順を変えない）。

#### 4.3.4 [P3] ショット解生成の抽出（P2-04 の解消）

「打った球が実際にネットを越えて相手コートへ入るか」を自動検証できるようにするため、`makeShot()` の前半（`src/game.ts:687-758`）を純粋関数として `src/physics.ts` へ切り出す。

```ts
export function solveShot(input: {
  from: Pick<BallVector, "x" | "y" | "z">;
  type: ShotId;
  direction: number;
  aimX: number;
  depth: number;
  contactQuality: number;
  extraError: number;
  ballY: number;              // SMASH の速度補正に使う
  random: () => number;
}): { vx: number; vy: number; vz: number; spin: number; side: number };
```

**抽出は挙動不変とする。** 計算式・分岐・**乱数の消費順（`side` → 非LOBの `speed` → `elevation` 誤差 → `azimuth` 誤差 → `speed` 誤差）**をそのまま移す。`makeShot()` は `solveShot()` を呼び、結果を `this.ball` へ書くだけになる。

これにより、単体テストから「代表的な打点・速度端・回転・品質で STOP / FLICK を解き、`simLand` でネット越えと相手コート着地と着地点範囲を検査する」ことができる（U28）。
