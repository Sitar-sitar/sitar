## 1. 判定

**着手不可**

- P1: 2件
- P2: 4件
- P3: 1件

固定速度へ事後補正を重ねる構造をやめ、台上技術だけを必要速度モデルへ移す方針は妥当である。`STOP` / `FLICK` の校正値を実装前に確定し、Obsidianの着手前チェックに従って両方向、誤差適用前後、明示的blunder、修正前negative controlまで設計した点も前設計より強い。

一方、設計どおりのコードは `const` で宣言した方位角を後段で更新するため型検査を通らない。また、U31が測るのは固定seedの標本内で「短球状態から外れるまで」であり、旧契約の「5往復以内に得点へ到達」でも、設計が主張する有限球数の構造的保証でもない。この2件は設計の実装可能性とA-4の受け入れ契約を直接壊すため、解消するまで実装へ進めない。

さらに、非対象5技のビット不変、実ゲームの打点平面を通る応酬、AIの狙い端、短サーブの実接触時短球判定が自動検証へ結線されていない。現行テストがgreenでも、これらの契約を満たしたことにはならない。

## 3. 指摘事項

### P1-01: 擬似コードは `const azimuth` を誤差適用時に更新するため、そのままでは型検査を通らない

**対象**

- 設計書 §4.2（252〜268行）
- 設計書 §7 S1（511行）
- 設計書 §9 G1（563行）
- `src/physics.ts:350-352`
- `src/physics.ts:433-437`
- `tsconfig.json:8-10`

**根拠**

設計書は `const { azimuth } = plan` と宣言した後、誤差適用で `azimuth += ...` を実行する。`const` へ再代入するためTypeScriptエラーとなり、「常に型検査が通る単位」とするS1の前提に反する。

現行 `solveShot()` は、誤差適用で3要素を更新するため `elevation`、`azimuth`、`speed` をすべて `let` で宣言している。判別共用体への変更後も、誤差を適用する3要素は可変でなければならない。

**必要な修正**

1. §4.2のコードを、例えば `let { speed, elevation, azimuth } = launchPlan(shot.speed);` のように3要素すべて可変で受ける形へ修正する。
2. 修正後コードを現行の厳格TypeScript設定へ当て、`npm run typecheck` が通ることを設計レビュー時点で確認する。
3. 設計書の変更履歴へ修正理由を残す。

**解消条件**

§4.2の完成形をそのまま実装して、S1末尾の型検査を通せることが確認できること。

### P1-02: U31は「得点への到達」も有限球数の構造的終了も保証しない

**対象**

- 設計書 §0（25行）
- 設計書 §4.4（299〜316行）
- 設計書 §5.1 U31（332行）
- 設計書 §9 G1（570行）
- supersede元設計書 §8.3-15（725行）
- supersede元設計書 §9.3（795行）

**根拠**

supersede元の契約は「ストップの応酬が5往復以内に**得点へ到達する**」である。これに対してU31-aのT1は、AIの `PUSH` 着地が短球でなくなることしか検査しない。長球へ移った後もラリーは継続できるため、短球状態から外れることと得点発生は同値ではない。

T2の「`STOP` のミス率が0より大きい」も、24球以内の終了を構造的には保証しない。各球で継続確率が0より大きい確率過程には任意に長い列が存在する。固定LCG・400試行で最大17球だったことから言えるのは、そのseedと標本に対する回帰エンベロープだけであり、製品挙動のハード上限ではない。

実測表でeasyが中央値・最大とも1球なのは、easyが最初の短球で必ず `PUSH` を選び「短球状態を終える」からであり、1球で必ず得点するからではない。この表自身が、U31-bの「終了」が得点ではなく台上局面の終了を数えていることを示す。

したがって、現在の§4.4は次の3つを混同している。

1. 短球から長球へ移ること
2. 固定標本内で台上局面が所定球数以内に終わること
3. ラリーが得点へ到達すること

**必要な修正**

1. A-4で保証したい契約を次のどちらかへ一意化する。
   - 台上局面の確率的な終了性を目的とする場合: 「構造的保証」「24球以内に終了」「旧5往復条件を自動検証へ昇格」という表現を撤回し、固定seed・試行数・p99・最大値を持つ統計回帰契約として定義する。旧「得点へ到達」はsupersedeせず、別の手動または統合試験として残す。
   - 得点までのハード上限を目的とする場合: 台上継続回数など製品側の決定論的な終了規則を設計し、実際の得点状態まで進める統合試験を追加する。
2. U31の「終了」が、短球判定終了、台上技術選択終了、または得点のどれを指すかを判定式で明記する。
3. §0、§4.4、§5.1、§5.3、§5.4、§9、supersedeバナーを同じ契約へ揃える。

**解消条件**

A-4の終了状態と保証水準が一意になり、その状態までを実際に検査するテストと手動確認が定義されること。固定400標本の最大値を製品の構造的上限として扱わないこと。

### P2-01: 非対象5技の「ビット単位で同一」は既存テストから証明できない

**対象**

- 設計書 §2.2（100〜101行）
- 設計書 §4.2（273〜278行）
- 設計書 §6.1（484〜489行）
- 設計書 §7 S1（511行）
- 設計書 §8-1・§8-2（546〜547行）
- 設計書 §9 G1（571行）
- `tests/game-core.test.ts:505-622`

**根拠**

設計書は、既存U群が無修正で通ることを `DRIVE` / `SMASH` / `PUSH` / `CHOP` / `LOB` のビット不変の根拠にしている。しかし現行45件のうち `solveShot()` の出力弾道を直接検査するブロックはSTOP / FLICK向けであり、非対象5技の `vx` / `vy` / `vz` をv0.6.0基準値と比較するテストは無い。

U21・U22はサーブの `solveServe()` 経路であり、通常ショットの `absolute` / `arc` 分岐を通らない。分類や表示の既存テストも、打ち出しベクトルのビット一致を検出できない。そのため、例えば `arc` に誤って `ensureNetClear()` を適用しても、設計が列挙した既存U群だけでは必ずしもfailしない。

**必要な修正**

1. S1着手前のv0.6.0から、非対象5技の決定論的な基準ベクトルを採取する。
2. 両方向、乱数端、代表打点を含めて、`vx` / `vy` / `vz` / `spin` / `side` を厳密一致で固定する。`SMASH` は `ballY` 補正の下限・中間・上限、`LOB` は4乱数契約を含める。
3. 新規テストIDと `test()` ブロックの対応、および単体期待件数を§5.1・§5.3・§9へ反映する。既存ブロックのサブケースへ含める場合は、その対応を明記する。

**解消条件**

`ShotSpeed` への表現変更で非対象5技の出力ビットまたは設計で定義した厳密な数値列が変わると、必ず自動テストがfailすること。

### P2-02: U31は製品の `Game.contactPlane()` と結線されず、実ゲームの応酬を検証できない

**対象**

- 設計書 §1.5（76〜83行）
- 設計書 §5.1 U31（332行）
- 設計書 §7 S3（513行）
- `src/game.ts:667-722`
- `src/game.ts:783-790`
- `tests/game-core.test.ts:1-31`

**根拠**

設計書の打点分布は `contactPlane()` を「再現して」測定している。現行の実処理は `Game` のprivateメソッドであり、`integrate()`、1バウンド、`tableBounce()`、高さ22の下降点、`CONTACT_PLANE_NEAR/FAR` のクランプを組み合わせて次打点を決める。

一方、S3の変更対象は `tests/game-core.test.ts` だけで、製品側の打点計算を純粋関数として公開・共有する変更が無い。テスト内に同じ式を複製すればU31は書けるが、将来 `Game.contactPlane()` だけが変わってもテスト側の複製はgreenのままになり得る。これはObsidianの「実ゲームで発生する打点をテストに含める」という再発防止条件を満たさない。

**必要な修正**

1. 推奨案として、打点予測とクランプを製品コードの純粋関数へ抽出し、`Game.contactPlane()` とU31が同じ関数を使うようにする。
2. 抽出しない場合は、`Game` の実状態遷移を通して打点・`lastBounceZ`・短球判定・得点または台上局面終了を観測できる統合テストを定義する。
3. S3の対象ファイル、非破壊条件、negative control、期待件数を実際の変更範囲へ合わせる。

**解消条件**

U31がテスト専用に再実装した打点ではなく、製品と同じ打点計算・短球判定を通った応酬を検査すること。

### P2-03: U28'-bの全数列挙からAIの狙い端が漏れている

**対象**

- 設計書 §5.1 U28'-b（341行）
- 設計書 §5.2 格子（363行）
- 設計書 §9 G1（567行）
- `src/ai.ts:134-146`

**根拠**

校正条件はhard AIと同じ `aimX = -sign(x) × HW × 0.72 × (0.6〜1.0)` を使う。現行AIではこの `0.6〜1.0` が独立した `aimRoll` から決まり、`depthRoll` とは別の乱数である。

しかしU28'-bが端値列挙するのは `side`、`margin`、仰角誤差、方位角誤差、速度誤差、`depth` の6軸だけで、`aimRoll` の `{0, 1}` が無い。記載された6912通り/方向は `54打点 × 2品質 × 2^6` であり、狙い端を数えていないことも確認できる。接触Xと目標Xは別入力なので、格子の `x ∈ {0, 45, -80}` だけでは狙い端の代わりにならない。

狙いは方位角と台内着地に直接影響する。Obsidianの着手前チェックが求める「方向・狙い・誤差端の組み合わせ列挙」を満たすには、狙い端も境界値検査へ含める必要がある。

**必要な修正**

1. U28'-bへ `aimRoll ∈ {0, 1}` を追加し、少なくとも13824通り/方向へ更新する。
2. 自陣落下率、ネット、台外、成立件数、方向対称性を追加後の全数列挙で再測定し、2%未満という判定値が維持できるか再校正する。
3. §5.1、§5.2、§6.1、§9、変更履歴の件数と実測値を同期する。

**解消条件**

AIの独立した狙い端とdepth端を同時に含む全数列挙で、U28'-bの受け入れ値が確定していること。

### P2-04: U32は2バウンド目Zしか見ず、短サーブが実接触時に `isShortBall` となることを検査しない

**対象**

- 設計書 §5.1 U32（333行）
- 設計書 §8-5（550行）
- 設計書 §9 G1（569行）
- `src/rules.ts:35-49`
- `tests/game-core.test.ts:80-127`
- `tests/game-core.test.ts:146-171`

**根拠**

`isShortBall()` の成立には、受け手側へバウンドした `lastBounceZ` がしきい値内であることに加えて、**実際の返球時の `ballY <= SHORT_BALL_MAX_Y`** が必要である。

現行 `cachedServeTrace()` が返すのは1・2バウンド目のXと2バウンド目Zであり、受け手の打点平面に到達した時のY、`lastBounceZ`、receiverを持たない。U32の記述どおり `secondZ` を `48` と比較するだけでは、中・長サーブをZで除外できても、「short全54件が短球」という受け入れ条件までは証明できない。

§1.5には短サーブからAI打点までの実測Yが `8.9〜20.2` と記録されているが、U32はその実測経路を自動テストへ結線していない。サーブ物理や打点計算が将来変わり、短サーブの接触Yだけが22を超えてもU32はgreenになる。

**必要な修正**

1. 両方向の各短サーブを実際の受け手打点まで進め、`lastBounceZ` と接触Yを `isShortBall()` へ渡して全件 `true` を確認する。
2. middle / longは同じ実接触経路で全件 `false` を確認する。
3. P2-02の打点純粋関数を採用する場合は、U31とU32で同じ製品関数を共有する。
4. Z帯だけを検査する設計を維持する場合は、U32とG1の表現を「2バウンド目Zの分離」へ狭め、実接触時の短球成立を別テストへ割り当てる。

**解消条件**

短・中・長の分類が2バウンド目Zの代理値ではなく、製品の実接触状態と `isShortBall()` の判定結果で自動検証されること。

### P3-01: 校正とU32で「全件」が90・54・162の3通りに読める

**対象**

- 設計書 §1.3（60〜68行）
- 設計書 §5.1 U32（333行）
- 設計書 §8-5（550行）
- 設計書 §9 G1（569行）

**根拠**

§1.3の5狙い校正は `9球種 × 2方向 × 5狙い = 90` であり、表の各長さについて90件、3長さ全体では270トレースである。一方、U32は既存の代表3狙いを使うため、各長さ54件、3長さ全体のキャッシュは162トレースとなる。

§5.1はこの違いを説明しているが、§8-5は「U32が全90通りを検査」と記載し、§9は単に「全件」とする。同じU32の母集団が箇所によって変わるため、実装者が5狙いへ拡張するのか、既存3狙いを再利用するのか一意でない。

**必要な修正**

1. 「校正: 各長さ90件・全270トレース」「U32: 各長さ54件・全162キャッシュ」のように単位を固定する。
2. §8-5の「全90通り」を、採用するU32母集団へ合わせる。
3. §9の「全件」に件数と組み合わせ式を併記する。

**解消条件**

校正データと自動テストの母集団が全節で同じ式・同じ単位により追跡できること。
