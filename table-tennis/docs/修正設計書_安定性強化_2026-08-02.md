# 修正設計書：v0.6.2 安定性強化

本書は、公開済み v0.6.1 を基準として、ユーザー向け機能やゲームバランスを増減せず、保存データ、ゲームループ、PWA キャッシュ、CI/E2E の障害耐性と回帰検出力を強化する次期修正の正本である。

- **作成日**: 2026-08-02
- **対象アプリ**: table-tennis
- **種別**: 修正設計書
- **対象バージョン**: v0.6.2
- **前提コミット**: `3f2903a802fd4f174cfbf9b600ea81447bdac7f3`（v0.6.1 公開済み）
- **ステータス**: 実装済み・公開済み（Chrome手動受入未了）
- **関連**: [v0.6.1 台上技術の成立性再設計](./修正設計書_台上技術の成立性再設計_2026-07-30.md) / [実装ログ](./実装ログ.md) / [設計書インデックス](./設計書インデックス.md)
- **supersede**: なし。既存のゲーム仕様、物理値、AI 難易度、戦績仕様、PWA オフライン仕様を維持したまま防御層と回帰試験を追加する

## 1. 目的・背景

外部コードレビューの妥当性確認では、固定タイムステップ、AI の反応遅延、旧 Service Worker キャッシュ削除、npm キャッシュ、デプロイ前検証は既に実装済みであり、再実装すべき問題ではないと確認した。一方、現行コードの直接調査から、次の安定性上の改善余地が残る。

1. IndexedDB から取得した値を TypeScript の型キャストだけで信頼しており、保存値の実行時スキーマ検証がない。
2. IndexedDB 接続に `versionchange` 処理がなく、将来の DB バージョン更新が既存タブに阻害される可能性がある。
3. 固定タイムステップは実装済みだが、フレーム分割、過大 `dt`、サブステップ上限の契約を直接検査する単体テストがない。
4. Service Worker の `caches.match()` が当該オリジンの全キャッシュを横断し、現在版以外の同一 URL 応答を拾える。キャッシュ名とアプリ版数の同期も手作業である。
5. Playwright は CI でも worker 数を明示しておらず、過去の Phase 9 では高負荷時に合成ジェスチャー E2E のフレークが再現している。

本修正では、不具合の再現根拠がない物理・AI の再設計は行わない。現行のゲーム挙動を特性テストで固定し、保存・更新・実行環境の部分障害がゲーム本体を巻き込まない構造を強化する。

## 3. 現状と制約

### 3.1 確認済みの現行契約

| 領域 | 現行事実 | 根拠 |
|---|---|---|
| ゲームループ | `requestAnimationFrame` の差分を最大 `0.05` 秒へ制限し、`1/240` 秒刻み、最大12回で `tick()` する | `src/game.ts:281-317` / `src/config.ts:316,341` |

### 3.2 残る具体的なリスク

#### R1: 保存値の型を実行時に検証しない

`getAll()` / `get()` の結果を `PlayerRecord` / `MatchRecord` / `SettingRecord` として直接扱う。古い版、DevTools、ブラウザ障害等で不正値が入ると、並び替えや集計など後段の別モジュールで失敗し、原因の切り分けが難しい。

#### R2: DB 接続が将来アップグレードをブロックする

`StatsStore.open()` の成功後 DB に `versionchange` listener がない。将来 version 2 以降を開くタブに対して旧タブが接続を保持すると、アップグレードが `blocked` になり得る。

#### R3: 固定ステップ契約が実装詳細に埋まっている

固定ステップ自体は正しく存在するが、`Game.loop` の private 実装だけにあり、通常リフレッシュレート、タブ復帰相当の過大差分、上限到達時の時間破棄を直接検査できない。

#### R4: 現在版以外のキャッシュを参照できる

fetch handler の `caches.match(event.request)` は全キャッシュを横断する。activate 前後や異常キャッシュが存在する状況で、現在版キャッシュに対象が無い場合、古い同一 URL 応答を返す余地がある。

#### R5: E2E の CPU 競合耐性を CI 設定で固定していない

`playwright.config.js` は `fullyParallel: true` だが CI worker 数を固定していない。Phase 9 で合成ジェスチャーの時間契約が高負荷時に崩れた履歴がある。機能追加より再現性を優先し、CI では直列実行を正本とする。

## 4. 設計方針

### 4.1 ユーザー決定

- 次期改修は機能追加ではなく、現在のアプリの安定性を主目的とする。
- 妥当性確認済みレビューの修正候補を取り込み、それ以外の安定性改善も現行コードから検討して設計へ含める。

### 4.2 採用方針

1. **ゲーム本体を保存機能から隔離する**: 保存値が不正、DB が利用不能、接続が無効化された場合も、戦績だけを停止しタイトルから試合を開始できる。
2. **保存データを黙って直さない**: 誤修復・データ消失を避け、異常を検出したら読み書きを停止する。元データは残す。
3. **現行挙動を純粋関数と回帰テストで固定する**: 固定ステップを再設計せず、現行の数値と上限処理をテスト可能な形へ抽出する。
4. **PWA 更新の参照範囲を現在版へ閉じる**: 古いキャッシュの削除だけに依存せず、fetch 時点でも現在版以外を読まない。
5. **CI は速度より再現性を優先する**: CI worker は1。ローカル通常実行の自動 worker は維持する。
6. **依存を増やさない**: 実行時検証は TypeScript の小さな type guard/parser で実装し、スキーマライブラリや fake IndexedDB を追加しない。

### 4.3 採用しない案

| 案 | 採らない理由 |
|---|---|
| 新しい `PhysicsEngine` と 1/120 秒サブステップ | 現行は既に 1/240 秒固定ステップ。挙動変更と重複実装になる |
| AI の Gaussian noise と新反応バッファ | 現行に反応遅延、再予測間隔、予測誤差、ミス率があり、変更根拠がない |
| LocalStorage の JSON parse 修正 | 対象ストレージを誤認している。現行は IndexedDB |
| 不正レコードだけを自動削除して継続 | 誤判定時にユーザーデータを失う。v0.6.2 は非破壊 fail-closed とする |
| DB version を2へ上げる | object store とレコード形を変えないため不要。versionchange 対応だけ先行する |
| Service Worker の build hash 自動生成 | Vite plugin と生成物処理が複雑になる。package version との一致検査で十分 |
| 更新検知時の強制 reload | 試合を中断し得る。手動再読み込みを維持する |
| Playwright ブラウザバイナリのキャッシュ | 復元コストと複雑性に対する利益が不明で、安定性改善の主目的から外れる |
| CI の test/deploy job 再分割 | 現行も `npm run check` 成功が deploy の前提。構造変更の実益がない |

## 5. 詳細仕様

### 5.1 保存レコードの実行時検証

#### 5.1.1 配置

`src/storage-schema.ts` を新設し、IndexedDB や DOM に依存しない次の純粋関数とエラー型を置く。

- `StorageDataError`
- `parsePlayerRecord(value: unknown): PlayerRecord`
- `parseMatchRecord(value: unknown): MatchRecord`
- `parseSelectedPlayerSetting(value: unknown): SettingRecord | null`

`SettingRecord` は parser と `storage.ts` が共有できるよう `storage-schema.ts` 内で export する。外部ライブラリは使わない。

#### 5.1.2 検証契約

| レコード | 必須条件 |
|---|---|
| `PlayerRecord` | plain object、`id` は空でない文字列、`name` は trim 前後が同一かつ1〜12 Unicode code point、`createdAt` は `Date.parse()` 可能な文字列 |
| `MatchRecord` | plain object、`id` / `playerId` は空でない文字列、`playedAt` は日時として解釈可能、`level` は `easy/mid/hard`、`won` は boolean、`scoreP/scoreA/maxRally/durationSec` は有限・0以上の整数 |
| 選択設定 | `null/undefined` は未選択として許可。それ以外は `key === "selectedPlayerId"`、`value` は空でない文字列 |

上限値は新設しない。現行の有効データを狭めないため、スコアや試合時間に任意の最大値を設けない。読み取り時に trim、丸め、既定値補完、日付書換えは行わない。

#### 5.1.3 適用箇所

`src/storage.ts` で IndexedDB から値を受け取る全経路へ適用する。

- `listPlayers()` の全件
- `renamePlayer()` / `deletePlayer()` / `setSelectedPlayerId()` / `recordMatch()` の取得プレイヤー
- `deletePlayer()` の再取得プレイヤー一覧と選択設定
- `getSelectedPlayerId()` の選択設定
- `listMatches()` の全件

`IDBRequest<T>` の型引数だけで安全とみなさず、request 結果を `unknown` として parser へ渡す。

#### 5.1.4 異常時の状態遷移

```text
loading / ready
  └─ StorageDataError または DB 接続無効化
       ├─ DBへの追加・変更・削除を停止
       ├─ selected playerをゲームから切り離す
       ├─ プレイヤー・戦績ボタンをdisabled
       ├─ 保存データを削除・修復しない
       └─ タイトル、試合、PWAオフライン起動は継続
```

`StatsUnavailableReason` を `src/types.ts` に追加し、少なくとも次を区別する。

- `unsupported`: IndexedDB が存在しない
- `open-failed`: open、transaction、request が失敗
- `invalid-data`: runtime schema validation 失敗
- `version-change`: 別タブまたは新版が DB 更新を開始

`Ui.setStatsPhase()` は reason を受け取り、次を表示する。

| reason | `#playerNotice` |
|---|---|
| `unsupported` / `open-failed` | `この端末では戦績を保存できません。` |
| `invalid-data` | `保存データを読み込めません。ゲームは続けられます。` |
| `version-change` | `戦績データを更新するため、ページを再読み込みしてください。ゲームは続けられます。` |

診断用 `console.warn` は reason、error name、検出 store/field だけを出し、プレイヤー名、ID、試合内容、保存値全体を出さない。通常経路では warning/error 0件を維持する。

### 5.2 IndexedDB `versionchange` 対応

`StatsStore.open()` は接続無効化 callback を受け取る。

1. open success 直後、返却前に DB へ `versionchange` listener を登録する。
2. event は `database.close()` を先に実行する。
3. その後 callback を1回だけ呼び、`main.ts` を `version-change` の unavailable 状態へ移す。
4. listener と callback は多重 event に対して冪等にする。
5. game loop、試合状態、入力、Service Worker は停止しない。

本修正では DB version を1のまま維持する。E2E 内だけ version 2 の open request を発行し、旧接続が閉じて upgrade が `blocked` のまま残らないことを確認する。

### 5.3 固定タイムステップの回帰可能化

#### 5.3.1 純粋関数

`src/utils.ts` に `planFixedSteps(accumulator, rawFrameDelta)` を追加し、次を返す。

```typescript
interface FixedStepPlan {
  frameDelta: number;
  steps: number;
  nextAccumulator: number;
  dropped: boolean;
}
```

契約は次のとおり。

- `rawFrameDelta` が負または非有限なら `frameDelta = 0`
- それ以外は `Math.min(rawFrameDelta, MAX_FRAME_DELTA)`
- `MAX_FRAME_DELTA = 0.05` を `src/config.ts` の名前付き定数へ移す
- `FIXED_STEP = 1 / 240` ごとに最大 `MAX_SUBSTEPS = 12` 回を計画
- 上限12回へ到達したら現行どおり残余を0へ捨て、`dropped = true`
- 上限未満なら1 step未満の残余を `nextAccumulator` へ保持

`Game.loop` は plan の `steps` 回だけ既存 `tick(FIXED_STEP)` を呼ぶ。`tick()` 内の順序、物理、AI、得点、描画は変えない。UI flash と swing 減衰には plan の `frameDelta` を使う。

#### 5.3.2 不変条件

- 通常の60Hz相当では1 frameあたり4 step、120Hzでは2 step
- 144Hz相当は残余を次 frameへ繰り越し、同じ総時間に対する step 数が許容誤差1 step以内で一致
- 1秒相当の停止後でも1 frameに12 stepを超えず、spiral of death を起こさない
- `pageshow`、pause/resume、new game の accumulator resetは維持
- `FIXED_STEP`、`MAX_SUBSTEPS`、物理定数を変更しない

### 5.4 Service Worker のキャッシュ分離と版数同期

#### 5.4.1 キャッシュ名

v0.6.2 から `CACHE_NAME` を package version と1対1にする。

```text
package.json version = 0.6.2
CACHE_NAME          = table-tennis-v0.6.2
```

`scripts/check-app.mjs` は `package.json` と `sw.js` を読み、完全一致しなければ fail する。従来の `table-tennis-v8` からの命名移行は1回限りで、activate の `table-tennis-` prefix 削除対象に含まれる。

#### 5.4.2 fetch

fetch event は最初に `caches.open(CACHE_NAME)` し、その cache instance の `cache.match(event.request)` だけを参照する。global `caches.match()` は使用しない。

- 現在版にあれば即返却する（cache-first維持）
- 現在版に無ければ network を試す
- 成功した同一 origin 応答だけ現在版へ `put`
- network 失敗かつ navigation なら現在版の `./index.html` へ fallback
- navigation 以外で現在版にも network にも無ければ `Response.error()`
- 他の `table-tennis-*` cache や別名 cache は fetch の候補にしない

install の `cache.addAll(APP_SHELL)`、`skipWaiting()`、activate の旧キャッシュ削除、`clients.claim()` は維持する。install が一部失敗した場合は新 Service Worker を activate せず、旧版を残すブラウザ標準の原子性に委ねる。

#### 5.4.3 更新確認

公開確認では、旧版で一度起動した Chrome を用い、v0.6.2 の Service Worker が install/activate した後に再読み込みして新版へ切り替わることを確認する。自動 reload は実装しない。

### 5.5 CI / E2E 安定性

`playwright.config.js` に次を設定する。

```typescript
workers: process.env.CI ? 1 : undefined
```

- `fullyParallel: true` はローカル通常実行のため維持
- CI の `retries: 2` は環境障害の診断情報確保のため維持
- CI の正式結果では、retry が発生した場合は成功扱いだけで閉じず、対象テスト名を実装ログへ残す
- npm cache は既に有効なので変更しない
- Playwright browser cache は追加しない

`package.json` に、Phase の安定性ゲート専用で次と同等の script を追加する。

```text
test:e2e:stability = playwright test --workers=1 --retries=0 --repeat-each=3
```

この script は通常の `npm run check` へ組み込まず、G1前に1回実行する。通常CI時間を3倍化せず、リリース単位でフレークの有無を検査する。

## 6. 既存機能の非破壊条件

### 6.1 ゲーム

- 9球種×3長さ、STOP/FLICK、DRIVE/SMASH/PUSH/CHOP/LOB の仕様・乱数順・物理結果を変えない
- U33 の非対象5技72ベクトルを含む既存単体49件を無修正で通す
- AI の難易度値と判断順を変えない
- 11点2点差、サーブ交代、得点理由、一時停止、pagehide/pageshow を変えない
- プレイヤー操作の160msフリック有効時間を変えない

### 6.2 戦績

- 現行v1の正しい `players` / `matches` / `settings` は無移行で読み書きできる
- プレイヤー追加、選択、改名、削除、連鎖削除、試合記録、直近10件を変えない
- 不正データ検出時もデータを削除しない
- IndexedDB が使えない場合にゲームを開始できる既存仕様を維持
- schema error と versionchange は戦績機能だけを停止し、ゲーム本体へ throw を伝播しない

### 6.3 PWA / 配布

- `dist/assets/app.js` / `app.css` の固定名、相対URL、manifest、iconsを維持
- 制御済みページのオフライン再読み込みを維持
- `table-tennis-` 以外の cache を削除しない
- install失敗時に不完全な新版を activate しない
- Pages公開はユーザーの明示指示があるまで行わない

## 10. リスクとロールバック

| リスク | 予防 | 検出 | 回復 |
|---|---|---|---|
| validatorが既存の正しいv1データを拒否 | 現行fixturesと実ブラウザ保存値だけを必須条件にする。任意上限を追加しない | U34〜U36、既存player-stats E2E、Chrome既存データ確認 | S1をrevert。保存値は無変更なのでデータ回復不要 |
| 不正1件で戦績全体が停止する | 誤集計よりfail-closedを優先し、ゲームは継続 | E20、reason文言 | サイトデータの扱いはユーザー判断。アプリは自動削除しない |
| versionchangeで旧タブの戦績が途中から使えない | 明示文言と再読み込み案内 | E21 | ページ再読み込み。ゲーム本体は継続 |
| 固定ステップ抽出で評価順が変わる | while相当の減算と上限時0クリアをそのまま移す | U37〜U39、既存49単体・57E2E | S3をrevert |
| cache名規則変更で旧資産が残る | prefix削除と現在cache限定matchを併用 | C10/C11、E22、Chrome更新確認 | 修正版は版数を戻さず次版へ上げる。cache名も新しいpackage versionへ進める |
| CI直列化で実行時間が増える | 通常checkは1回、3反復はG1前だけ | Actions durationとローカル実測を記録 | 安定性を落としてworkerを増やさず、必要時はproject単位shardを別設計で検討 |
| reason別文言で既存UIが崩れる | 同じ`#playerNotice`内の短文に限定 | 320px E2E、Chrome境界 | 文言のみrevert可能 |

### 10.1 ロールバック順

1. 公開済みの場合、機能commitを `git revert` で S5 → S4 → S3 → S2 → S1 の逆順に戻す。
2. Service Worker のcache名は旧 `table-tennis-v8` へ戻さず、ロールバック用の次版（例: v0.6.3）へ進める。
3. `package.json` / `package-lock.json` / `sw.js` / README / 設計書 / 実装ログ / 索引を同じ状態へ揃える。
4. `npm run check`、Actions、deployment SHA、HTTP/PWA資産、Chrome再読み込み、オフラインを再確認する。
5. 保存DBはversion 1・同じshapeのままであり、本設計は保存値を変更しないため、DBのダウングレードや復元を行わない。
