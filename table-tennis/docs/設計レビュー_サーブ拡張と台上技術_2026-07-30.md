## 1. 判定

**着手不可**

- P1: 3件
- P2: 5件
- P3: 2件

Phase 1 の不具合修正を小さな純粋関数と既存制御フローの修正へ分ける方針、Phase 2 でサーブを縦回転と横回転の直積として拡張する方針、Phase 3 で短球判定とショット分類を純粋関数へ出す方針は妥当である。

一方、現行物理モデルへ設計値をそのまま適用した数値検証では、Phase 2 の成立性契約162通り中52通りが不成立だった。特に `long` は54通り中36通りが不成立で、設計の「成立性テストが落ちたら実装時に調整する」という留保で吸収できる規模ではない。

また、Phase 3 のAI側は現行 `OpponentAi.decideShot()` が返す難易度由来の `depth` を `Game.makeShot()` へ渡すため、ショット種別を `STOP` に変えるだけでは `SHOTS.STOP.dep = 26` が使われない。設計どおりに実装してもAIのストップはネット際へ短く止まらない。

さらに、Phase 1 は「公開しなくても締めてPhase 2へ進める」としながら、実際のPages公開を唯一のワークフロー検証かつ受け入れ条件にしている。共通の実装フェーズ記録ルールでは未検証のフェーズを締められないため、公開権限が与えられない実装ランではPhase 1を閉じられず、Phase 2へ進めない。

以上のP1を解消し、各Phaseの入力・出力・完了ゲートを一意にしてから再レビューする必要がある。

### P1-01: Phase 2 のサーブ長さパラメータは成立性契約162通り中52通りを満たさない

**対象**

- 設計書 §4.2.1（224〜248行）
- 設計書 §4.2.2（250〜295行）
- 設計書 §7-4〜6（477〜479行）
- 設計書 §8.1 U21（499行、515行）
- 設計書 §9.2（601〜603行）
- `src/physics.ts:201-285`
- `tests/game-core.test.ts:39-95`

**根拠**

§4.2.2 は `short` / `middle` / `long` の探索値を確定値の表として示し、U21と受け入れ条件は162通りすべての `ok === true` を要求している。しかし、現行物理モデルと設計値を組み合わせた実測では52通りが失敗した。

特に `long` は、上回転単独と横上2種を除く6球種が全方向・全狙いで不成立だった。これは数件の境界調整ではなく、長いサーブの大半が提供できない状態である。

§4.2.1と§10-2は、成立性テストが落ちたら回転値や探索値を実装時に調整してよいとする。しかし、設計書が正本である以上、実装者が機能仕様と物理値を同時に探索し、結果だけを後から設計へ戻す形では、S5の開始条件、レビュー対象、回帰基準が確定しない。さらに§4.2.2の長さフォールバックが入ると、不成立の `long` が `middle` として成功し、表面上のサーブ成功だけで欠陥を隠せる。

**必要な修正**

1. `SERVE_LENGTH_PROFILES` と組み合わせ球の回転値を、少なくともU21の162通りが全件成立する値へ事前調整し、確定値と実測結果を設計書へ記録する。
2. 調整を独立作業にする場合は、S4より前へ「物理パラメータ校正スライス」を置き、その完了条件を162/162成立、長さごとの実測着地点範囲、フォールバック未使用とする。
3. `ok` だけでなく、`abs(z2)` が設計した短・中・長の範囲に入り、同一球種・方向・狙いで実測値が単調増加することを検証する。
4. 成立しない組み合わせを仕様として除外する案を採るなら、9球種×3長さというスコープ、UI、AI重み、受け入れ条件を同時に縮小する。フォールバックだけで隠さない。

**解消条件**

設計書に確定したパラメータで162通りが全件成立し、短・中・長の実測着地点が重ならない定量範囲に入り、指定長さから別長さへのフォールバック無しでU21をpassすること。

### P1-03: AIの `STOP` は `SHOTS.STOP.dep = 26` を使わず、短く止まらない

**対象**

- 設計書 §4.3.2（368〜377行）
- 設計書 §4.3.3（379〜391行）
- 設計書 §7-9（482行）
- 設計書 §8.3-14、15（562〜563行）
- 設計書 §9.3（614〜615行）
- `src/ai.ts:96-146`
- `src/game.ts:687-704`
- `src/game.ts:943-1009`

**根拠**

プレイヤー側は `playerContact()` が `SHOTS[type].dep` から `depth` を作り、`makeShot()` へ渡す。そのため、プレイヤーの `STOP` では設計値 `dep = 26` が目標zへ反映される。

一方、AI側は `OpponentAi.decideShot()` がショット種別と無関係に `LEVELS[level].depth * (0.82 + 0.3 * random())` を返し、`opponentContact()` がその値をそのまま `makeShot()` へ渡す。現行値では次の範囲になる。

- mid: 約 `77.9〜106.4`
- hard: 約 `82〜112`

§4.3.3の指示どおり「短球分岐でtypeを `STOP` にする」だけでは、`SHOTS.STOP.dep = 26` はAI経路で参照されない。速度と回転は `SHOTS.STOP` になるが、着地点は通常の中・長球と同じ深さになり、「相手も台上処理を強いられる短い返球」というSTOPの契約を満たさない。

**必要な修正**

1. `OpponentAi.decideShot()` の短球分岐が、`type` だけでなく技に対応した `depth` を明示的に返す契約にする。
2. 推奨案は、`STOP` のAI `depth` を `SHOTS.STOP.dep` を基準に決め、`FLICK` / `PUSH` は攻撃性に応じた別の範囲を明記することである。
3. AIの `STOP` について、`AiShotDecision.depth`、実際の着地点、相手側の `isShortBall()` が真になることを決定論的にテストする。
4. §8.3-15の「ストップの応酬」を、少なくとも一定回数ラリーが継続し、無限化せず得点へ到達するシナリオとして定量化する。

**解消条件**

AIが `STOP` を選んだときにネット際の所定範囲へ着地し、相手側で短球として扱われることが、判断値と物理結果の双方で自動検証されること。

### P2-01: 長さフォールバックの順序・伝播・表示が未定義で、選択UIと実際のサーブが食い違う

**対象**

- 設計書 §4.2.2（275〜295行）
- 設計書 §4.2.3（297〜311行）
- 設計書 §8.2 E13（525行）
- 設計書 §9.2（600〜604行）
- `src/ai.ts:149-160`
- `src/game.ts:231-247`
- `src/game.ts:486-606`

**根拠**

設計書は `solveServe()` へ `length` を追加するが、次のランタイム契約を定義していない。

- `OpponentAi.chooseServe()` が選択した長さをどう返すか
- `tryPlayerServe()` / `doServe()` / `findServeSolution()` が長さをどう受け渡すか
- `findServeSolution()` が要求長さと実際に成立した長さのどちらを返すか
- 「長さをmiddleへ落とす」「狙いを0へ戻す」「AIならknuckleへ落とす」の正確な優先順
- フォールバックした長さをUI、flash、DOM状態、テストからどう観測するか

現行 `findServeSolution()` の戻り値は `solution` / `serveType` / `spin` / `side` だけである。ここへ長さを追加しないまま実装すると、ユーザーが `short` または `long` を選んでも、実際には `middle` が出たことを検出できない。`selectedServeLength` と `aria-pressed` は要求値のままなので、UIが実際の球と食い違う。

**必要な修正**

1. `chooseServe`、`doServe`、`findServeSolution` のシグネチャと戻り値を設計書へ記載し、要求長さと解決後長さを区別する。
2. フォールバック行列を順序付きで定義する。例えば「同球種・同長さで狙い0 → 同球種・middleで元狙い → 同球種・middleで狙い0 → AIのみknuckle」のように、全経路を一意にする。
3. フォールバック時は実際の球種と長さをflashまたは検証可能なDOM状態へ出し、無言でUI選択と異なる球を出さない。
4. プレイヤー操作では別長さへの無言フォールバックを禁止し、選択値を実現できない場合の扱いを明記する案も検討する。
5. 各フォールバック段を単体テストし、要求値、解決値、乱数消費、表示が一致することを確認する。

**解消条件**

要求した球種・長さ・狙いから最終的な球種・長さ・狙いまでの変換が一意で、実際に出た値をUIとテストから観測できること。

### P2-02: AI短球分岐の挿入位置と乱数契約が一意でなく、射程外でも返球し得る

**対象**

- 設計書 §4.3.3（379〜391行）
- 設計書 §5.1（403行）
- 設計書 §5.4（430行）
- 設計書 §9.3（614〜615行）
- `src/ai.ts:96-139`
- `src/game.ts:992-1011`
- `tests/opponent-ai.test.ts:52-58`

**根拠**

設計書は `OpponentAi.decideShot()` の「先頭」に短球分岐を足すと書いている。現行関数の先頭には射程と高さのguardがあり、`opponentContact()` 側には同等のguardが無い。そのため、短球分岐を文字どおりguardより前に置いて `AiShotDecision` を返すと、横に届かない球や高さ範囲外の球でもAIが返球する。

また、hardの「`random() < 0.35` でFLICK、`< 0.7` でSTOP」は、同じ乱数値を再利用するのか2回引くのかが擬似コード上不明である。本文は短球分岐で1回だけ消費すると定めるため、1回の `roll` を保存して境界判定する必要がある。easyは常にPUSHであり、0回消費か契約維持のため1回消費かも明記されていない。

**必要な修正**

1. 短球分岐は現行の射程・高さguardの**後**、既存ショット種別分岐の前へ置くと明記する。
2. `const tableTopRoll = random()` のように1回だけ取得し、mid / hardの全境界へ同じ値を使う擬似コードを示す。
3. easy / mid / hardごとの短球時乱数消費回数を明記する。
4. 「短球だが射程外」「短球だが低すぎる／高すぎる」で `null`、hardの `0.349... / 0.35 / 0.699... / 0.7` で期待種別、長球時は既存乱数列不変、を単体テストへ追加する。

**解消条件**

短球でも既存の到達可能性guardが常に先に適用され、全難易度の種別境界と乱数呼出回数が決定論的テストで固定されること。

### P2-03: `lastBounceZ` の所有先・初期値・更新結線が自己矛盾している

**対象**

- 設計書 §4.3.1（329〜344行）
- 設計書 §6 S8（461行）
- 設計書 §8.1 U24（503行）
- 設計書 §9.3（613行）
- `src/types.ts:55-61`
- `src/game.ts:87-110`
- `src/game.ts:913-940`

**根拠**

§4.3.1は `BallState` に `lastBounceZ` を追加すると定める一方、更新式を `this.lastBounceZ = this.ball.z` としている。現行 `Game` に `lastBounceZ` は無く、設計どおりではTypeScript型検査を通らない。所有先を `BallState` とするなら更新式は `this.ball.lastBounceZ` でなければならない。

また、初期値、点開始時の値、打球直後の値が未定義である。現行の `bounces` guardにより多くの経路では古い値が直ちに使われないが、短球判定の正本としては「受け手側の最新有効バウンドがまだ無い」状態を表現できる必要がある。数値 `0` はネット中央の実座標と区別できず、将来の結線変更時に誤分類を招く。

U24は純粋関数へ任意値を渡すだけで、`judgeBounce()` が正しい状態へ記録する結線を検査しない。

**必要な修正**

1. 所有先を `BallState.lastBounceZ` に統一し、更新式も `this.ball.lastBounceZ` にする。
2. `number | null` など未記録状態を表現できる型、初期化、点開始・打球開始時のリセット規則を定義する。
3. サーブ1バウンド目、受け手側バウンド、通常ラリーの受け手側バウンド、フォルト、点間リセットについて期待値を定める。
4. `judgeBounce()` から `playerContact()` / `OpponentAi.decideShot()` までの結線を、Gameレベルテストまたはソース契約検査で固定する。

**解消条件**

`lastBounceZ` の所有先とライフサイクルが一意で、未記録値を短球と誤認せず、受け手側の有効バウンドだけが次のショット分類へ使われることを自動検証できること。

### P2-04: テストは長さと台上技術の「選択」だけを見ており、物理結果を保証しない

**対象**

- 設計書 §8.1 U21〜U26（499〜505行）
- 設計書 §8.2 E13、E14（525〜526行）
- 設計書 §8.2（536行）
- 設計書 §9.2（601〜603行）
- 設計書 §9.3（611〜615行）

- `src/game.ts:687-758`

**根拠**

U21はサーブの1・2バウンドが台へ入ることと `ok` だけを確認し、実際の `z2` がshort / middle / longの所定範囲に入ることを検査しない。U22もプロファイルの `targetZ` が単調増加することを見るだけで、探索結果の着地点を見ない。

Phase 3ではU24〜U26が分類結果だけを確認し、E14も `#flash` に「ストップ」または「フリック」が出ることだけを見る。`STOP` / `FLICK` の速度・回転・深さを `makeShot()` へ通した結果、ネットを越えるか、相手コートへ入るか、STOPが短球になるか、FLICKが攻撃的な深さになるかは自動検証されない。

したがって、ボタンとラベルが正しくても、長さが区別できない、STOPが長い、FLICKがネットに掛かる、といった中核機能の破損を `npm run check` が検出できない。

**必要な修正**

1. 同一球種・方向・狙いについて、実測 `abs(z2)` が `short < middle < long` となり、各長さの許容範囲へ入ることを検証する。

4. E14を落とす場合でも、物理結果を検証する単体または統合テストは必須とし、手動確認だけへ全面移管しない。

**解消条件**

選択された長さ・技名だけでなく、実際のサーブ着地点と台上技術の着地点・成立性が自動テストで保証されること。

## 5. 確認できた妥当な点

- Phase 1 → Phase 2 → Phase 3の一方向依存を明記し、実装ログをPhaseごとに締める方針は、大きな変更を追跡可能な単位へ分けるうえで妥当である。
- `swingTypeOf`、`classifyPlayerShot`、`isShortBall` を `rules.ts` の純粋関数へ出す方針は、現行 `game.ts` の分岐肥大化を抑え、Canvasに依存しない単体テスト境界を作れる。
- `middle` の `targetZ`、距離候補、速度候補を現行値と同一にする方針は、引数伝播と探索順を変えなければ既存サーブの回帰基準として使える。
- `scheduleAiServe()` が先に既存timerをcancelし、generation guardも維持する方針は、`pageshow` と `resume()` が連続してもtimerを1本に保てる。
- 既存5球種の識別子を維持し4球種を追加する方針は、文字列リテラルを合成型へ全面変更するより差分が小さく、現行規模に合う。
- UIの静的契約を `check-app.mjs` へ追加し、要素を減らすとfailする負の確認まで求める方針は、HTMLとTypeScript設定の二重管理を検出する手段として有効である。
- `CONTACT_PLANE_NEAR` の変更が `paddleDepthRatio` へ波及することを数値で明記し、U13と実機確認の両方を更新する方針は妥当である。
- `master` pushが公開を起動する承認境界、Actions run、deployment SHA、PWA資産、Chrome再読込までを公開確認に含める方針は、build成功だけで公開完了としない既存運用に合う。
- 公開後ロールバックでService Workerのキャッシュ番号を下げず次番号へ上げる方針は、既存クライアントに古い資産を再採用させないため妥当である。
