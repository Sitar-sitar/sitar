## 1. 目的・背景

### 1.1 A-1: STOP がノーリスク化している

`playerContact()` は常に `extraError = 0` を渡す（`src/game.ts:971`）ため、**プレイヤーの STOP は必ず S14 の最終帯再解決に該当し、接触品質に関わらずネットにも自陣にも落ちない**。AI も非 blunder 時（上級 98%）は同じ。

現行モデルの実測（台上打点54通り × 各品質2160試行・§5.2 の格子）:

| 接触品質 | STOP ミス率 | 内訳 |
|---:|---:|---|
| 1.00 | **0.0%** | — |
| 0.75 | 0.9% | — |
| 0.50 | 1.5% | — |
| 0.25 | 2.2% | — |

**接触品質を 1.00 から 0.25 まで落としてもミス率が 2.2% にしか上がらない**。同じ打点での他技は `DRIVE` 19.0% / `CHOP` 2.7% / `PUSH` 2.2%（品質1.0）であり、STOP は「位置取りが下手でも必ず入る技」になっている。短球に対して STOP が支配戦略になり、位置取りの上達がゲーム性に反映されない。

### 1.2 A-2: FLICK の失敗率が難易度設定を上回り、打点距離に逆依存する

固定速度 `sp = [640, 720]` を `solveAngle()` に渡す現行モデルでは、打点がネットに近いほど目標 `dep = 78` へ届かせる仰角が浅くなり、誤差適用後にネットへ落ちる。実測（`extraError = 0`）:

| AI 打点 `abs(z)` | 34 | 45 | 55 | 65 | 75 | 87 |
|---|---:|---:|---:|---:|---:|---:|
| ミス率 | **30%** | 22% | 16% | 13% | 13% | 11% |

打点距離による差は **19pt**。短球では AI 打点が 34〜87 に集中する（§1.5）ため実効 13〜30%。接触品質1.0でも 9.1% 失敗する。**上級 AI に設定した明示的ミス率 `miss = 0.02` を一桁上回っており**、hard が短球で FLICK を 35% 選ぶ設定と噛み合っていない。

### 1.3 A-3: `SHORT_BOUNCE_Z = 58` と中サーブ帯が重なる

サーブ2バウンド目の実測帯（9球種 × 2方向 × 5狙い＝90通り）:

| 長さ | 2バウンド目 `abs(z)` |
|---|---|
| `short` | `22.7 〜 43.5` |
| `middle` | **`54.6 〜 78.8`** |
| `long` | `108.2 〜 131.7` |

しきい値 `58` は `middle` の下限 `54.6` を上回るため、**90通り中12通り（13%）の中サーブが短球と判定される**。設計意図（短いサーブに対して台上技術）から外れ、中サーブに対してストップが打てる。

### 1.4 A-4: 台上応酬の終了性が自動検証されていない

`STOP` の着地から相手打点を追うと、**着地が有効な STOP は 400/400 (100%) で再び短球になる**。したがって STOP は「短球 → 短球」の不動点であり、A-1 でミス率が実質0だった状態では原理的に応酬が終わらない。旧 §8.3-15 は「5往復以内に得点」を手動確認で担保していたが、回帰を検知できない。

### 1.5 台上打点のジオメトリ（校正の前提）

`contactPlane()` を再現して実測した、台上技術が発生する打点の実分布:

| 経路 | 打点 `abs(z)` | 打点 `y` |
|---|---|---|
| 短サーブ → AI 打点（45通り） | `44.2 〜 86.5` | `8.9 〜 20.2` |
| STOP 着地 → 相手打点（400通り） | `34.5 〜 85.7` | `7.3 〜 20.4` |

以降の校正格子は、この実測を覆う **`abs(z) ∈ {34, 45, 55, 65, 75, 87}` × `y ∈ {7, 14, 21}` × `x ∈ {0, 45, -80}` ＝ 54打点**とする。

## 3. 全体方針

### 3.1 「固定速度＋後付け補正」から「必要速度＋余裕率」へ

現行の非 LOB 経路は次の構造を持つ。

```
speed = sp[0..1] から抽選         ← 打点距離を見ていない
solveAngle(...) で仰角を合わせる   ← 速度が足りなければ解が無い
ensureNetClear(...)               ← 仰角だけで救済
[STOP のみ] 誤差前に届くか確認 → solveSpeed で救済（S13）
誤差適用
[STOP のみ] 最終弾道が帯外なら solveSpeed で再解決（S14）  ← ミスが消える
```

**根本原因は「速度が打点距離と無関係に決まる」こと**である。近い打点では過剰、遠い打点では不足し、その不足を STOP だけ2段の事後補正で埋めた結果、補正が誤差を上書きしてミスを消した。

そこで台上技術は、**目標へちょうど届く速度を先に解き、それに技ごとの余裕率を掛ける**。

```
required = solveSpeed(from, targetX, targetZ, elev, spin, side)
speed    = required.speed × (marginMin〜marginMax から抽選)
elevation = elev（技ごとに固定）
azimuth   = required.azim
ensureNetClear(...)
誤差適用   ← 以降の補正は無い
```

これにより (a) 打点距離が自動的に織り込まれ、(b) S13・S14 の分岐が不要になり、(c) **誤差が最後に効くのでミスの余地が残る**。

**この方式は新規ではない。** `LOB` は既に `solveSpeed(..., 1.02, ...)` で同じことをしている（`src/physics.ts:354-365`）。台上技術を同じ土俵に載せ、3つの速度モデルを型で明示するだけである。

### 3.2 代替案を退けた理由

| 代替案 | 退けた理由 |
|---|---|
| S14 の帯を広げる／再解決の条件を緩める | ミスが消える構造は変わらない。帯の端で不連続なジャンプが残る |
| `STOP.sp` の下限を上げる | 近い打点で過剰になり、ストップがネット際に止まらなくなる。距離依存の問題は解けない |
| プレイヤーにも `extraError` を与える | A-1 の症状（プレイヤー STOP が無敵）は隠れるが、AI 非 blunder 時の無敵は残る。原因ではなく症状への対処 |
| 全ショットを必要速度モデルへ統一 | `DRIVE` 等の弾道が全面的に変わり、回帰面が広すぎる（CLAUDE.md §1・YAGNI）。台上技術だけで A-1・A-2 は解ける |

### 3.3 設計値は設計段階で校正を完了させる

前設計のレビュー指摘 P1-01 で確立した方針を継続する。§4.2 の `elev` / `margin` と §4.3 のしきい値は、**製品コード無変更のまま現行 `solveSpeed` / `ensureNetClear` / `simLand` を使って実測した確定値**であり、実装者が探索する余地は残さない（§5.2 に実測結果）。

### 3.4 ミスの「質」も設計対象にする

同じミス率でも、ネットに落ちるのか台外へ出るのかで体感が変わる。実測（§5.2）では、新モデルの `FLICK` のミスは**ほぼ全部が台外（オーバー）**、`STOP` は**ネットと台外の両方**になる。攻撃技が「ネットにポトリ」ではなく「振り抜いてオーバー」で外れるのは原因が読み取りやすく、卓球の体感に近い。これを受け入れ条件（§6）に含める。

## 4. 詳細仕様

### 4.1 `ShotSpeed` 判別共用体（A-1・A-2 の器）

`src/types.ts`:

```ts
export type ShotSpeed =
  /** 絶対速度を抽選する。乱数1回。 */
  | { readonly model: "absolute"; readonly sp: readonly [number, number] }
  /** 目標へ届く必要速度をそのまま使う（高い弧）。乱数0回。 */
  | { readonly model: "arc"; readonly elev: number }
  /** 必要速度に余裕率を掛ける（台上技術）。乱数1回。 */
  | {
      readonly model: "touch";
      readonly elev: number;
      readonly margin: readonly [number, number];
    };

export interface ShotConfig {
  speed: ShotSpeed;   // 旧 sp を置き換える
  spin: number;
  dep: number;
  err: number;
  lab: string;
}
```

**乱数消費回数をモデルに紐づける**のが要点。`absolute` と `touch` は1回、`arc` は0回。これにより `solveShot()` 全体の消費は現行と完全に一致する（`absolute` / `touch` = 5回、`arc`（LOB）= 4回）。

`src/config.ts` の `SHOTS`:

| ID | `speed` | 変更 |
|---|---|---|
| `DRIVE` | `{ model: "absolute", sp: [810, 950] }` | 表現のみ |
| `SMASH` | `{ model: "absolute", sp: [1360, 1520] }` | 表現のみ |
| `PUSH` | `{ model: "absolute", sp: [430, 510] }` | 表現のみ |
| `CHOP` | `{ model: "absolute", sp: [395, 470] }` | 表現のみ |
| `LOB` | `{ model: "arc", elev: 1.02 }` | **`sp: [0, 0]` の死に値を解消**。仰角 `1.02` は現行のハードコード値と同一 |
| `STOP` | `{ model: "touch", elev: 0.5, margin: [1.0, 1.08] }` | **新規校正値**（§5.2） |
| `FLICK` | `{ model: "touch", elev: 0.4, margin: [1.03, 1.18] }` | **新規校正値**（§5.2） |

`spin` / `dep` / `err` / `lab` は7件すべて現行値を維持する。

### 4.2 `solveShot()` の再構成

`src/physics.ts`。モジュール定数 `STOP_DISTANCE_ELEVATION` / `STOP_SPEED_MARGIN` と、S13・S14 の2ブロック（現 `394-430` 行・`439-465` 行）を**削除**する。

**分岐は `let` への代入ではなく値を返す形にする。** 判別共用体の網羅 switch でも「代入前使用」の推論に依存させないため、また分岐部分を単体で読めるようにするため。

```ts
const side = (random() - 0.5) * 0.25;   // ① 乱数1回目（現行と同じ）
const spin = shot.spin;

// 打ち出しの3要素を速度モデルごとに解く。乱数消費は arc=0 / touch=1 / absolute=1。
function launchPlan(
  speedSpec: ShotSpeed,
): { speed: number; azimuth: number; elevation: number } {
  switch (speedSpec.model) {
    case "arc": {
      const result = solveSpeed(from, targetX, targetZ, speedSpec.elev, spin, side);
      return {
        speed: result.speed,
        azimuth: result.azim,
        elevation: speedSpec.elev,
      };
    }
    case "touch": {
      const { elev, margin } = speedSpec;
      const result = solveSpeed(from, targetX, targetZ, elev, spin, side);
      const roll = random();                                     // ② 乱数2回目
      return {
        speed: result.speed * (margin[0] + roll * (margin[1] - margin[0])),
        azimuth: result.azim,
        elevation: elev,
      };
    }
    case "absolute": {
      const { sp } = speedSpec;
      let speed = sp[0] + random() * (sp[1] - sp[0]);             // ② 乱数2回目
      if (type === "SMASH") {
        speed *= 0.86 + 0.14 * Math.min(1, Math.max(0, (ballY - 20) / 30));
      }
      const result = solveAngle(from, targetX, targetZ, speed, spin, side);
      return { speed, azimuth: result.azim, elevation: result.elev };
    }
  }
}

// 誤差適用で3要素すべてを更新するため、3つとも可変で受ける（レビュー P1-01）
let { speed, elevation, azimuth } = launchPlan(shot.speed);

// arc（LOB）は現行どおり ensureNetClear を通さない。**この条件は必須**（下記）。
if (
  shot.speed.model !== "arc" &&
  !extraError &&
  contactQuality > 0.3
) {
  elevation = ensureNetClear(from, elevation, azimuth, speed, spin, side);
}

const error = shot.err + (1 - contactQuality) * 0.055 + extraError;
elevation += (random() * 2 - 1) * error;        // ③
azimuth += (random() * 2 - 1) * error * 1.5;    // ④
speed *= 1 + (random() * 2 - 1) * error * 1.6;  // ⑤

return { ...launch(speed, elevation, azimuth), spin, side };
```

**非破壊の要点**:

- `absolute` の分岐は現行 `else` ブロックと式・順序が同一 → `DRIVE` / `SMASH` / `PUSH` / `CHOP` はビット不変。
- `arc` は `ensureNetClear` を通さないため `LOB` もビット不変。**`shot.speed.model !== "arc"` の条件を落とすと LOB が変わる**ので必須。これは理屈上の注意ではなく実測済みの分岐で、`LOB` の基準弾道が実際にネットへ掛かる条件が存在する（180条件を走査して **6件**。すべて **打点 `abs(z) = 30`（`CONTACT_PLANE_NEAR`）かつ `y = -46`（`SHOT_ORIGIN_Y_MIN`）** の帯）。この帯を U33 の基準ベクトルへ必ず含め、誤って `arc` に適用したら fail するようにする（レビュー P2-01）。
- 誤差適用は3ショットモデル共通・現行と同一。以降に補正が無い（S14 の撤去）。
- **型検査の確認済み**: 上記の完成形を現行 `tsconfig.json`（`strict` / `noUncheckedIndexedAccess` / `exactOptionalPropertyTypes`）へ当てて `npm run typecheck` が pass することを設計時点で実地確認した（2026-07-30）。3要素を `let` の分割代入で受けること、網羅 switch を戻り値形式にすること、`sp` / `margin` をタプル型にすること（`noUncheckedIndexedAccess` 下で `[0]` / `[1]` が `number` になる）が条件（レビュー P1-01）。
- `solveSpeed()` の探索域 `[250, 1300]` は変更しない。下限 `250` に貼り付く STOP が 162 条件中21件あるが、下限を `180` / `120` へ広げても着地帯は `22/32/46`（p2/p50/p98）で変わらず、ミス率も 1.9%→2.2% の範囲に収まるため、**LOB のビット不変を優先して現行のまま据え置く**（二分探索の刻みが変わると LOB の解が変わる）。

`solveShot()` は約150行から約80行へ縮む。

### 4.3 短球しきい値（A-3）

`src/config.ts`: `SHORT_BOUNCE_Z` を `58` → **`48`**。`SHORT_BALL_MAX_Y`（`22`）は変更しない。

### 4.4 台上局面の終了性（A-4）

**保証対象を「台上局面の終了」に一意化する。得点への到達は保証対象にしない**（レビュー P1-02）。旧 §8.3-15 の「ストップの応酬が5往復以内に得点へ到達する」は supersede せず、手動確認（§5.4-7）として維持する。

#### 4.4.1 用語の定義（判定式）

台上局面 = 「直前の着地が短球で、打ち手が台上技術（`STOP` / `FLICK` / `PUSH`）を選べる状態」の連続。**終了の判定式**は次のとおりで、`n` 球目の打球後に評価する。

```
終了(n) ⇔ ミス(n) ∨ ¬短球(n)

ミス(n)   : simLand の結果が net、または自陣側、または台外
短球(n)   : isShortBall(着地z, 次打点でのy, 次の受け手) === true
            （着地z = その打球の着地点 z ＝ 次の lastBounceZ）
```

**「終了」は得点の発生を意味しない。** `¬短球(n)` で終わった局面は、そのまま長い球のラリーとして続きうる。実測表で easy が中央値・最大とも1球なのは、easy が最初の短球で必ず `PUSH` を選び**台上局面を抜ける**からであり、1球で得点するからではない。

#### 4.4.2 2つの性質（保証水準が違う）

| # | 性質 | 種別 | 実測 | 検証 |
|---|---|---|---|---|
| **S-1** | AI が短球で `PUSH` を選ぶと、その着地は**短球にならない**（`PUSH.dep = 88` は短球帯の外） | **決定論的**（列挙した格子上で全件） | **0 / 414 件が短球** | U31-a |
| **S-2** | `STOP` のミス率が**全接触品質帯で 0 より大きい**（`1.9%〜15.3%`・§5.2） | **確率的** | 下表 | U30 ＋ U31-b |

**S-2 から言えること／言えないこと**を明確にする。

- **言える**: 各球の終了確率が `p > 0` で下から抑えられるため、台上局面は**確率1で有限回で終了**し、継続長の裾は幾何的に減衰する。
- **言えない**: **球数のハード上限は無い。** 継続確率が正である確率過程には任意に長い列が存在する。したがって「24球以内」を製品の構造的上限として主張しない（レビュー P1-02）。
