### P1-01: R5の自動検証はAI挙動不変を証明できない

**対象**

- 計画書 §R5 完了条件（現行391〜392行）
- `tests/game-smoke.spec.js`
- `tests/game-core.test.ts`
- `src/game.ts` の `planAi` / `refineAi` / `aiThink` / `aiHit` / `aiServe`

**根拠**

計画書は、既存E2Eが15件通ることを「AI挙動が壊れていない証明」としている。しかし現行E2Eの5シナリオは、タイトル開始、一時停止、Service Worker、プレイヤーサーブ、320pxレイアウトだけであり、AIサーブ、AI返球、反応時刻、再予測、移動、ショット選択、乱数消費順を検証していない。単体テストも `chooseWeightedServe` の境界だけで、R5で移すAIロジック自体を固定していない。

R5では乱数を使う判断を `OpponentAi` に移し、乱数を使う打球生成を `Game.makeShot` に残す。呼び出し順や分岐が1つ変わるだけで、同じ乱数関数を渡しても以後のショット系列が変わり得る。1ポイントの手動確認ではこの差を再現可能な回帰基準にできない。

**必要な修正**

1. R5コミットに `OpponentAi` の決定論的単体テストを追加する。
2. 固定した乱数列を使い、少なくとも次を検証する。
   - `chooseServe`: サーブ種別、狙い、乱数消費順
   - `decideShot`: 範囲外の `null`、LOB / SMASH / CHOP / PUSH / DRIVE、難易度別aim、depth、quality、blunder
   - `plan` / `update`: react待ち、refine時刻、予測更新、最大移動量、`PADDLE_LIMIT` クランプ
   - `reset`: 現行 `newGame` と同じ `x = 0` / `plan = null` の状態遷移
3. PlaywrightにAIサーブ開始のシナリオを追加し、AIがサーバーのとき約700ms後に `rally` へ遷移することを自動確認する。可能なら固定乱数でAI返球も1ケース固定する。
4. §R5・§R6・§5の期待テスト件数を、追加後の実数へ更新する。「15件維持＝AI挙動不変」という表現は削除する。

**解消条件**

新しいAI単体テストとE2Eのテスト名・入力・期待値が計画書に明記され、R5完了条件がそれらのpassを要求していること。

### P1-02: R0の基準コミット手順が現在の索引と未追跡文書に対して成立しない

**対象**

- 計画書 §R0-1（現行110〜120行）
- 計画書 §R0-4（現行129〜137行）
- `docs/設計書インデックス.md`（現行8〜9行）

**根拠**

レビュー開始時点の状態は次のとおりだった。

```text
## master...origin/master
 M docs/設計書インデックス.md
?? docs/リファクタリング計画書_2026-07-27.md
?? docs/機能設計書_プレイヤー戦績とラケット表示改修_2026-07-27.md
```

索引はリファクタリング計画書と後続機能設計書の両方へリンクしている。一方、R0-4の `git add` はリファクタリング計画書、索引、実装ログだけを列挙しており、後続機能設計書と本レビュー文書を含まない。そのままコミットすると、索引が未追跡ファイルを参照する履歴を作り、直後の「docs関連の未追跡・未コミットが残っていない」という期待にも失敗する。

また、計画書をレビュー反映してからdocs基準コミットを作るとHEADは `6721ceb` ではなくなるため、「コードの前提コミット」と「現在のdocsを含むHEAD」を同一視しない確認方法が必要である。

**必要な修正**

1. R0-4の基準コミット対象をレビュー後の実ファイル集合で確定する。
2. 索引に残すリンク先は同じ基準コミットへ含める。後続機能設計書を今回コミットしないなら、その索引行も今回の基準コミットへ入れない。
3. 本レビュー文書と、レビュー反映後の計画書を基準コミットへ含める。
4. `git diff --cached --name-only` と文書リンク検査をコミット前ゲートへ追加する。
5. コードベースラインは `6721ceb` に対する `table-tennis/src`、`tests`、設定・スクリプトの差分有無で判定し、docs-onlyコミット後のHEADハッシュとは分離する。
6. 「未追跡は許容」と「docs未追跡0件」のどちらを採るかを明示し、許容する場合はパスを列挙する。

**解消条件**

更新後のR0コマンドを現在の作業ツリーへ適用した場合に、索引のリンク先が全て追跡され、意図した文書以外がステージされず、R0後の期待statusが一意に定まること。

### P2-01: `master` 直コミットは共通Gitルールと既存PR検証経路に反する

**対象**

- 計画書 §R0-1（現行118行）
- [共通AGENTS.md](../../../AGENTS.md)（現行141、144行）
- [test-table-tennis.yml](../../.github/workflows/test-table-tennis.yml)
- [README](../README.md)（現行91行）

**根拠**

本計画は5つのコードコミットを伴い、R5自身を中〜高リスクと評価しているため「大きな変更」に該当する。共通ルールは大きな変更前の作業ブランチを要求し、2台PC運用時の競合分離も要求している。さらにリポジトリにはPull Request時に `npm run check` を実行する専用ワークフローが既にある。`master` へのpushがPages公開トリガーであることは、作業ブランチを省略する理由ではなく、公開前の分離を強くする理由になる。

**必要な修正**

- R0で `master` と `6721ceb` を確認した後、`codex/refactor-table-tennis-phase3` などの作業ブランチを作る。
- R1〜R5は作業ブランチへコミットする。
- 最終検証後も、ユーザーが公開を承認するまでは `master` へ反映・pushしない。
- PRを使う場合は既存PRワークフローのgreenをマージ条件へ含める。PRを使わない場合も、統合前に `master` との差分とコミット列を確認する。

**解消条件**

計画書のブランチ・統合・公開順が共通ルールおよびPagesトリガーと矛盾しないこと。

### P2-02: R4の定数化対象と完了検査に同義リテラルの漏れがある

**対象**

- 計画書 §R4（現行315〜331行）
- `src/game.ts:630`
- `src/game.ts:929`
- `src/game.ts:983`
- `src/game.ts:999`

**根拠**

計画書は `game.ts:929` の `26` を `SMASH_MIN_Y`、`game.ts:983` の `-46` を `PLAYER_CONTACT_Y_MIN` として移す。しかし、実際にスマッシュ種別を成立させる `playerContact` の `game.ts:999` も `ball.y > 26` を使い、打球起点を作る `makeShot` の `game.ts:630` も `Math.max(ball.y, -46)` を使う。

前者を残すと、将来 `SMASH_MIN_Y` を変更した際にスマッシュ可能表示と実際のショット判定がずれる。後者も接触下限変更時に打球起点の下限だけ旧値へ残る。さらに現行の完了コマンドは定数の定義17行と4種類の代表リテラルしか確認しないため、この漏れがあってもpassする。

**必要な修正**

- `SMASH_MIN_Y` を `updateSmashable` と `playerContact` の両方で使う。
- `game.ts:630` は意味を確認し、同じ契約なら `PLAYER_CONTACT_Y_MIN` を使う。別概念なら `SHOT_ORIGIN_Y_MIN` など別名で意図を分離する。
- 完了条件に各定数の参照箇所・期待件数を含め、定義が存在するだけでは完了にしない。
- `npm run check` は値不変の十分な証明ではないため、R4差分で旧値と新定義の対応表を確認するゲートを追加する。

**解消条件**

同義リテラルの扱いが設計上決まり、完了コマンドが定義漏れ・参照漏れの双方を検出できること。

### P2-03: 公開承認後のライブ検証とService Worker更新確認が完了条件にない

**対象**

- 計画書 §1.3-7〜8（現行64〜65行）
- 計画書 §5（現行438〜447行）
- [共通AGENTS.md](../../../AGENTS.md) §6.7
- `sw.js:1`、`sw.js:43`、`sw.js:55`

**根拠**

計画書の手動確認はローカル `npm run dev` までで、最後は「ユーザー承認後にpush」として終了している。公開が承認された場合に必要なActions run、Pages deployment、公開HTTP資産、Chrome実操作の確認が手順化されていない。共通ルールは公開時にこれら全てを確認することを完了条件としている。

また、成果物は固定名 `assets/app.js` で、Service Workerは同じ `table-tennis-v2` キャッシュを使い、キャッシュがあればそれを先に返してバックグラウンドで更新する。キャッシュ名据え置き自体を直ちに否定するものではないが、既存PWA利用者が新しいapp.jsへ更新される経路を公開確認しないと、初回表示の旧キャッシュを新リリースと誤認し得る。

**必要な修正**

「公開承認がない場合」と「公開承認がある場合」を分け、後者には次を追加する。

1. 対象Actions runのbuild/deploy成功
2. Pages deploymentと対象コミットの一致
3. 公開HTML、manifest、Service Worker、app.js、app.css、iconsのHTTP確認
4. 公開app.jsとローカル `dist/assets/app.js` の内容またはハッシュ一致
5. 既存Service Worker／キャッシュがあるChromeで更新経路を確認し、新コードでゲーム開始・AIサーブ・AI返球が成立すること
6. 公開失敗時の中断・ロールバック判断

**解消条件**

公開を行う場合の完了条件が共通AGENTS.md §6.7を満たし、固定名アセットの更新確認方法が明記されること。
