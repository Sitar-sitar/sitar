## 1. 判定

**着手不可**

- P1: 1件
- P2: 4件
- P3: 1件

持ち手を共有描画へ追加する方針、奥行きを完全な透視投影ではなく画面空間の線形式で圧縮する方針、物理座標と描画追従値を分離する方針は妥当である。

一方、設計どおり横位置も `player.viewZ` で投影すると、ボールと当たり判定が使う `player.z` と投影スケールが分かれる。特に設計自身が追従未完了を許容している高速返球時は、「画面上で重なった位置」と実際の打球成立位置が一致しない。この状態は「打球判定は不変」「左右の一致は保たれる」という設計契約と両立しないため、P1-01を解消するまで実装へ進めない。

あわせて、小画面で最もはみ出しやすい条件、lockfileの版数、`viewZ` の状態遷移、奥行きだけを戻す場合の文書・版数整合を設計へ追加する必要がある。

## 3. 指摘事項

### P1-01: `viewZ` で横投影すると、ボールとラケットの画面上X座標が打球時に一致しない

**対象**

- 設計書 §3.2（95行）
- 設計書 §3.3（97〜105行）
- 設計書 §4.4（219〜233行）
- 設計書 §7-2、§7-3（307〜308行）
- `src/render.ts:106-112`
- `src/render.ts:539-542`
- `src/render.ts:617-631`
- `src/game.ts:863-865`
- `src/game.ts:935-943`

**根拠**

`Renderer.project()` のX座標は `camera.f / (z - camera.z)` を倍率として使うため、同じワールドXでもZが異なれば画面上Xが変わる。ボールは実際の `ball.z` で投影され、打球判定はボールが物理平面 `player.z` を通過した時に `ball.x` と `player.x` を比較する。

しかし設計書 §4.4 はラケットのX座標を `project(player.x, 0, player.viewZ).x` とする。`viewZ` が `player.z` へ到達していない間、ラケットだけが別の投影倍率になる。設計書 §7-3は高速球で追従が間に合わない場合を明示的に許容しているため、この差は理論上だけではなく設計上発生し得る。

例えば320×568px、`player.x = 104` では、現行投影式によるラケット中心の差は次のとおりになる。

- `player.z = -178`、`viewZ = -152`: 約41.6px
- `player.z = -178`、`viewZ = -62`: 約123.2px

この差は現行の当たり判定半径 `P_REACH = 31` より大きくなり得る。したがって、§7-2の「横位置は従来どおり投影値のため、ボールとの左右の一致は保たれる」は成立しない。「移動途中のラケットで打つ自然な絵」として許容できるのは縦位置・大きさの遷移であり、画面上の打球位置まで物理判定から離すと操作フィードバックを壊す。

**必要な修正**

1. 推奨案として、ラケットXは現行どおり `project(player.x, 0, player.z).x` を使い、縦位置・大きさ・影だけを `viewZ` から求める。これなら物理判定を変えず、打球時の左右一致を維持できる。
2. 横位置にも補間を入れる場合は、許容する最大ピクセル差、適用時間、打球瞬間に物理投影へ収束させる規則を定義する。単に `viewZ` を共用するだけでは不可とする。
3. `player.z !== player.viewZ` の状態で、ボールが `player.z` を通過するケースを決定論的なテスト条件へ追加する。少なくとも画面上Xの一致、または設計で確定した許容差を検証する。
4. §3.2、§4.4、§7-2、§7-3、§8.3-3の説明を同じ契約へ統一する。

**解消条件**

`viewZ` が追従途中でも、打球成立時のボールとラケットの画面上X座標が一致するか、明示した小さな許容差内になることが、投影式と自動テストで確認できること。

### P2-01: 版数更新の対象から `package-lock.json` が漏れている

**対象**

- 設計書 §4.7（264〜267行）
- 設計書 §6 S3（295行）
- 設計書 §9（366行）
- `package-lock.json:3`
- `package-lock.json:9`

**根拠**

設計書は `package.json` だけを `0.4.0` へ更新すると定め、S3の対象にも `package-lock.json` を含めていない。現行lockfileはトップレベルとルートパッケージの2か所に `version: "0.3.0"` を持つため、設計どおりでは同一リリース内で版数が分裂する。

依存関係が変わらなくても、`package-lock.json` はCIの `npm ci` とリリース追跡に使う正本の一部である。アプリ版数を更新するならルート版数も同期し、差分として確認できる必要がある。

**必要な修正**

1. §4.7とS3の対象へ `package-lock.json` を追加する。
2. `package.json` とlockfileのルート2か所を同じ `0.4.0` にする更新手順を定める。
3. 受け入れ条件へ3か所の版数一致を追加する。

**解消条件**

`package.json`、`package-lock.json` のトップレベル、`packages[""]` の版数がすべて `0.4.0` で一致し、`npm ci` を使う既存Actionsの入力が自己矛盾しないこと。

### P2-02: 320px確認が最もはみ出しやすい手前側・横画面を検証しない

**対象**

- 設計書 §4.2.3（159〜171行）
- 設計書 §4.3（197〜215行）
- 設計書 §5（281行）
- 設計書 §8.3-7（346行）

**根拠**

手動確認は「最も奥の打点」を対象にしているが、最も奥ではラケットが上へ移動し70%へ縮むため、画面下端へのはみ出しに対して最も安全な条件である。最もはみ出しやすいのは `depth = 1` の手前側で、画面高が小さい横向きである。

設計値を320×240pxへ当てはめると、`depth = 1` では次の寸法になる。

- ラケット中心Y: `240 * 0.86 = 206.4px`
- `paddleScreenRadius`: `18px`
- `paddle()` 内の実ブレード半径: `18 * 1.25 = 22.5px`
- 持ち手先端までの中心距離: `22.5 * (0.55 + 1.15) = 38.25px`
- 持ち手軸の先端Y: `206.4 + 38.25 = 244.65px`

太さとstrokeを含める前の軸だけで240pxを超えるため、横向き320×240pxでは持ち手が下端で欠ける。§5の「320px幅でラケットと影が画面内に収まる」は、現行の設計値と検証条件では保証できない。

**必要な修正**

1. 320px幅の確認を、少なくとも320×240の横向きと320×568相当の縦向きに分ける。
2. `depth = 0` だけでなく、最大サイズ・最下位置になる `depth = 1`、待機位置 `PZ`、最大傾きのスマッシュ／ツッツキを確認する。
3. 画面内に収めることを必須にするなら、持ち手を含む描画外接矩形からYを制限するか、定数を調整する規則を設計する。
4. 「視認できる」だけでなく、Canvas境界から持ち手・ブレード・影が欠けないことを受け入れ条件にする。

**解消条件**

対応対象とする最小縦横ビューポートが明記され、`depth = 0 / PZ / 1` と最大傾きでラケット全体と影がCanvas内に収まることを確認できること。

### P2-03: `viewZ` の初期化・追従・点間リセットが自動テストされない

**対象**

- 設計書 §4.6（246〜262行）
- 設計書 §8.1（318〜328行）
- 設計書 §9（361〜362行）
- `src/game.ts:304-325`
- `src/game.ts:426-440`
- `tests/game-core.test.ts:123-127`

**根拠**

U13〜U15は奥行き比、影、角度の純粋関数を検証し、既存の `moveToward` テストは1回の数値更新だけを検証する。設計で新たに導入する次の状態契約は自動検証されない。

- 初期値が `PZ`
- 返球で `player.z` が変わっても `viewZ` は瞬間移動しない
- 固定ステップごとに `P_DEPTH_SPEED * dt` 以下で追従する
- 目標を越えず最終的に一致する
- 点間の `startServe()` では `PZ` へ即時リセットする
- 相手側 `viewZ` は初期化・リセットだけで更新しない

これらの結線を1行でも漏らすと、型検査とU13〜U15がgreenでも、ラケットが動かない、ワープする、前ポイント位置から滑り続ける、といった受け入れ違反が残る。

**必要な修正**

`viewZ` の状態遷移を決定論的に検証できるテスト境界を設け、上記6条件を自動テストへ追加する。実装を過剰に公開しない範囲で、状態更新を純粋関数へ切り出すか、`Game` のテスト用スナップショットを最小限用意する。

**解消条件**

追従開始、複数tick、到達、点間リセット、相手側非追従の各ケースが自動テストで固定され、期待件数が追加後の実数へ更新されていること。

### P2-04: S2単独revertでは、版数・README・supersede状態が奥行き実装と食い違う

- 設計書 §0（15〜26行）

**根拠**

## 4. 確認できた妥当な点

- `Game.playerContact`、`contactPlane`、`makeShot` を変更せず、描画専用値を分離する基本方針は、物理挙動を守る変更境界として妥当である。
- `paddleScreenY`、`paddleScreenRadius`、奥行き比、影、角度を純粋関数へ集約する方針は、Canvas描画と計算契約を分離できる。
- 持ち手を先に描き、ブレードを後から重ねて根元を隠す描画順と、相手側では手から腕の付け根へ向ける角度計算は、現行 `drawOpponent()` の座標から実装可能である。
- `startServe()` で点間をスナップさせ、通常tickだけを補間する方針は、前ポイントからの不自然な復帰アニメーションを避ける。
- Service Workerキャッシュ名を固定名アセットの変更に合わせて更新し、公開後に既存キャッシュ経路を確認する方針は妥当である。
- S1とS2を型が閉じる垂直スライスへ分ける方針は、持ち手と奥行きを独立に検証する単位として利用できる。
